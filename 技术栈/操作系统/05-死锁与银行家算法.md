# 05 死锁与银行家算法

[返回教程目录](操作系统教程.md) · [下一章：内存管理](06-内存管理与地址转换.md)

## 本章目标

解释死锁四个必要条件，区分死锁、饥饿和活锁，独立完成安全性和资源请求判断。

## 1. 死锁是什么

任务 A 持有打印机，等待扫描仪；任务 B 持有扫描仪，等待打印机。双方都不主动释放已有资源，也没有外部处理措施，就无法继续。

死锁：一组任务中的每个任务都等待其他成员才能产生的事件，导致这组任务无法推进。

| 现象 | 是否在执行 / 尝试 | 核心原因 |
| --- | --- | --- |
| 死锁 | 等待无法自行解除 | 形成相互依赖 |
| 饥饿 | 其他任务可以继续 | 一直分不到所需资源 |
| 活锁 | 反复动作，但没有有效进展 | 双方持续让步或重试 |

## 2. 四个必要条件

1. **互斥**：至少有资源不能被多个任务同时占用。
2. **占有且等待**：已有资源尚未释放，又等待更多资源。
3. **不可剥夺**：资源不能由系统随意强制收回。
4. **循环等待**：任务等待关系形成闭环。

四条件是经典资源死锁模型中的必要条件。对多实例资源，仅看到资源分配图有环，并不足以断言已经死锁；每类资源只有一个实例时，环可以判定死锁。

## 3. 处理策略

| 策略 | 思路 | 例子与代价 |
| --- | --- | --- |
| 预防 | 从规则上破坏某个必要条件 | 统一锁顺序；一次申请全部资源，但利用率可能低 |
| 避免 | 每次分配前判断是否仍安全 | 银行家算法；需知道最大需求 |
| 检测与解除 | 允许发生，再检测和恢复 | 终止任务、回滚或回收可剥夺资源 |
| 忽略 | 权衡后不做通用处理 | 应用或管理员负责处置部分情况 |

“避免”和“预防”不同：预防制定限制规则；避免在运行过程中判断具体分配是否安全。

## 4. 安全状态不等于当前资源足够满足所有人

安全状态：存在某种完成顺序，按照这个顺序，每个任务都能取得其剩余所需资源，完成后释放已有资源，让后续任务继续。

不安全状态：找不到这样的保证。**不安全不一定已经死锁**，因为任务实际需求可能小于声明上限，或者它们会提前释放资源。

## 5. 银行家算法的四类数据

- Available：目前可用资源向量。
- Max：每个任务声明的最大需求。
- Allocation：已分配给每个任务的资源。
- Need = Max − Allocation：还可能需要的资源。

所有向量比较均逐分量进行。比如 (1,2,0) ≤ (2,2,1) 成立。

## 6. 完整安全性例题

资源 A、B、C，Available = (3,3,2)。

| 进程 | Allocation | Max | Need |
| --- | --- | --- | --- |
| P0 | (0,1,0) | (7,5,3) | (7,4,3) |
| P1 | (2,0,0) | (3,2,2) | (1,2,2) |
| P2 | (3,0,2) | (9,0,2) | (6,0,0) |
| P3 | (2,1,1) | (2,2,2) | (0,1,1) |
| P4 | (0,0,2) | (4,3,3) | (4,3,1) |

令 Work 初始等于 Available。找未完成且 Need ≤ Work 的进程，假设它完成，然后把它原有的 Allocation 加回 Work。

| 步骤 | 选择进程 | 选择前 Work | Need 是否满足 | 完成后 Work |
| --- | --- | --- | --- | --- |
| 1 | P1 | (3,3,2) | (1,2,2) ≤ Work | (5,3,2) |
| 2 | P3 | (5,3,2) | (0,1,1) ≤ Work | (7,4,3) |
| 3 | P4 | (7,4,3) | (4,3,1) ≤ Work | (7,4,5) |
| 4 | P0 | (7,4,5) | (7,4,3) ≤ Work | (7,5,5) |
| 5 | P2 | (7,5,5) | (6,0,0) ≤ Work | (10,5,7) |

所以系统安全，一个安全序列是 **P1 → P3 → P4 → P0 → P2**。安全序列可以不唯一。

为什么不是加 Max？因为 Work 在推演中没有实际扣除临时满足 Need 的资源：如果显式借出 Need 再归还 Max，净变化也正好是 Allocation。

## 7. 资源请求判断

在原始状态下，P1 请求 Request=(1,0,2)。

1. Request ≤ Need(P1)=(1,2,2)，没有超出声明需求。
2. Request ≤ Available=(3,3,2)，现有资源足够试分配。
3. 试分配：Available=(2,3,0)；Allocation(P1)=(3,0,2)；Need(P1)=(0,2,0)。
4. 检查安全性：P1 完成后 Work=(5,3,2)，然后可按 P3、P4、P0、P2 完成。
5. 仍安全，可以批准。

另看一个**独立请求**：在原始状态下，P4 请求 (3,3,0)。前两项检查通过；试分配后 Available=(0,0,2)，P4 的 Need=(1,0,1)。这时没有任何进程的 Need ≤ Work，状态不安全，应撤销试分配、让 P4 等待。

资源够分配，不代表分配后安全。

## 8. 面试中的死锁治理

优先建立统一锁顺序，缩小锁范围，减少嵌套锁，避免持锁进行长时间外部 I/O。必要时使用限时获取和失败恢复。

超时不是自动修复：失败后必须释放已持有资源，并确认业务状态可以回滚或重试。线程转储可以帮助观察“谁持有什么、谁等什么”，但某些跨进程或分布式依赖不会直接显示为 JVM 内部死锁。

## 自测与答案

1. “当前每个进程都不能立即取得全部剩余资源”，是否说明不安全？
2. 不安全状态是否等于已死锁？
3. 找安全序列时，Work 应增加 Allocation 还是 Need？

**答案**：①不一定，可能先让某个进程完成再释放资源；②不等于；③增加 Allocation。
