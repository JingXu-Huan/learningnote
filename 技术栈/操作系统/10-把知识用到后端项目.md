# 10 把知识用到后端项目

[返回教程目录](操作系统教程.md) · [下一章：期末模拟卷](11-期末模拟卷与解析.md)

## 本章目标

把课程概念连接到 Java 服务和 IoT 数据平台，形成从现象到证据的排查思路。

## 1. 贯穿案例：校园用水数据接入

假设设备持续上报读数，网关接收请求，Java 服务验证数据并写入数据库，后台任务生成告警。

| 操作系统概念 | 项目中对应什么 |
| --- | --- |
| 进程 | 网关、Java 服务、数据库各自的运行实例 |
| 线程 | 请求处理、数据库访问、定时任务等执行流 |
| 调度 | 多个可运行线程竞争 CPU 时间 |
| 同步与互斥 | 维护共享队列、更新共享状态 |
| I/O 等待 | 等设备网络数据、数据库响应、日志写入 |
| 虚拟内存 | 各进程地址空间、页映射和实际驻留 |
| 文件系统 | 日志、配置、数据库文件 |

一次请求往往交替经历“计算”和“等待”。因此，线程数量、CPU 利用率和请求数量不会总是同步增长。

## 2. 为什么线程多不一定吞吐高

CPU 密集型任务如压缩和复杂计算，需要真实 CPU 时间。线程数量远超可用执行能力时，更多线程可能只增加切换、栈内存和竞争。

I/O 密集型任务常在等外部结果，多一些并发可以覆盖等待，但会受数据库连接数、下游容量、队列长度和超时约束。

有时可用 N×(1+等待时间/计算时间) 估计传统平台线程的数量起点，其中 N 为可用核心数。它只是基于简化假设的经验估计，不能代替实际测量，也不应直接套用于虚拟线程或协程。

线程池要同时考虑：**工作线程数、任务队列容量、拒绝策略、超时和下游承受能力**。无界队列可能把过载隐藏成越来越长的等待和内存占用。

## 3. 排查先区分是哪一种慢

| 现象 | 可能原因 | 下一步看什么证据 |
| --- | --- | --- |
| CPU 高、延迟高 | 计算过重、空轮询、热点竞争、GC | 热点线程、CPU 分析、GC 日志 |
| CPU 不高、延迟高 | 等数据库、连接池、锁、磁盘或网络 | 线程状态、队列等待、下游耗时 |
| 内存持续上涨 | 缓存增长、对象保留、线程增长、本地内存 | 堆统计、线程数、驻留内存、分配趋势 |
| 磁盘忙、响应慢 | 写入压力、同步刷盘、交换活动 | I/O 延迟、队列、吞吐、换页指标 |
| 线程数持续增加 | 阻塞堆积、任务无边界扩张 | 创建来源、等待对象、池与队列配置 |

这些是待验证的假设，不是看到一个指标就能定论。

例如 CPU 高并不直接证明“线程太多”：可能只有一个线程在无限循环。CPU 低也不直接证明“服务器资源够用”：任务可能全在等一把锁。

## 4. 一个可以在面试中复述的过程

问题：设备上报突增，接口从 50 ms 变成 3 s，但 CPU 只有 25%。

1. 先确认变慢范围：所有接口还是写入接口？与流量、发布或数据库事件是否同时发生？
2. 将总延迟拆成入口排队、业务处理、连接池等待、数据库执行和返回。
3. 查看线程状态和转储：是否大量线程在等同一资源？
4. 查看连接池与数据库指标：是否连接耗尽，或查询、锁等待变长？
5. 检查任务队列长度、请求超时和重试：是否已经形成堆积或重试放大？
6. 依据证据采取措施：限制并发、修复慢查询、缩短锁范围、调整资源容量等。
7. 用相同负载验证延迟、错误率、队列和资源变化。

这里最重要的推理是：**CPU 不高且请求慢，先找等待时间在哪里。** 直接扩大线程池可能让更多请求一起等数据库。

## 5. Java 内存与线程状态的边界

JVM 内存不只包含堆。即使堆使用正常，也可能因为线程栈、直接内存或其他本地资源导致进程内存过高。

Java 的 NEW、RUNNABLE、BLOCKED、WAITING、TIMED_WAITING、TERMINATED 是 JVM 线程状态，不是第 02 章操作系统状态图的一一翻译。

- Java BLOCKED 特指等待进入 synchronized 监视器等相应情形，不能拿它代表所有 I/O 等待。
- Java RUNNABLE 也不能直接证明该线程此刻正在 CPU 上计算。
- 某些锁等待会表现为 WAITING / TIMED_WAITING，要结合调用栈解释。

分析状态时应同时看线程栈和 CPU 时间，不能只数某种状态的数量。JVM 状态的定义与操作系统状态的区别，可核对 [Java Thread.State 官方文档](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/Thread.State.html)。

## 6. 容器与虚拟机（拓展）

虚拟机通常运行自己的操作系统内核，通过虚拟化获得硬件环境；常见 Linux 容器共享所在宿主环境的内核，通过隔离和资源限制形成运行环境。

容器内存超限可能导致进程被终止，即使机器还有可用内存，因为容器有独立限制。容器 CPU 配额限制也可能使任务延迟增加，而宿主机整体 CPU 未满。

在 Windows 或 macOS 上运行 Linux 容器时，背后可能存在 Linux 虚拟机，因此应说清你观察的是容器、虚拟机还是物理宿主。

## 7. 可选观察练习：无需写代码

在 Windows 任务管理器的“详细信息”页观察进程、线程数、CPU 和内存；在资源监视器中观察磁盘、网络活动。不同工具的内存列定义不同，比较时先确认含义。

如果已有 Linux 环境，可只读查看以下指标；不需要为了本章额外安装环境。

| 工具 | 用途 | 注意 |
| --- | --- | --- |
| top / ps | 查看进程和线程活动 | 指标是观察样本，不是完整因果证明 |
| vmstat | 观察运行队列、内存与交换活动 | 列含义与单位先查本机手册 |
| iostat | 观察设备吞吐与延迟 | 常需单独安装，不是所有系统默认存在 |
| free | 查看内存统计 | Linux 的缓存可回收，空闲少不直接代表内存不足 |
| jcmd / jstack | 查看 JVM 信息、线程栈 | 需要对应权限与工具；现场采集也有成本 |

## 自测与答案

1. CPU 低、延迟高，第一步是否应该加线程？
2. JVM 堆正常，是否说明进程没有内存问题？
3. Java RUNNABLE 是否等于操作系统“此刻运行”？

**答案**：①先定位等待和瓶颈；②不是，还要看其他内存来源；③不是，要结合调用栈和 CPU 时间。
