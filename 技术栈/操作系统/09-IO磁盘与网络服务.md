# 09 I/O、磁盘与网络服务

[返回教程目录](操作系统教程.md) · [下一章：后端项目应用](10-把知识用到后端项目.md)

## 本章目标

理解设备访问、缓冲和 DMA，手算磁盘调度，并分清阻塞、非阻塞、多路复用和异步 I/O。

## 1. I/O 为什么常常需要等待

CPU 执行速度与设备工作速度不同。程序请求的数据可能仍在磁盘、网络或设备队列中，因此任务会等待。

| 方式 | 谁承担什么工作 | 理解重点 |
| --- | --- | --- |
| 程序查询 / 轮询 | CPU 反复检查设备状态 | 简单，但可能浪费 CPU |
| 中断驱动 | 设备到适当时机通知 CPU | CPU 不必一直检查 |
| DMA | 专门机制在设备与内存间传输数据 | CPU 设置和处理结果，减少逐项搬运负担 |

DMA 并不意味着 CPU 完全不参与，也不意味着应用层永远没有复制。

**缓冲**用于缓解速度差异、合并传输和暂存数据；**缓存**主要利用访问局部性，减少重复获取。同一片区域有时兼具两类作用。

拓展：假脱机 Spooling 可把多个打印任务暂存到磁盘队列，再由服务统一交给打印机，提高协作便利性；打印机物理上仍按其能力处理任务。

## 2. 磁盘调度：先说明模型

经典磁盘题讨论机械硬盘的磁头移动；寻道、旋转等待和传输构成访问时间。SSD 没有机械寻道，不能直接用磁头移动距离解释其真实性能。

| 算法 | 行为 |
| --- | --- |
| FCFS | 按请求到达顺序 |
| SSTF | 每次选离当前磁头最近的请求 |
| SCAN | 按一个方向移动到端点，再反向服务 |
| LOOK | 按一个方向服务到该方向最后一个请求，再反向 |
| C-SCAN | 单方向服务，到端点后回到另一端 |
| C-LOOK | 单方向服务，到最后请求后跳到另一侧最远请求 |

SSTF 可能让远处请求饥饿；扫描类算法改善等待分布。SCAN 与 LOOK 的端点规则是高频辨析点。

## 3. 完整磁盘调度例题

磁道编号 0～199，磁头初始在 53，初始方向朝编号增大；请求队列：98、183、37、122、14、124、65、67。假设无新请求，处理完最后一个请求即可结束。

| 算法 | 移动路径 | 总移动量 |
| --- | --- | --- |
| FCFS | 53→98→183→37→122→14→124→65→67 | 640 |
| SSTF | 53→65→67→37→14→98→122→124→183 | 236 |
| SCAN | 53→65→67→98→122→124→183→199→37→14 | 331 |
| LOOK | 53→65→67→98→122→124→183→37→14 | 299 |
| C-SCAN | 53→65→67→98→122→124→183→199→0→14→37 | 382 |
| C-LOOK | 53→65→67→98→122→124→183→14→37 | 322 |

SCAN：从 53 到 199，再到 14，总量 (199−53)+(199−14)=331。

C-SCAN：从 53 到 199，回到 0，再到 37，总量 146+199+37=382。此表把回绕移动计入；如果题目规定不计回绕，须按题设重算。

LOOK：从 53 到 183，再到 14，总量 130+169=299。

平均移动量 = 总移动量 / 请求数。例如 SSTF 为 236/8=29.5。

## 4. RAID 基础（拓展）

假设 N 块等容量磁盘，每块容量 S，忽略元数据开销。

| 级别 | 思路 | 常见有效容量 | 容错理解 |
| --- | --- | --- | --- |
| RAID 0 | 条带化 | N×S | 无冗余，单盘故障可破坏阵列数据 |
| RAID 1 | 镜像 | 两盘镜像约为 S | 两盘镜像可容忍其中一盘故障 |
| RAID 5 | 分布式单校验 | (N−1)×S | 通常容忍一盘故障，至少三盘 |
| RAID 6 | 双校验 | (N−2)×S | 通常容忍两盘故障，至少四盘 |
| RAID 10 | 镜像后条带化 | N×S/2 | 是否能承受多盘故障取决于故障是否落在同一镜像组 |

RAID 增加某些设备故障下的可用性，不替代备份：误删、逻辑损坏等可能传播到冗余副本。

## 5. I/O 模型的两个观察角度

**阻塞 / 非阻塞**：发起操作后，如果此刻不能完成，调用是否等待，还是立即返回“暂时不能完成”。

**同步 / 异步 I/O**：在常见接口模型中，谁等待并取得操作结果，是否由完成通知报告结果。具体 API 的术语需结合其定义，不能只看有没有回调。

以 Socket 读取为例：

| 模型 | 工作过程 | 主要代价或优势 |
| --- | --- | --- |
| 阻塞 I/O | 请求读取，没数据时等待 | 简单，但大量等待连接可能需要很多线程 |
| 非阻塞轮询 | 读取立即返回，未就绪则稍后重试 | 避免单次长期等待，但忙轮询可能耗 CPU |
| I/O 多路复用 | 先统一等待哪些连接就绪，再读取 | 一个或少量线程可管理大量等待连接 |
| 异步 I/O | 提交操作，之后接收完成结果 | 适合完成事件驱动，但支持与语义依接口而异 |

多路复用的“多”指同时监控多个 I/O 对象，**不代表数据读取已经完成**。就绪通知之后通常还要调用相应读写操作。

## 6. select、poll 与 epoll

select / poll 常通过检查集合来找就绪对象；epoll 维护注册兴趣与就绪事件，适合大量连接中部分活跃的情况。但任何机制都有注册、事件处理、内存与调度成本，不能把 epoll 的总体处理成本说成无条件 O(1)。

Linux epoll 是 I/O 就绪通知机制；等待函数本身也可以阻塞。水平触发 LT 在条件仍满足时可继续通知；边缘触发 ET 的使用需要正确管理就绪状态，常配合非阻塞读写，处理到暂时没有数据或无法继续。它不直接等于异步 I/O 完成通知。[epoll 官方手册](https://man7.org/linux/man-pages/man7/epoll.7.html)

对后端开发，先抓住一个关键边界：事件线程可以高效管理等待，但若在上面做很慢的数据库调用或 CPU 计算，仍可能阻塞其他连接的处理。

## 7. 零拷贝如何表达

零拷贝通常指**减少某些数据复制或用户态 / 内核态之间的搬运**，不等于物理上没有任何数据移动。

sendfile、内存映射等可在不同路径下减少复制或调用开销，具体效果受操作、平台和设备能力影响。面试先描述传统路径，再说明优化省掉哪一段，不必背绝对固定的复制次数。

## 自测与答案

1. DMA 工作时，CPU 是否完全无需参与？
2. LOOK 是否一定要移动到磁盘端点？
3. epoll 返回可读事件是否意味着数据已经放进应用缓冲区？
4. 非阻塞是否一定更省 CPU？

**答案**：①仍需设置和处理结果；②不必，到该方向最后请求即可反向；③不意味着；④不一定，频繁空轮询可能更耗 CPU。
