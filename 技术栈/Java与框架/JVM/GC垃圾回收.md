## 一、GC 如何判断对象是垃圾

主流 JVM 的核心思路是**可达性分析**：

1. 选出一批 GC Roots；
2. 从 Roots 沿引用链向下遍历；
3. 能被遍历到的是可达对象；
4. 无法从 Roots 到达的对象，才有资格被回收。

这也是循环引用通常不会导致 Java 堆对象永远无法回收的原因：

~~~java
class Node {
    Node next;
}

Node a = new Node();
Node b = new Node();
a.next = b;
b.next = a;
a = null;
b = null;
~~~

即使两个 Node 互相引用，只要整个环都不再能从任何 GC Root 到达，它们仍然可以被回收。

## 二、GC Roots 都有哪些

常见的 GC Roots 来源包括：

- 活动线程的栈帧和 JIT 寄存器中的对象引用；
- 已加载类的静态字段引用；
- JNI / 本地方法持有的引用；
- JVM 内部结构、活动线程、代码缓存等实现相关引用。

因此，一个方法里的局部变量可能暂时让对象保持可达：

~~~java
void handle() {
    User user = loadUser(); // 栈帧中的 user 是一条可达路径
    process(user);
}
~~~

方法执行结束不代表对象必然立即被回收，只是其中一条引用路径可能消失。对象何时真正不可达，要看所有 Roots 的引用链。

## 三、动画中的回收过程

动画使用**经典代际模型**解释基本过程，按“分配 → Roots → 标记 → 转移 / 清理 → 老年代压力”展开：

1. 新对象先被分配到 Eden（示意）；
2. Eden 空间紧张或达到阈值，触发一次年轻代收集；
3. JVM 在需要的阶段暂停应用线程，枚举 GC Roots；
4. 从 Roots 出发标记可达对象；
5. 存活对象复制到 Survivor，或在条件满足时晋升到 Old；
6. 不可达对象的空间被清理，Eden 再次可用于分配；
7. 老年代压力较高时，收集器可能执行老年代回收、Mixed GC 或 Full GC。

> **STW（Stop The World）不等于整个 GC 都停顿。**并发收集器可以让大量标记、转移等工作与应用并发执行，但关键阶段通常仍需要短暂停顿。

## 四、分代模型与对象晋升

为什么很多 JVM 会有“年轻对象”和“老对象”的概念？

因为大量对象生命周期很短。把年轻对象放在适合快速回收的区域，可以减少扫描长期对象的成本。

常见的学习模型：

| 区域 | 作用 |
| --- | --- |
| Eden | 新对象通常先进入这里 |
| Survivor | Young GC 后暂存仍存活的对象，记录年龄 |
| Old Gen | 长期存活或 Survivor 放不下的对象可能进入这里 |

一次 Young GC 中，存活对象通常被复制到另一块 Survivor 区，年龄加一。达到年龄阈值，或 Survivor 空间不足时，对象可能晋升到老年代。

不过要牢记：

- Eden / Survivor / Old 是收集器实现层的常见模型，不是 JVM 规范强制的连续分块；
- G1 把堆划分为许多 Region，年轻代、老年代只是 Region 当前承担的逻辑角色；
- ZGC、Shenandoah 等收集器的实现策略也不同。

## 五、标记、清扫、复制与整理

不同收集器会组合使用不同算法思想：

| 思想 | 大致过程 | 优点 | 典型代价 |
| --- | --- | --- | --- |
| 标记-清扫 | 标记存活对象，清扫其余空间 | 实现直观 | 可能留下碎片 |
| 标记-整理 | 标记后把存活对象压缩到一端 | 空间连续 | 移动对象成本较高 |
| 复制 | 把存活对象复制到另一块区域 | 分配快、碎片少 | 需要预留复制空间 |

对象可以在 GC 期间移动。因此，Java 程序不能依赖对象“内存地址恒定”；JVM 会通过更新引用或读写屏障等机制保证程序看到正确对象。

## 六、Minor、Major、Full GC 不要混用

这些术语在不同 JVM、收集器和监控工具中的含义并不完全一致：

| 常见称呼 | 学习时可先理解为 | 注意 |
| --- | --- | --- |
| Young GC / Minor GC | 主要回收年轻代 | 触发条件和范围依收集器而变 |
| Major GC | 有时被用来指老年代回收 | 没有统一、严格的跨收集器定义 |
| Full GC | 更大范围、通常代价更高的回收 | 具体覆盖哪些区域取决于收集器 |
| Mixed GC（G1） | 回收年轻代加一部分老年代 Region | 是 G1 特有的重要概念 |

不要只看到日志里写着“Major”或“Full”就机械推断发生了什么。排障时必须查看收集器类型、启动参数和 GC 日志。

## 七、实战观察与常见误区

### 常用观察方式

JDK 9+ 可以先用统一日志观察 GC：

~~~bash
java -Xlog:gc*,safepoint -jar app.jar
~~~

实际排障还应结合：

- jcmd；
- JFR；
- 堆转储（Heap Dump）；
- 监控平台的 GC 次数、暂停时间、堆使用曲线；
- 当前 JVM 启动参数和实际收集器。

### 设为 null 就会立刻回收吗？

不会。设为 null 只是去掉一条引用；对象是否已完全不可达、GC 何时运行，仍由 JVM 决定。

### System.gc() 能保证立即回收吗？

不能。它通常只是一次请求，而且不应被当作资源管理手段。

### GC 能释放数据库连接、文件句柄吗？

不要依赖它。连接、文件、Socket 等外部资源应显式关闭，例如使用 try-with-resources。

~~~java
try (var input = new java.io.FileInputStream("data.txt")) {
    // use input
}
~~~

### 内存泄漏是不是“对象永远不被 GC”？

更准确地说，是程序本不再需要的对象，仍然被某条引用链保持可达，所以 GC 无法回收它。常见原因包括静态集合、缓存、监听器、ThreadLocal 使用不当等。

### 一句话总结

> GC 从 GC Roots 做可达性分析；不可达对象才可回收。分代、暂停时机和具体回收步骤都依赖实际 JVM 与收集器，不要把教学图当作唯一实现。
