## 1. 先建立正确的并发模型

### 1.1 三个容易混淆的概念

| 概念 | 含义 | 典型目标 |
| --- | --- | --- |
| 并发 Concurrency | 多个任务的生命周期重叠，轮流或协作推进 | 提高等待型系统吞吐 |
| 并行 Parallelism | 多个任务在同一时刻真正执行 | 利用多核加速计算 |
| 异步 Asynchrony | 发起操作后不阻塞当前执行流，完成时再继续 | 高效等待网络、数据库等 I/O |

一个单线程事件循环可以并发处理大量连接，但同一时刻通常只执行一个 Python 任务；多个进程则可以在多个 CPU 核上并行。

### 1.2 I/O 密集与 CPU 密集

- I/O 密集：大部分时间在等网络、数据库、磁盘、消息队列或用户输入。
- CPU 密集：大部分时间在执行纯 Python 计算，例如大规模压缩、图像处理或复杂算法。

这不是绝对二分。一个 API 请求可能先等待数据库，再进行较重的 JSON 转换。应先测量耗时和资源占用，再决定拆分位置。

### 1.3 常见执行模型

~~~text
同步单线程：一次完成一个任务，最易理解
线程：      多个执行流共享同一进程内存
进程：      多个独立进程，可真正利用多核
协程：      在事件循环中主动 await，让出执行权
~~~

选择并发模型的核心不是语法，而是：

1. 任务在哪里等待？
2. 依赖库是同步还是异步？
3. 是否需要共享内存？
4. 任务能否序列化？
5. 失败和取消应传播到哪里？
6. 最大并发量和资源上限是多少？

## 2. 准确理解 GIL

### 2.1 默认 CPython 中的 GIL

在常规的、启用 GIL 的 CPython 中，同一时刻通常只有一个线程执行 Python 字节码。解释器会在线程之间切换，阻塞 I/O 期间也通常会释放 GIL，因此线程仍然很适合许多 I/O 密集任务。

结论：

- 纯 Python CPU 密集循环通常不会仅靠增加线程获得多核加速。
- 等待网络和文件的线程可以在其他线程运行时挂起，因此能提升吞吐。
- 一些 C 扩展会在重计算时释放 GIL，例如部分 NumPy 操作；是否并行取决于扩展实现。
- GIL 是 CPython 实现机制，不应被当作 Python 语言层面的永久保证。

### 2.2 GIL 不等于线程安全

GIL 不会把多步业务操作变成原子事务：

~~~python
import threading

balance = 100
lock = threading.Lock()

def withdraw(amount: int) -> bool:
    global balance
    with lock:
        if balance < amount:
            return False
        balance -= amount
        return True
~~~

“检查余额”和“扣减余额”是一个逻辑整体，仍需要锁。即使某个单独的 `dict` 或 `list` 操作在当前实现中没有崩溃，也不能据此拼出线程安全业务协议。

### 2.3 可选的 free-threaded CPython

Python 3.13 起提供可选的 free-threaded 构建，可在关闭 GIL 时让线程并行执行。它不是本章 3.10 基线，也不能假设所有三方扩展都已兼容；不兼容扩展甚至可能重新启用 GIL。

因此新代码仍应：

- 使用 Lock、Queue 等明确同步机制，不依赖 GIL 的偶然保护。
- 在实际解释器和依赖组合上测试性能与正确性。
- 对 CPU 任务优先选择经过验证的进程池、原生扩展或专门任务系统。

Python 3.14 还提供 `InterpreterPoolExecutor`，每个工作线程使用独立解释器，可实现多核并行；这是 3.14+ 的高级选项，数据共享与兼容性模型不同，不应作为 3.10 项目的默认方案。

## 3. threading：共享内存的线程

### 3.1 创建和等待线程

~~~python
import threading
import time

def download(name: str) -> None:
    print(f"{name} started")
    time.sleep(0.5)  # 模拟阻塞 I/O
    print(f"{name} finished")

threads = [
    threading.Thread(target=download, args=(f"task-{index}",))
    for index in range(3)
]

for thread in threads:
    thread.start()

for thread in threads:
    thread.join()
~~~

`start` 启动新线程，`join` 等待结束。直接调用 `thread.run()` 不会创建并发线程。

手动管理少量长期线程时 `threading.Thread` 合适；批量短任务通常优先 `ThreadPoolExecutor`。

### 3.2 Lock 与 RLock

~~~python
import threading

counter = 0
counter_lock = threading.Lock()

def increment_many(times: int) -> None:
    global counter
    for _ in range(times):
        with counter_lock:
            counter += 1
~~~

- `Lock` 同一时刻只允许一个线程进入临界区。
- `RLock` 允许同一线程重复获取，适合可重入调用；不要用它掩盖不清晰的锁层次。
- 使用 `with lock` 确保异常时释放。
- 临界区尽量短，不在持锁时做缓慢网络 I/O。
- 多把锁必须规定固定获取顺序，避免死锁。

### 3.3 Event、Condition 与 Semaphore

| 原语 | 用途 |
| --- | --- |
| `Event` | 广播“某状态已发生”，例如停止信号 |
| `Condition` | 在锁保护的状态条件上等待与通知 |
| `Semaphore` | 限制同时进入某资源的线程数 |
| `Barrier` | 让固定数量线程在阶段边界会合 |

~~~python
import threading
import time

stop_event = threading.Event()

def worker() -> None:
    while not stop_event.wait(timeout=0.2):
        print("working")

thread = threading.Thread(target=worker)
thread.start()
time.sleep(0.7)
stop_event.set()
thread.join()
~~~

用 `Event.wait(timeout)` 比循环 `sleep` 后检查更及时，也便于安全停止。

### 3.4 `queue.Queue`：线程间通信

~~~python
from queue import Queue
import threading

SENTINEL = object()
jobs: Queue[object] = Queue(maxsize=100)

def consumer() -> None:
    while True:
        item = jobs.get()
        try:
            if item is SENTINEL:
                return
            print("processing", item)
        finally:
            jobs.task_done()

thread = threading.Thread(target=consumer)
thread.start()

for value in range(5):
    jobs.put(value)
jobs.put(SENTINEL)

jobs.join()
thread.join()
~~~

有界 `maxsize` 能给生产者施加背压，防止任务无限堆积。每次成功 `get` 都必须对应一次 `task_done`，否则 `join` 会永久等待。

### 3.5 daemon 线程不是清理方案

程序只剩 daemon 线程时解释器可以直接退出，文件、事务和网络缓冲区可能来不及清理。可靠服务应使用停止信号、`join` 和 `try/finally` 完成有序关闭。

## 4. concurrent.futures：优先使用的池接口

`concurrent.futures` 为线程池和进程池提供统一的 `Executor` / `Future` 接口。

### 4.1 ThreadPoolExecutor：阻塞 I/O

~~~python
from concurrent.futures import ThreadPoolExecutor, as_completed
from urllib.request import urlopen

def fetch_size(url: str) -> tuple[str, int]:
    with urlopen(url, timeout=5) as response:
        return url, len(response.read(1024 * 1024))

urls = [
    "https://example.com",
    "https://www.python.org",
]

with ThreadPoolExecutor(max_workers=8, thread_name_prefix="fetch") as executor:
    future_to_url = {
        executor.submit(fetch_size, url): url
        for url in urls
    }
    for future in as_completed(future_to_url):
        url = future_to_url[future]
        try:
            completed_url, size = future.result()
        except Exception as exc:
            print(url, "failed", exc)
        else:
            print(completed_url, size)
~~~

`submit` 返回 Future；异常会在 `future.result()` 时重新抛出。上下文管理器会调用 `shutdown(wait=True)`。

注意：

- `max_workers` 应根据上游连接数、数据库池、文件句柄和限流一起确定。
- 线程越多不一定越快，过多会增加内存和调度开销。
- 一次提交百万任务会占用大量内存；使用有界队列、分批提交或生产者—消费者模型。
- 请求函数本身仍需要超时，否则池关闭时可能长期等待。

### 4.2 避免线程池内部互等

下面的设计容易死锁：池中任务提交另一个任务到同一小池，然后同步等待其结果。

~~~python
from concurrent.futures import ThreadPoolExecutor

executor = ThreadPoolExecutor(max_workers=1)

def outer() -> int:
    inner_future = executor.submit(lambda: 42)
    return inner_future.result()  # 唯一 worker 正被 outer 占用
~~~

不要在同一受限池中形成 Future 循环等待。把编排放在池外，或重新设计任务粒度。

### 4.3 ProcessPoolExecutor：CPU 密集计算

~~~python
from concurrent.futures import ProcessPoolExecutor

def count_primes(limit: int) -> int:
    count = 0
    for number in range(2, limit):
        for divisor in range(2, int(number ** 0.5) + 1):
            if number % divisor == 0:
                break
        else:
            count += 1
    return count

def main() -> None:
    limits = [40_000, 45_000, 50_000]
    with ProcessPoolExecutor() as executor:
        results = list(executor.map(count_primes, limits))
    print(results)

if __name__ == "__main__":
    main()
~~~

Windows 通常使用 spawn 启动子进程，因此：

- 创建进程池的入口必须放在 `if __name__ == "__main__":` 保护中。
- 任务函数定义在可导入模块顶层，不使用 lambda、局部函数或 REPL 临时函数。
- 参数和返回值必须可 pickle。
- 不把数据库连接、锁、打开的文件和巨型不可序列化对象直接传给子进程。
- 进程启动和序列化有成本，小任务可能比单进程更慢。

## 5. multiprocessing：多进程并行

`multiprocessing` 提供 Process、Queue、Pipe、Pool、共享内存和同步原语。若只需“提交函数并收结果”，先用 `ProcessPoolExecutor`；需要长期自定义进程拓扑时再使用底层 API。

### 5.1 Process 与 Queue

~~~python
from multiprocessing import Process, Queue
from queue import Empty

def square_worker(source: Queue, target: Queue) -> None:
    while True:
        item = source.get()
        if item is None:
            return
        target.put((item, item * item))

def main() -> None:
    source: Queue = Queue()
    target: Queue = Queue()
    process = Process(target=square_worker, args=(source, target))
    process.start()

    for number in range(5):
        source.put(number)
    source.put(None)

    process.join(timeout=10)
    if process.is_alive():
        process.terminate()
        process.join()
        raise RuntimeError("worker did not stop")

    while True:
        try:
            print(target.get_nowait())
        except Empty:
            break

if __name__ == "__main__":
    main()
~~~

### 5.2 多进程设计原则

- 进程内存默认隔离，显式通过 Queue、Pipe、共享内存或外部存储通信。
- Queue 的消息仍需序列化；传输大对象可能抵消并行收益。
- `Manager` 使用代理进程，方便但通常更慢，不能当本地字典无成本使用。
- 优先传不可变、小粒度数据，减少共享可变状态。
- `terminate` 是最后手段，目标进程可能持有锁或正在写文件；先发协作式停止信号。
- 子进程日志集中化，避免多个进程无协调写同一文件。
- 创建数据库连接应在子进程内完成，不复用父进程连接池。

## 6. asyncio 基础

### 6.1 协程与事件循环

调用 `async def` 函数会创建协程对象，只有被 `await`、包装为 Task 或交给事件循环后才执行：

~~~python
import asyncio

async def greet(name: str) -> str:
    await asyncio.sleep(0.1)
    return f"hello, {name}"

async def main() -> None:
    message = await greet("Python")
    print(message)

asyncio.run(main())
~~~

`asyncio.run` 负责创建事件循环、运行入口协程和关闭循环。已经处于事件循环中的代码（FastAPI、Jupyter 等）不能嵌套调用它，应直接 `await`。

### 6.2 `await` 是协作式让出

事件循环线程一次执行一个任务，任务运行到可挂起的 `await` 时才让出控制权。以下代码会冻结整个事件循环：

~~~python
import time

async def wrong() -> None:
    time.sleep(5)  # 阻塞事件循环
~~~

改为：

~~~python
import asyncio

async def right() -> None:
    await asyncio.sleep(5)
~~~

只有“真正异步”的库调用才能带来异步 I/O。把同步 Requests、同步数据库驱动或 `time.sleep` 放进 `async def` 并不会自动异步。

### 6.3 顺序 await 与并发任务

顺序执行：

~~~python
first = await fetch("a")
second = await fetch("b")
~~~

并发执行：

~~~python
first, second = await asyncio.gather(
    fetch("a"),
    fetch("b"),
)
~~~

并发适合相互独立的等待型操作。若第二步依赖第一步结果，就应顺序执行。

## 7. TaskGroup、gather 与任务所有权

### 7.1 `asyncio.gather`：收集多个结果

Python 3.10+ 可用：

~~~python
import asyncio

async def load(name: str, delay: float) -> str:
    await asyncio.sleep(delay)
    return name

async def main() -> None:
    results = await asyncio.gather(
        load("a", 0.2),
        load("b", 0.1),
    )
    print(results)  # 按传入顺序，而非完成顺序

asyncio.run(main())
~~~

默认 `return_exceptions=False` 时，第一个异常会传播给等待者，但其他已提交任务不会因此自动全部取消。`return_exceptions=True` 会把异常当作结果返回，容易让失败被忽略，只应在调用者明确逐项处理时使用。

### 7.2 `asyncio.TaskGroup`：结构化并发

Python 3.11+ 推荐用 TaskGroup 表达“一组任务属于同一作用域”：

~~~python
import asyncio

async def main() -> None:
    async with asyncio.TaskGroup() as group:
        first = group.create_task(load("a", 0.2))
        second = group.create_task(load("b", 0.1))

    print(first.result(), second.result())

asyncio.run(main())
~~~

当组内某个普通任务失败时，TaskGroup 会取消其他任务，等待它们清理后以 ExceptionGroup 汇总错误。这比“创建后忘记管理的后台任务”更容易推理。

处理特定异常（Python 3.11+）：

~~~python
try:
    async with asyncio.TaskGroup() as group:
        group.create_task(operation_a())
        group.create_task(operation_b())
except* ValueError as group_error:
    for error in group_error.exceptions:
        print("invalid data", error)
~~~

### 7.3 Python 3.10 的显式清理方案

如果需要 TaskGroup 类似的“一个失败就取消其余任务”语义，可显式拥有所有 Task：

~~~python
import asyncio
from collections.abc import Awaitable
from typing import TypeVar

T = TypeVar("T")

async def gather_cancel_on_error(*items: Awaitable[T]) -> list[T]:
    tasks = [asyncio.create_task(item) for item in items]
    try:
        return await asyncio.gather(*tasks)
    except BaseException:
        for task in tasks:
            task.cancel()
        await asyncio.gather(*tasks, return_exceptions=True)
        raise
~~~

关键不是复制某个辅助函数，而是明确任务所有权：谁创建、谁等待、谁在失败和关机时取消。

### 7.4 不要制造“失联任务”

~~~python
# 风险：没有保存引用，也没有处理异常和关闭
asyncio.create_task(send_report())
~~~

如果任务必须完成：

- 在 TaskGroup 中创建并等待。
- 保存强引用，并在生命周期结束时取消与汇总异常。
- 持久任务放入外部任务队列，由 worker 重试和观测。

“不等待结果”不等于“不需要管理”。

## 8. 超时、取消与资源清理

### 8.1 Python 3.11+：`asyncio.timeout`

~~~python
import asyncio

async def load_with_timeout() -> bytes:
    try:
        async with asyncio.timeout(3):
            return await read_from_network()
    except TimeoutError:
        return b"fallback"
~~~

超时作用域可覆盖多个 await。超时内部通过取消当前任务实现，并在上下文外转换为 `TimeoutError`。

### 8.2 Python 3.10+：`asyncio.wait_for`

~~~python
import asyncio

async def load_with_timeout() -> bytes:
    try:
        return await asyncio.wait_for(read_from_network(), timeout=3)
    except asyncio.TimeoutError:
        return b"fallback"
~~~

Python 3.11 起 `asyncio.TimeoutError` 是内置 `TimeoutError` 的别名。为了兼容 3.10，可以按项目基线捕获 `asyncio.TimeoutError`。

超时不是“线程强杀”。被取消的协程必须有机会运行清理；底层同步调用若已经在线程中执行，取消等待者也不一定停止那个线程函数。

### 8.3 正确处理 CancelledError

~~~python
import asyncio

async def consume() -> None:
    resource = await open_resource()
    try:
        while True:
            item = await resource.receive()
            await process(item)
    except asyncio.CancelledError:
        print("consumer is stopping")
        raise
    finally:
        await resource.aclose()
~~~

`CancelledError` 用来协作式停止任务。捕获后完成必要清理，并通常重新抛出；吞掉它会让 TaskGroup 和超时机制行为异常。

更简单时优先异步上下文管理器：

~~~python
async with httpx.AsyncClient() as client:
    response = await client.get(url)
~~~

### 8.4 `asyncio.shield` 要慎用

`shield` 能让内部 awaitable 不因外层任务取消而被连带取消，但外层等待仍会收到 `CancelledError`。它可能延长关机并制造孤儿任务，只适合确实不能中断且有独立所有权的短清理动作。

数据库提交、文件替换等操作更应依赖明确事务和幂等设计，不能只靠 shield 获得可靠性。

### 8.5 清理顺序

可靠关闭通常按以下顺序：

1. 停止接收新任务。
2. 通知生产者和消费者结束。
3. 等待有界时间。
4. 取消剩余任务。
5. 等待取消传播和 `finally` 执行。
6. 关闭 HTTP 客户端、数据库池、文件和线程/进程池。

## 9. Queue、锁与背压

### 9.1 asyncio.Queue

`asyncio.Queue` 用于同一事件循环内的任务通信，不是线程安全队列。

~~~python
import asyncio

SENTINEL = object()

async def producer(queue: asyncio.Queue[object]) -> None:
    for number in range(10):
        await queue.put(number)
    await queue.put(SENTINEL)

async def consumer(queue: asyncio.Queue[object]) -> None:
    while True:
        item = await queue.get()
        try:
            if item is SENTINEL:
                return
            await asyncio.sleep(0.05)
            print("processed", item)
        finally:
            queue.task_done()

async def main() -> None:
    queue: asyncio.Queue[object] = asyncio.Queue(maxsize=5)
    producer_task = asyncio.create_task(producer(queue))
    consumer_task = asyncio.create_task(consumer(queue))

    await producer_task
    await queue.join()
    await consumer_task

asyncio.run(main())
~~~

`maxsize` 让 `put` 在队列满时等待，形成背压。没有上限的任务列表或队列会把短暂流量峰值变成内存事故。

多个消费者需要为每个消费者发送一个 sentinel，或使用明确的关闭协议。Python 3.13 新增 Queue shutdown API，但基线 3.10 项目不能依赖它。

### 9.2 asyncio.Lock

即使事件循环单线程，多次 await 之间仍可能被其他任务插入：

~~~python
import asyncio

lock = asyncio.Lock()
cache: dict[str, str] = {}

async def get_or_load(key: str) -> str:
    async with lock:
        cached = cache.get(key)
        if cached is not None:
            return cached

        value = await load_value(key)
        cache[key] = value
        return value
~~~

这个示例为了说明互斥，但它在锁内等待 I/O，会让所有不同 key 串行。更好的实际设计可能是：

- 为不同 key 建立独立锁。
- 缓存进行中的 Task，让同 key 请求合并。
- 在锁外加载，再用版本检查解决重复写。

锁保护的是“不变量”，不是某个变量本身。先写清楚哪些状态必须一起变化。

### 9.3 Lock、Semaphore、Event、Condition

| asyncio 原语 | 用途 |
| --- | --- |
| `Lock` | 单个事件循环内互斥修改状态 |
| `Semaphore` | 限制同时访问外部资源的任务数 |
| `Event` | 广播状态已发生 |
| `Condition` | 等待受锁保护的复杂状态条件 |

~~~python
import asyncio

limit = asyncio.Semaphore(10)

async def limited_fetch(url: str) -> bytes:
    async with limit:
        return await fetch(url)
~~~

信号量限制“正在进行”的数量，但不能替代超时、重试、上游限流和连接池配置。

asyncio 同步原语没有统一的 `timeout=` 参数；在 Python 3.10 可用 `asyncio.wait_for(lock.acquire(), timeout=...)`，并确保成功获取后释放。

不要在协程中使用 `threading.Lock` 包围 await；它会阻塞事件循环甚至死锁。线程状态使用线程原语，协程状态使用 asyncio 原语。

## 10. 桥接阻塞调用

### 10.1 `asyncio.to_thread`

Python 3.9+ 可把阻塞函数放入默认线程池：

~~~python
import asyncio
from pathlib import Path

def read_large_legacy_file(path: Path) -> str:
    return path.read_text(encoding="utf-8")

async def load_file(path: Path) -> str:
    return await asyncio.to_thread(read_large_legacy_file, path)
~~~

适用：

- 暂时无法替换的同步 HTTP / SDK。
- 阻塞文件或系统调用。
- 会释放 GIL 的扩展函数。

`to_thread` 通常不能让纯 Python CPU 密集代码获得多核加速。它只是避免阻塞事件循环，而且线程函数开始后不能被安全强杀。

### 10.2 `run_in_executor` 与进程池

需要指定独立线程池或进程池时：

~~~python
import asyncio
from concurrent.futures import ProcessPoolExecutor
from functools import partial

async def count_primes_async(
    limit: int,
    process_pool: ProcessPoolExecutor,
) -> int:
    loop = asyncio.get_running_loop()
    call = partial(count_primes, limit)
    return await loop.run_in_executor(process_pool, call)
~~~

进程池仍受可 pickle、入口保护和生命周期管理限制。真实应用应在受 main guard 保护的启动阶段或应用生命周期中创建池，在关闭阶段显式 `shutdown`。

### 10.3 从其他线程提交协程

事件循环通常只在其所属线程中操作。其他线程需要调度回循环时，可使用 `loop.call_soon_threadsafe`；提交协程可使用 `asyncio.run_coroutine_threadsafe(coro, loop)`。

不要从任意线程直接调用非线程安全的 asyncio 对象。

## 11. FastAPI 中的 async def 与 def

### 11.1 选择规则

| 路由内部主要调用 | 路由声明 |
| --- | --- |
| 可 `await` 的 HTTP、数据库、缓存客户端 | `async def` |
| 只有同步阻塞 SDK / ORM / 文件调用 | `def` |
| 很短且不阻塞的纯计算 | 两者都可，按调用链保持清晰 |
| 大量 CPU 计算 | 不在请求事件循环或普通线程池硬算；使用进程 / 任务系统 |

异步客户端应在应用 `lifespan` 中统一创建和关闭；下面给出可直接运行的最小示例，避免路由访问尚未设置的 `app.state.http_client`：

~~~python
from collections.abc import AsyncIterator
from contextlib import asynccontextmanager

from fastapi import FastAPI
import httpx


@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    async with httpx.AsyncClient(
        base_url="https://api.example.com",
        timeout=5.0,
    ) as client:
        app.state.http_client = client
        yield


app = FastAPI(lifespan=lifespan)

@app.get("/upstream/{user_id}")
async def read_upstream(user_id: int) -> dict:
    response = await app.state.http_client.get(f"/users/{user_id}")
    response.raise_for_status()
    return response.json()
~~~

同步 SDK 示例：

~~~python
from fastapi import FastAPI

app = FastAPI()

@app.get("/legacy/{user_id}")
def read_legacy(user_id: int) -> dict:
    return legacy_sync_client.fetch_user(user_id)
~~~

FastAPI 会把普通 `def` 路由和依赖放在线程池中执行，避免它们直接阻塞事件循环。

### 11.2 最容易误解的细节

在 `async def` 路由中直接调用普通辅助函数，FastAPI 不会自动把这个辅助函数移到线程池：

~~~python
@app.get("/wrong")
async def wrong() -> dict:
    return blocking_sync_call()  # 会阻塞事件循环
~~~

可选择：

1. 如果整个路由都依赖同步阻塞栈，把路由写成 `def`。
2. 局部桥接：`result = await asyncio.to_thread(blocking_sync_call)`。
3. 换用真正异步的客户端或驱动。

### 11.3 生命周期与资源

- HTTPX AsyncClient、数据库 Engine / pool 在应用 lifespan 中创建并关闭。
- SQLAlchemy AsyncSession 按请求创建，不能在并发请求之间共享。
- 所有外部 I/O 设置超时；连接池大小应与应用并发和数据库容量匹配。
- 不要每个请求创建全新连接池或 HTTP 客户端。
- 请求取消时让下游调用可取消，并在 `finally` / 上下文管理器中释放资源。

### 11.4 BackgroundTasks 的边界

FastAPI BackgroundTasks 在响应后于应用进程中执行，适合短小、非关键的后处理。它不是持久任务队列：

- 进程重启时任务可能丢失。
- 大量阻塞或 CPU 工作仍会占用应用资源。
- 需要重试、持久化、跨机器扩展和监控时使用 Celery、Dramatiq、RQ 或其他任务系统。

## 12. 技术选择矩阵

| 场景 | 首选 | 为什么 | 主要限制 |
| --- | --- | --- | --- |
| 少量同步流程 | 普通函数 | 最简单、最易调试 | 无并发 |
| 多个阻塞 I/O 调用 | ThreadPoolExecutor | 易接入同步库 | 线程数和资源有限 |
| 长期共享状态线程 | threading + Queue/Lock | 可精细控制 | 竞态、死锁 |
| 大量异步网络 I/O | asyncio | 单线程管理大量等待 | 任何阻塞会拖慢全循环 |
| 纯 Python CPU 密集 | ProcessPoolExecutor | 绕过默认 GIL、利用多核 | 启动与序列化成本 |
| 自定义进程拓扑 | multiprocessing | 原语完整 | 生命周期复杂 |
| NumPy 等释放 GIL 的计算 | 实测线程 / 库自身并行 | 可能避免进程复制 | 取决于扩展和内部线程 |
| FastAPI + 异步驱动 | `async def` | 直接 await | 需全链路非阻塞 |
| FastAPI + 同步 SDK | `def` 或局部 to_thread | 避免阻塞事件循环 | 线程池可能饱和 |
| 长任务、需重试持久化 | 外部任务队列 | 与 Web 生命周期解耦 | 增加基础设施 |
| 3.14+ 隔离解释器并行 | InterpreterPoolExecutor | 单进程多解释器多核 | 非 3.10 基线、共享受限 |

做性能选择前至少测量：

- 吞吐量和 P50/P95/P99 延迟。
- CPU、内存、线程和进程数量。
- 连接池等待、队列深度和拒绝数。
- 单任务大小、序列化开销和上游限流。

## 13. 常见并发陷阱

### 13.1 忘记 await

~~~python
result = async_function()  # 只是协程对象
result = await async_function()  # 才执行并取得结果
~~~

启用测试告警并把 “coroutine was never awaited” 当作缺陷处理。

### 13.2 在事件循环中做阻塞工作

错误组合包括：

- `time.sleep`。
- Requests 同步请求。
- 同步数据库查询。
- 大文件压缩、哈希或纯 Python 大循环。

使用异步库、`to_thread`、进程池或外部 worker。

### 13.3 无界并发

~~~python
# 数据量大时会一次创建海量协程和连接
await asyncio.gather(*(fetch(item) for item in millions_of_items))
~~~

改用有界 Queue、Semaphore、分批处理或滑动窗口。并发上限要与下游容量一致。

### 13.4 以为单线程没有竞态

只要两个状态操作之间有 await，其他任务就可能插入。缓存、配额、连接状态和“先检查后写入”仍需要原子设计或锁。

### 13.5 锁顺序和持锁 await

- 多把锁顺序不一致会死锁。
- 在锁内进行外部 I/O 会放大阻塞。
- 捕获异常却忘记释放锁会永久卡住；使用上下文管理器。
- 不要把线程锁和 asyncio 锁混用。

### 13.6 吞掉取消

~~~python
try:
    await work()
except BaseException:
    pass  # 也吞掉 CancelledError，破坏关机和超时
~~~

只捕获能处理的异常；清理后重新抛出取消。宽泛捕获时也要单独处理 `CancelledError`。

### 13.7 后台任务没有所有者

任务未保存引用、未等待、未记录异常，会出现 “Task exception was never retrieved”。使用 TaskGroup 或集中任务注册表，并在关闭时汇总。

### 13.8 错误理解超时

- 外层超时不一定停止已经在线程或远端执行的操作。
- 只设 HTTP 客户端超时，不代表整个业务请求有总预算。
- 重试会放大最坏耗时；总预算应覆盖连接、读取、重试和退避。
- 超时后还需幂等和补偿，尤其是写请求。

### 13.9 Windows 多进程递归启动

忘记 `if __name__ == "__main__":` 会让子进程重新执行创建进程的模块。函数不可导入或参数不可 pickle 也会失败。

### 13.10 资源跨并发边界误共享

- SQLAlchemy Session / AsyncSession 不跨线程或并发任务共享。
- 普通 Requests Session 的跨线程共享要遵循库文档和自己的同步策略。
- asyncio Queue/Lock 不跨线程使用。
- 子进程不继承并安全复用父进程数据库连接。

### 13.11 并发掩盖容量问题

增加线程和协程只会更快地把压力传给数据库或上游。连接池、限流、背压、缓存、批处理和降级要一起设计。

## 14. 测试、调试与观测

### 14.1 开启 asyncio 调试

本地可使用：

~~~python
import asyncio

asyncio.run(main(), debug=True)
~~~

也可设置 `PYTHONASYNCIODEBUG=1`。调试模式能发现慢回调、未正确等待的协程和部分线程错误，但会增加开销。

### 14.2 测试并发代码

- 测试正常完成、部分失败、超时、取消和关闭路径。
- 用 Event / Barrier 控制交错顺序，少依赖 `sleep` 猜时间。
- 异步 pytest 使用 pytest-asyncio 或 AnyIO，并按插件文档配置。
- 给测试本身设置总超时，避免 CI 永久挂起。
- 多进程函数必须可导入，集成测试在目标操作系统执行。
- 竞态通常不稳定，重复或压力测试只能增加发现概率，不能证明没有竞态。

### 14.3 生产观测

建议记录和监控：

- 请求总预算、上游超时和取消次数。
- 事件循环延迟 / lag。
- 线程池和进程池活跃数、排队时间。
- Queue 深度、生产速率、消费速率和丢弃量。
- 数据库 / HTTP 连接池使用率和等待时间。
- 任务成功、失败、重试和死信数量。

日志带请求 ID / 任务 ID，但不要包含令牌和敏感载荷。并发日志会交错，结构化字段比拼接长字符串更易检索。
