## 1. 测试策略

### 1.1 测试金字塔

```text
              少量端到端测试
           浏览器 / 网关 / 真实依赖
        ─────────────────────────
             适量 API 集成测试
          FastAPI + 数据库 + 鉴权
        ─────────────────────────
               大量单元测试
        Service / 纯函数 / 领域规则
```

各层关注点：

| 类型 | 主要验证 | 特点 |
| --- | --- | --- |
| 单元测试 | 业务分支、边界条件、纯函数 | 快、定位清晰、依赖多为 fake / mock |
| 集成测试 | 路由、Pydantic、依赖、SQL、事务 | 比单元测试慢，但能发现组件连接问题 |
| 端到端测试 | 部署后的真实用户流程 | 最接近生产，也最慢、最容易受环境影响 |

不要只追求覆盖率数字。高价值测试应覆盖：

- 权限与所有者边界。
- 事务提交 / 回滚。
- 唯一约束竞态与冲突响应。
- Token 过期、签名错误和停用用户。
- PATCH 的“未传字段”与“明确传 null”。
- 分页边界和稳定排序。

### 1.2 可测试的代码结构

上一章的分层天然支持测试：

- Router 通过 HTTP 集成测试验证。
- Service 通过 fake repository 或 mock session 单元测试。
- Repository 使用真实测试数据库验证 SQL 行为。
- 外部 HTTP、邮件和消息服务通过接口封装后替换为 fake。

如果一个测试必须 mock 十几个内部函数，通常说明被测代码职责过多或依赖方向混乱。

## 2. pytest 与测试目录

### 2.1 推荐目录

```text
tests/
├── conftest.py
├── factories.py
├── unit/
│   ├── test_auth_service.py
│   └── test_task_service.py
└── integration/
    ├── test_auth_api.py
    ├── test_task_api.py
    └── test_task_repository.py
```

测试文件和函数以 `test_` 开头。Arrange、Act、Assert 三段结构有助于快速阅读：

```python
def test_example() -> None:
    # Arrange：准备输入和依赖
    value = 2

    # Act：执行被测行为
    result = value * 3

    # Assert：验证外部可观察结果
    assert result == 6
```

### 2.2 pytest 配置

上一章 `pyproject.toml` 已包含：

```toml
[tool.pytest.ini_options]
asyncio_mode = "auto"
testpaths = ["tests"]
```

可以继续增加严格标记：

```toml
[tool.pytest.ini_options]
asyncio_mode = "auto"
testpaths = ["tests"]
addopts = "-ra --strict-markers"
markers = [
    "unit: 不访问真实数据库的快速测试",
    "integration: 需要数据库或完整 ASGI 应用的测试",
]
```

常用命令：

```powershell
pytest
pytest -m unit
pytest tests/integration/test_task_api.py -vv
pytest -k 'token_expired'
pytest --maxfail=1
```

测试必须能独立运行，不能依赖执行顺序。

## 3. Fixture 与隔离测试数据库

Fixture 负责测试资源的创建和释放。数据库集成测试至少要做到：

- 测试不会连接开发或生产数据库。
- 每个测试从可预测状态开始。
- 测试结束释放连接、清理依赖覆盖。
- 并行测试不会写入同一份共享数据。

### 3.1 SQLite 快速集成 Fixture

下面示例使用内存 SQLite，适合验证基础 CRUD。它不能替代 PostgreSQL 集成测试，因为 JSON、数组、锁、隔离级别、约束和 SQL 方言可能不同。

`tests/conftest.py`：

```python
from collections.abc import AsyncIterator
from typing import Any

import pytest_asyncio
from httpx import ASGITransport, AsyncClient
from sqlalchemy import event
from sqlalchemy.ext.asyncio import (
    AsyncSession,
    async_sessionmaker,
    create_async_engine,
)
from sqlalchemy.pool import StaticPool

from app import models  # noqa: F401，注册全部 ORM 模型
from app.db.base import Base
from app.db.session import get_db_session
from app.main import app


@pytest_asyncio.fixture
async def db_session() -> AsyncIterator[AsyncSession]:
    test_engine = create_async_engine(
        "sqlite+aiosqlite://",
        poolclass=StaticPool,
        connect_args={"check_same_thread": False},
    )

    @event.listens_for(test_engine.sync_engine, "connect")
    def enable_sqlite_foreign_keys(
        dbapi_connection: Any,
        connection_record: Any,
    ) -> None:
        cursor = dbapi_connection.cursor()
        cursor.execute("PRAGMA foreign_keys=ON")
        cursor.close()

    async with test_engine.begin() as connection:
        await connection.run_sync(Base.metadata.create_all)

    session_factory = async_sessionmaker(
        test_engine,
        expire_on_commit=False,
        autoflush=False,
    )
    async with session_factory() as session:
        yield session

    await test_engine.dispose()


@pytest_asyncio.fixture
async def client(db_session: AsyncSession) -> AsyncIterator[AsyncClient]:
    async def override_db_session() -> AsyncIterator[AsyncSession]:
        yield db_session

    app.dependency_overrides[get_db_session] = override_db_session
    transport = ASGITransport(app=app, raise_app_exceptions=False)
    async with AsyncClient(
        transport=transport,
        base_url="http://testserver",
    ) as test_client:
        yield test_client

    app.dependency_overrides.clear()
```

这个 Fixture 每个测试创建一套新表，简单但不是最高效。测试规模变大后可以：

- 测试会话级建表，每个测试在事务 / SAVEPOINT 中运行并回滚。
- 每个并行 worker 使用独立数据库或独立 schema。
- 使用容器启动与生产相同主版本的 PostgreSQL。
- 在测试库上执行 Alembic，而不是只运行 `create_all()`，验证迁移链本身。

### 3.2 PostgreSQL 才是最终依据

至少在 CI 中增加 PostgreSQL 集成阶段，验证：

- Alembic 能从空库升级到 `head`。
- 模型与迁移结果一致。
- 唯一约束、外键、级联和索引行为符合预期。
- 并发事务和锁行为符合预期。
- 异步驱动和连接池配置真实可用。

测试数据库名称应明确带 `test`，应用启动时还可以加入保护：如果测试环境的数据库 URL 不包含预期标记就拒绝执行清库操作。

## 4. HTTPX ASGITransport 与 TestClient

### 4.1 异步测试：ASGITransport

HTTPX `ASGITransport` 直接在进程内调用 ASGI 应用，不占用真实端口：

```python
import pytest
from httpx import ASGITransport, AsyncClient

from app.main import app


@pytest.mark.asyncio
async def test_liveness() -> None:
    transport = ASGITransport(app=app)
    async with AsyncClient(
        transport=transport,
        base_url="http://testserver",
    ) as client:
        response = await client.get("/health/live")

    assert response.status_code == 200
    assert response.json() == {"status": "ok"}
```

需要注意：HTTPX 的 `ASGITransport` **不会自动触发 ASGI lifespan**。大多数路由集成测试可以有意识地不运行 lifespan，并覆盖数据库等依赖；需要测试启停逻辑时使用 `asgi-lifespan`：

```python
import pytest
from asgi_lifespan import LifespanManager
from httpx import ASGITransport, AsyncClient

from app.main import app


@pytest.mark.asyncio
async def test_application_lifespan() -> None:
    async with LifespanManager(app) as manager:
        transport = ASGITransport(app=manager.app)
        async with AsyncClient(
            transport=transport,
            base_url="http://testserver",
        ) as client:
            response = await client.get("/health/live")

    assert response.status_code == 200
```

此测试会执行真实 lifespan，因此必须在导入应用前注入测试配置，并让应用使用测试 Engine。更容易测试的做法是让 `create_app()` 接收 Settings、Engine 或 lifespan 工厂，而不是把基础设施全部写死在模块全局。

### 4.2 同步测试：TestClient

FastAPI 的 `TestClient` 适合普通同步测试函数：

```python
from fastapi.testclient import TestClient

from app.main import app


def test_liveness_with_testclient() -> None:
    with TestClient(app) as client:
        response = client.get("/health/live")

    assert response.status_code == 200
```

只有把 `TestClient` 当作上下文管理器使用，lifespan 才会按预期进入和退出。该示例同样要求应用已指向隔离测试环境。

选择建议：

| 场景 | 工具 |
| --- | --- |
| 测试函数本身是同步的 | `TestClient` |
| 要在测试中等待异步数据库 / 客户端 | `AsyncClient` + `ASGITransport` |
| 专门验证启动和关闭 | 上述工具 + lifespan 管理 |

`raise_app_exceptions=True` 有利于开发时直接看到服务端异常；设为 `False` 时可以把未处理异常当作 `500` 响应进行断言。

## 5. FastAPI 依赖覆盖

`app.dependency_overrides` 以“原依赖函数”为键、替代函数为值。它适合替换：

- 数据库会话。
- 当前用户。
- 外部支付、邮件和 HTTP 客户端。
- 时间、随机数等非确定性依赖。

### 5.1 绕过 Token，直接注入用户

```python
from datetime import datetime, timezone

import pytest
from httpx import AsyncClient
from sqlalchemy.ext.asyncio import AsyncSession

from app.api.dependencies import get_current_user
from app.main import app
from app.models.user import User


@pytest.mark.asyncio
async def test_create_task_with_overridden_user(
    client: AsyncClient,
    db_session: AsyncSession,
) -> None:
    fake_user = User(
        id=10,
        username="tester",
        email="tester@example.com",
        password_hash="unused-in-this-test",
        is_active=True,
        created_at=datetime.now(timezone.utc),
    )

    # 当前测试仍会向真实测试库写 Task，因此外键指向的用户也必须存在。
    db_session.add(fake_user)
    await db_session.flush()

    async def override_current_user() -> User:
        return fake_user

    app.dependency_overrides[get_current_user] = override_current_user
    try:
        response = await client.post(
            "/api/v1/tasks",
            json={"title": "write tests"},
        )
    finally:
        app.dependency_overrides.pop(get_current_user, None)

    assert response.status_code == 201
    assert response.json()["owner_id"] == 10
```

这个测试验证任务接口，不重复验证 JWT。即使覆盖了“当前用户”依赖，只要任务仍写入数据库，就必须先持久化满足外键约束的用户。另写认证集成测试覆盖真实登录流程。

### 5.2 清理覆盖

依赖覆盖是应用级可变状态，测试结束必须清理，否则后续用例会受到污染。优先在 Fixture 的 `finally` 中清理自己添加的键。测试并行运行时，共享同一个 app 对象的不同测试修改覆盖表可能相互干扰，应按进程隔离或为每个测试创建 app 实例。

## 6. Service 单元测试

单元测试不启动 ASGI 应用，也不访问数据库。下面用 fake repository 和 `AsyncMock` 验证业务行为。

`tests/unit/test_task_service.py`：

```python
from typing import cast
from unittest.mock import AsyncMock

import pytest
from sqlalchemy.ext.asyncio import AsyncSession

from app.core.errors import NotFoundError
from app.models.task import Task
from app.schemas.task import TaskCreate
from app.services.task import TaskService


class FakeTaskRepository:
    def __init__(self) -> None:
        self.saved: list[Task] = []

    async def add(self, task: Task) -> Task:
        task.id = 1
        self.saved.append(task)
        return task

    async def get_owned(self, task_id: int, owner_id: int) -> Task | None:
        return next(
            (
                task
                for task in self.saved
                if task.id == task_id and task.owner_id == owner_id
            ),
            None,
        )

    async def list_owned(
        self,
        owner_id: int,
        *,
        offset: int,
        limit: int,
    ) -> tuple[list[Task], int]:
        owned = [task for task in self.saved if task.owner_id == owner_id]
        return owned[offset : offset + limit], len(owned)

    async def delete(self, task: Task) -> None:
        self.saved.remove(task)


@pytest.mark.asyncio
async def test_create_task_commits_transaction() -> None:
    session_mock = AsyncMock(spec=AsyncSession)
    session = cast(AsyncSession, session_mock)
    fake_repository = FakeTaskRepository()
    service = TaskService(session, repository=fake_repository)

    task = await service.create(
        owner_id=7,
        payload=TaskCreate(title="learn pytest"),
    )

    assert task.id == 1
    assert task.owner_id == 7
    assert fake_repository.saved == [task]
    session_mock.commit.assert_awaited_once()
    session_mock.refresh.assert_awaited_once_with(task)


@pytest.mark.asyncio
async def test_get_hides_foreign_task_as_not_found() -> None:
    session_mock = AsyncMock(spec=AsyncSession)
    session = cast(AsyncSession, session_mock)
    fake_repository = FakeTaskRepository()
    fake_repository.saved.append(Task(id=1, owner_id=99, title="private"))
    service = TaskService(session, repository=fake_repository)

    with pytest.raises(NotFoundError, match="任务不存在"):
        await service.get(task_id=1, owner_id=7)
```

Fake 保存真实状态，适合表达行为；Mock 适合验证某个协作调用是否发生。`spec=AsyncSession` 约束 Mock 的运行时属性，但不会让 `AsyncMock` 成为 `AsyncSession` 的静态子类型，因此保留 `session_mock` 做断言，并用 `cast` 生成传入 Service 的类型化引用。上一章的 `TaskRepositoryPort` 让真实 Repository 和 Fake 通过结构化类型满足同一契约，不需要继承，也不需要用 `type: ignore` 绕过检查。不要断言大量内部调用顺序，否则小规模重构也会导致测试无意义地失败。

### 6.1 纯业务规则优先做成纯函数

例如任务状态转换可以单独建模：

```python
from app.core.errors import BusinessValidationError
from app.models.enums import TaskStatus


def ensure_transition_allowed(current: TaskStatus, target: TaskStatus) -> None:
    if current is TaskStatus.DONE and target is TaskStatus.IN_PROGRESS:
        raise BusinessValidationError("已完成任务不能直接恢复为进行中")
```

纯函数测试快、输入输出清晰，也不会依赖数据库或 Web 框架。

## 7. API 集成测试

```python
import pytest
from httpx import AsyncClient


@pytest.mark.asyncio
async def test_register_login_and_create_task(client: AsyncClient) -> None:
    register_response = await client.post(
        "/api/v1/auth/register",
        json={
            "username": "alice",
            "email": "alice@example.com",
            "password": "Very-Long-Test-Password-123!",

    assert register_response.status_code == 201
    assert "password_hash" not in register_response.json()

    token = token_response.json()["access_token"]

    assert task_response.json()["status"] == "todo"
```

```python
import pytest
from httpx import AsyncClient


@pytest.mark.asyncio
async def test_page_size_has_upper_bound(client: AsyncClient) -> None:
    await client.post(
        "/api/v1/auth/register",
        json={
            "username": "page_tester",
            "email": "page_tester@example.com",
            "password": "Very-Long-Test-Password-123!",

    token_response = await client.post(

    )

    response = await client.get(
        "/api/v1/tasks?page_size=101",
        headers={"Authorization": f"Bearer {token}"},
    )

    assert response.status_code == 422


@pytest.mark.asyncio
async def test_duplicate_username_returns_conflict(client: AsyncClient) -> None:
    payload = {
        "username": "same_name",
        "email": "first@example.com",
        "password": "Very-Long-Test-Password-123!",
    }
    assert (await client.post("/api/v1/auth/register", json=payload)).status_code == 201

    payload["email"] = "second@example.com"
    response = await client.post("/api/v1/auth/register", json=payload)

    assert response.status_code == 409
    assert response.json() == {
        "error": {
            "code": "conflict",
            "message": "用户名已存在",
        }
    }
```

### 7.3 Repository 集成测试

Repository 测试应直接使用 `db_session`，覆盖排序、过滤、外键和约束。对于唯一约束，要断言 `IntegrityError` 并在捕获后 `rollback()`，因为数据库异常会让当前事务进入失败状态。

### 7.4 测试迁移

CI 中至少执行一次：

```powershell
alembic upgrade head
alembic current
```

更严格的迁移测试可以：

1. 从空数据库升级到 head。
2. 插入代表性旧数据。
3. 执行新迁移。
4. 验证数据转换和约束。
5. 根据团队策略验证 downgrade 或前向修复方案。

## 8. 测试设计要点

### 8.1 时间可控

Token 过期、截止时间等逻辑不要在测试中真实 `sleep()`。把“当前时间”封装成依赖或向令牌函数传入可选时钟，在测试中固定时间。

### 8.2 数据工厂

当测试大量创建用户和任务时，用小型 factory 减少噪声，但关键字段仍应在用例中显式可见：

```python
def user_payload(**overrides: str) -> dict[str, str]:
    payload = {
        "username": "user_1",
        "email": "user_1@example.com",
        "password": "Very-Long-Test-Password-123!",
    }
    payload.update(overrides)
    return payload
```

不要让随机数据导致失败无法复现。使用随机测试时记录 seed。

### 8.3 参数化边界

```python
import pytest
from pydantic import ValidationError

from app.schemas.task import TaskCreate


@pytest.mark.parametrize("title", ["", " ", "x" * 101])
def test_invalid_task_title(title: str) -> None:
    with pytest.raises(ValidationError):
        TaskCreate(title=title)
```

该测试同时保护 Schema 的标题规范化规则：去除首尾空格、拒绝纯空白，并继续验证最大长度。仅靠 `min_length=1` 不会自动拒绝只包含空格的标题，因此这类业务约束必须由校验器和测试共同固定下来。

### 8.4 不泄露真实秘密

测试 Token、账号和数据库必须是专用测试值。录制外部 HTTP 响应时清除 Authorization、Cookie 和个人信息。失败日志也不能打印完整请求头或 `.env`。

## 9. Ruff、类型检查与覆盖率

### 9.1 Ruff

Ruff 同时承担高性能 lint 和格式化。配置示例：

```toml
[tool.ruff]
target-version = "py310"
line-length = 100

[tool.ruff.lint]
select = ["E", "F", "I", "B", "UP", "ASYNC", "S"]
ignore = [
    "S101", # pytest 需要 assert
]

[tool.ruff.lint.per-file-ignores]
"tests/**/*.py" = ["S105", "S106"] # 测试凭证是固定假值
```

命令：

```powershell
ruff check .
ruff format --check .
```

本地确认后可以运行 `ruff check . --fix` 和 `ruff format .`。CI 应使用只检查模式，避免 CI 静默修改代码。

### 9.2 类型检查

SQLAlchemy 2.x 的 `Mapped`、`mapped_column()` 和 Pydantic 类型注解已经提供良好的静态分析基础：

```toml
[tool.mypy]
python_version = "3.10"
plugins = ["pydantic.mypy"]
strict = true
warn_unused_ignores = true
exclude = ["alembic/versions/"]
```

运行：

```powershell
mypy app tests
```

不要为了让检查通过大量添加无解释的 `# type: ignore`。如果确实是第三方库缺少类型信息，应缩小忽略范围并标注错误代码。

### 9.3 覆盖率

```powershell
pytest --cov=app --cov-report=term-missing --cov-report=xml
```

覆盖率阈值可以逐步提高：

```toml
[tool.coverage.run]
branch = true
source = ["app"]

[tool.coverage.report]
show_missing = true
fail_under = 85
```

分支覆盖率比单纯行覆盖率更能发现“只测试了 if 的一边”。但 100% 覆盖率也不能证明并发、安全和需求正确。

### 9.4 建议的本地检查顺序

```powershell
ruff format --check .
ruff check .
mypy app tests
pytest
```

仓库的构建动作由维护者执行；文档项目本身无需运行这些命令。

## 10. 日志与可观测性

### 10.1 日志应该回答什么

一次请求出现问题时，日志至少要帮助回答：

- 哪个服务、环境和版本？
- 哪个请求？请求 ID / Trace ID 是什么？
- 哪个路由、方法、状态码？
- 花了多久？错误类型是什么？
- 是否发生数据库超时、外部服务超时或重试？

推荐结构化字段，而不是把所有信息拼成难解析的字符串：

```json
{
  "timestamp": "2026-08-13T10:20:30.123Z",
  "level": "INFO",
  "service": "task-api",
  "environment": "production",
  "request_id": "cd72...",
  "method": "PATCH",
  "path": "/api/v1/tasks/42",
  "status_code": 200,
  "duration_ms": 18.7
}
```

### 10.2 请求 ID

入口代理可生成请求 ID，应用也应在缺失时补充，并把它：

- 写入日志上下文。
- 作为 `X-Request-ID` 响应头返回。
- 传递给下游 HTTP / 消息调用。
- 与 Trace ID 关联。

异步应用中可使用 `contextvars.ContextVar` 保存请求上下文，但要在请求结束清理，避免值泄漏到复用上下文。

### 10.3 禁止记录的内容

- 明文密码和密码哈希。
- 完整 JWT、Session Cookie、API Key。
- 数据库连接串中的用户名和密码。
- 身份证、银行卡等不必要的个人数据。
- 完整文件内容和未经脱敏的请求体。

对 `Authorization`、`Cookie`、`Set-Cookie`、`X-API-Key` 等字段默认脱敏。异常响应只给客户端稳定错误码；内部堆栈写服务端错误日志。

### 10.4 三类可观测信号

| 信号 | 用途 | 示例 |
| --- | --- | --- |
| Logs | 具体事件和错误上下文 | 请求失败、迁移结果 |
| Metrics | 聚合趋势与告警 | RPS、P95、5xx 比例、连接池等待 |
| Traces | 跨服务调用链 | API → PostgreSQL → 消息队列 |

只收集数据没有价值，还要为可行动的 SLO 设置告警，并避免高基数字段导致指标系统成本失控。

## 11. 配置与密钥管理

### 11.1 配置原则

- 环境相关配置通过环境变量或密钥管理服务注入。
- 启动时用 Pydantic Settings 验证类型、范围和必填项。
- 开发 `.env` 不提交；只提交 `.env.example`。
- 测试、预发布和生产使用不同数据库、JWT 密钥和第三方凭证。
- 默认配置应偏安全，例如 `DEBUG=false`。

### 11.2 密钥生命周期

密钥管理不仅是“放到环境变量”：

1. 安全生成足够随机的密钥。
2. 只授予运行服务读取所需密钥的权限。
3. 日志、异常、诊断页面和进程参数不暴露密钥。
4. 定期轮换，并设计新旧密钥短期并存方案。
5. 员工、设备或服务离开作用域时及时撤销。
6. 记录密钥访问审计，但不记录密钥值。

### 11.3 JWT 轮换

对称 HS256 适合单体或少数可信签发 / 验证方。多个服务只需要验证令牌时，可考虑非对称算法：认证服务持有私钥，业务服务只持公钥。令牌头中的 `kid` 可辅助密钥轮换，但服务端必须从可信密钥集合解析，不能根据攻击者提供的任意 URL 拉取密钥。

## 12. Dockerfile 与镜像设计

### 12.1 多阶段 Dockerfile

下面示例安装项目 wheel，并以非 root 用户运行。版本应通过依赖锁文件固定；示例省略具体锁定工具的细节。

```dockerfile
FROM python:3.12-slim AS builder

ENV PIP_DISABLE_PIP_VERSION_CHECK=1 \
    PIP_NO_CACHE_DIR=1

WORKDIR /build
COPY pyproject.toml ./
COPY app ./app
RUN python -m pip install --upgrade pip \
    && python -m pip wheel --wheel-dir /wheels .

FROM python:3.12-slim AS runtime

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PIP_DISABLE_PIP_VERSION_CHECK=1 \
    PIP_NO_CACHE_DIR=1

RUN addgroup --system app \
    && adduser --system --ingroup app --home /app app

WORKDIR /app
COPY --from=builder /wheels /wheels
RUN python -m pip install /wheels/*.whl \
    && rm -rf /wheels

# 同一镜像可供独立迁移 Job 使用。
COPY alembic.ini ./
COPY alembic ./alembic

USER app
EXPOSE 8000

HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
    CMD ["python", "-c", "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health/live', timeout=2)"]

CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--proxy-headers"]
```

说明：

- builder 使用 `pip wheel` 同时生成项目及依赖 wheel，运行阶段无需编译 Python 包。
- 运行镜像不包含源代码时，项目 wheel 必须正确包含 `app` 包。
- 不在镜像里复制 `.env`。
- 生产中通常由编排平台做健康检查，Dockerfile 的 `HEALTHCHECK` 可按平台规范保留或移除。
- `--proxy-headers` 只应在可信代理之后使用，并配置可接受的 forwarded IP 范围。

### 12.2 .dockerignore

```dockerignore
.git
.github
.venv
.env
__pycache__
*.py[cod]
.pytest_cache
.mypy_cache
.ruff_cache
.coverage
htmlcov
tests
```

是否排除 tests 取决于镜像是否要在某个安全阶段执行测试；运行镜像通常不需要测试文件。

### 12.3 镜像安全

- 使用明确的 Python 小版本或镜像 digest，按计划更新安全补丁。
- 扫描系统包和 Python 依赖漏洞。
- 非 root 运行，只提供必要文件权限。
- 运行时根文件系统尽量只读，临时文件写受控目录。
- 设置 CPU、内存和进程资源限制。
- 不在镜像层、构建参数或历史中放密钥。
- 生成 SBOM 并保留镜像来源、签名和发布记录。

本章不实际执行 `docker build`；构建与部署由项目维护者在对应环境完成。

## 13. 生产部署模型

### 13.1 常见链路

```text
Internet
  ↓ HTTPS
CDN / WAF / Load Balancer
  ↓
Ingress / Reverse Proxy
  ↓
FastAPI 实例（Uvicorn worker）× N
  ↓
PostgreSQL / Redis / Message Broker / Object Storage
```

反向代理通常负责 TLS 终止、连接管理、请求体大小限制、部分限流和路由；应用仍负责认证、授权、业务限流和输入校验。

### 13.2 Worker 数量

可以用 Uvicorn / FastAPI CLI 启动多个 worker：

```powershell
uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 4
```

但 worker 数量没有固定公式：

- 每个 worker 是独立进程，有独立内存、事件循环和连接池。
- worker 增多会增加数据库最大连接数需求。
- I/O 密集服务通常先通过压测找延迟、吞吐和资源拐点。
- CPU 密集任务不应长期阻塞 API worker，应拆到专用进程或服务。
- 容器编排环境常采用“每容器一个进程，再横向扩容多个容器”，便于资源和故障隔离。

数据库连接预算示例：

```text
总潜在连接数 ≈ 实例数 × 每实例 worker 数 × 每 worker 连接池上限
```

还要为迁移、管理工具和故障切换预留连接。不要只调大连接池掩盖慢查询。

### 13.3 状态必须外置

多 worker / 多实例部署时，以下内容不能只放进程内存：

- 用户 Session / Token 撤销状态。
- WebSocket 跨实例广播。
- 限流计数。
- 可靠后台任务。
- 上传文件。

应按需求使用数据库、Redis、消息系统和对象存储。进程内缓存只能作为可丢失、可重建的优化。

### 13.4 超时与重试

每一层都要有明确超时：客户端、代理、应用外部 HTTP、数据库语句和任务执行。重试只适合幂等操作，并使用指数退避、抖动和总时间预算；错误的自动重试会把局部故障放大成重试风暴。

## 14. 数据库迁移与滚动发布

### 14.1 迁移是独立发布步骤

推荐发布流程：

```text
构建并扫描唯一镜像
        ↓
在临时数据库验证迁移
        ↓
备份 / 确认恢复方案
        ↓
独立 migration Job：alembic upgrade head
        ↓
滚动发布应用实例
        ↓
健康检查、指标与错误率观察
```

不要让每个 API worker 在 lifespan 中运行迁移。否则多进程并发、权限边界和失败恢复都难以控制。

### 14.2 Expand / Contract

滚动发布期间新旧版本会短暂共存，数据库变更必须兼容：

1. **Expand**：先增加可空字段、新表或兼容索引，新旧代码都能运行。
2. **Migrate**：后台回填数据，监控进度和锁等待。
3. **Switch**：部署新代码，开始双写或读取新字段。
4. **Contract**：确认旧版本完全下线后，再删除旧字段和兼容逻辑。

直接重命名 / 删除字段往往会让滚动中的旧实例立即报错。大表加非空字段、建立索引和类型转换要评估锁表时间，并使用数据库支持的在线策略。

### 14.3 回滚不是只执行 downgrade

某些数据迁移不可逆，数据库 `downgrade()` 也可能丢数据。发布前应明确：

- 应用镜像如何回滚。
- Schema 是否向后兼容旧应用。
- 数据如何备份和恢复。
- 迁移执行到一半如何继续或前向修复。
- 谁拥有生产迁移权限和审计记录。

## 15. 健康检查与优雅关闭

### 15.1 三种探针

| 探针 | 回答的问题 | 失败后的典型动作 |
| --- | --- | --- |
| Startup | 应用是否完成慢启动 | 继续等待或判定启动失败 |
| Liveness | 进程是否卡死 | 重启实例 |
| Readiness | 是否能接收新流量 | 暂时从负载均衡移除 |

Liveness 不应依赖数据库：数据库短暂故障时重启所有 API 实例会放大故障。Readiness 可以检查关键依赖，但必须设置短超时和合理降级策略。

### 15.2 优雅关闭

部署平台发送终止信号后：

1. 实例先被标记为不就绪，不再接收新流量。
2. Uvicorn 等待正在处理的请求完成，受优雅关闭超时限制。
3. FastAPI lifespan 执行 `yield` 后的清理逻辑。
4. 关闭数据库连接池、HTTP 客户端和消费者。
5. 超时后平台才强制终止。

后台任务若必须可靠完成，不能依赖 API 进程优雅关闭，应交给持久化队列。

## 16. CORS、代理与网络边界

### 16.1 生产 CORS

```python
app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://app.example.com"],
    allow_credentials=True,
    allow_methods=["GET", "POST", "PATCH", "DELETE"],
    allow_headers=["Authorization", "Content-Type", "X-Request-ID"],
)
```

- 精确列出 origin，注意协议、域名和端口都是 origin 的组成部分。
- 不把 `*` 与凭证请求混用。
- CORS 只约束浏览器，不阻止 curl 或恶意服务端客户端。
- 非浏览器客户端的安全依赖认证、授权、网络策略和限流。

### 16.2 Forwarded Headers

TLS 在代理终止后，应用收到的连接可能是 HTTP。如果不正确处理可信代理头，重定向 URL、客户端 IP 和安全 Cookie 判断会出错。

只信任已知代理写入的 `Forwarded` / `X-Forwarded-*`。如果应用直接暴露到公网却无条件信任这些头，攻击者可以伪造客户端 IP 和协议。

### 16.3 代理参数

需要协同设置：

- 最大请求体，尤其是文件上传。
- Header 大小与数量。
- 连接、读取、写入和空闲超时。
- WebSocket Upgrade 与空闲连接策略。
- 流式响应缓冲。
- 每 IP / 用户 / Token 的限流。

代理的超时应与应用下游超时和客户端超时形成合理预算，避免客户端已经断开但后端仍长时间占用资源。

## 17. 安全检查清单

### 17.1 认证与授权

- [ ] 所有敏感接口显式要求认证。
- [ ] 每次访问资源都校验所有者、角色或策略，不只依赖前端隐藏按钮。
- [ ] `401` 与 `403` 语义正确，并按协议返回 `WWW-Authenticate`。
- [ ] JWT 固定允许算法，校验签名、`exp`、`sub` 和令牌类型。
- [ ] Access Token 短期有效，Refresh Token 可轮换、可撤销。
- [ ] 登录、注册、找回密码有速率限制与审计。

### 17.2 密码与密钥

- [ ] 密码使用 pwdlib 推荐算法，不手写密码学实现。
- [ ] 日志、响应和数据库中没有明文密码。
- [ ] 密钥来自受控环境变量或密钥管理服务。
- [ ] 密钥可以轮换，泄露后有撤销和响应流程。
- [ ] 不在 Git 历史、镜像层、CI 输出中出现真实密钥。

### 17.3 输入与输出

- [ ] 所有输入限制类型、长度、范围和集合大小。
- [ ] 上传限制体积、扩展名 / 签名、存储路径和访问权限。
- [ ] SQL 使用 ORM / 参数化查询，不拼接用户输入。
- [ ] 响应使用显式 Schema，敏感字段默认不输出。
- [ ] 错误响应不暴露堆栈、SQL、文件路径和连接串。
- [ ] 防止 SSRF：外部 URL 有协议、域名、IP 范围和重定向限制。

### 17.4 Web 与基础设施

- [ ] 全链路 HTTPS，安全 Cookie 设置 `Secure`、`HttpOnly`、合适的 `SameSite`。
- [ ] CORS 只允许可信来源。
- [ ] 设置 Host 校验和必要安全响应头。
- [ ] 依赖和基础镜像持续扫描、及时升级。
- [ ] 容器非 root，权限和网络访问遵循最小化原则。
- [ ] 数据库账号只有应用所需权限，迁移账号可单独管理。
- [ ] 备份经过恢复演练，而不只是“备份任务显示成功”。

安全是持续过程，清单不能替代威胁建模、代码审查、渗透测试和事件响应演练。

## 18. CI 示例

下面是 GitHub Actions 示例。它启动 PostgreSQL、执行迁移和质量检查；具体版本应由项目维护者固定并定期升级。

前文的教学版 `db_session` fixture 固定使用内存 SQLite，因此下面直接运行 `pytest` 时，API / Repository 测试仍不会自动切换到 PostgreSQL；PostgreSQL 服务只验证了 Alembic 迁移。生产项目应另建 `postgres_db_session` fixture，从专用 `TEST_DATABASE_URL` 连接该服务，并用 `@pytest.mark.postgres` 标记方言、约束、事务和并发测试。不要让集成 fixture 直接读取通用 `DATABASE_URL` 后执行清库。

`.github/workflows/ci.yml`：

```yaml
name: ci

on:
  pull_request:
  push:
    branches: [master]

permissions:
  contents: read

jobs:
  quality-and-test:
    runs-on: ubuntu-latest
    timeout-minutes: 15

    services:
      postgres:
        image: postgres:17
        env:
          POSTGRES_DB: task_test
          POSTGRES_USER: task_test
          POSTGRES_PASSWORD: test-only-password
        ports:
          - 5432:5432
        options: >-
          --health-cmd "pg_isready -U task_test -d task_test"
          --health-interval 5s
          --health-timeout 5s
          --health-retries 10

    env:
      ENVIRONMENT: test
      DEBUG: "false"
      DATABASE_URL: postgresql+asyncpg://task_test:test-only-password@127.0.0.1:5432/task_test
      TEST_DATABASE_URL: postgresql+asyncpg://task_test:test-only-password@127.0.0.1:5432/task_test
      JWT_SECRET: ci-test-secret-that-is-longer-than-thirty-two-characters
      JWT_ALGORITHM: HS256
      ACCESS_TOKEN_EXPIRE_MINUTES: "5"
      CORS_ORIGINS: "[]"

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip

      - name: Install dependencies
        run: |
          python -m pip install --upgrade pip
          python -m pip install -e ".[dev]"

      - name: Check formatting
        run: ruff format --check .

      - name: Lint
        run: ruff check .

      - name: Type check
        run: mypy app tests

      - name: Apply migrations
        run: alembic upgrade head

      - name: Test
        run: pytest --cov=app --cov-report=term-missing --cov-report=xml
```

进一步可增加：

- 实现 `postgres_db_session` 后增加 `pytest -m postgres`，真正验证 PostgreSQL 行为；没有对应测试时不要添加会因“未收集用例”而失败的空步骤。
- 依赖锁文件一致性检查。
- 安全 / 许可证扫描、secret scanning。
- 构建一次镜像并扫描，后续环境复用同一 digest。
- Alembic 多版本升级测试。
- OpenAPI 破坏性变更检查。
- 上传测试报告和覆盖率，但避免包含密钥。

第三方 Action 应固定到可信版本，安全要求高时固定完整 commit SHA。

## 19. 常见故障排查

### 19.1 返回 422

排查顺序：

1. 查看响应 `detail` 中的 `loc`、`type` 和 `msg`。
2. 确认 JSON、表单、查询参数是否放在正确位置。
3. OAuth2 登录必须是 `application/x-www-form-urlencoded`，不是 JSON。
4. 检查字段是否必填、是否允许 null、枚举值是否正确。
5. 对照 `/openapi.json` 或 `/docs` 的实际契约。

### 19.2 总是 401

- Header 是否为 `Authorization: Bearer <token>`。
- Token 是否过期，服务器时间是否同步。
- 签发和验证是否使用同一密钥、算法和环境。
- `sub` 是否能转换为有效用户 ID。
- 用户是否已被停用或删除。
- 代理是否错误移除了 Authorization Header。

不要把完整 Token 粘贴到工单或公共日志。

### 19.3 浏览器报 CORS，但 curl 正常

- 请求 origin 是否与允许列表完全一致。
- 预检 `OPTIONS` 是否到达应用，代理是否拦截。
- 请求方法和自定义 Header 是否允许。
- 凭证请求是否错误使用 `*`。
- 实际问题是否是后端 `500`，只是浏览器因缺少 CORS Header 将其显示为 CORS。

### 19.4 MissingGreenlet

通常是异步 SQLAlchemy 在不允许等待的位置触发隐式 I/O：

- 响应序列化访问了未预加载的 relationship。
- commit 后属性过期又被读取。
- 使用了不兼容的同步 lazy load。

处理方式：查询时使用 `selectinload()` 等显式预加载、保持 `expire_on_commit=False`、在会话有效范围内转换 DTO，并避免隐式 I/O。

### 19.5 数据库连接池耗尽

- 查看慢查询、锁等待和事务是否长时间不结束。
- 确保每个请求结束关闭会话。
- 外部 HTTP 调用不要包在不必要的数据库事务中。
- 计算实例 × worker × pool 总连接预算。
- 给获取连接和 SQL 设置超时。
- 优化查询与索引，再谨慎调整池大小。

### 19.6 Alembic 提示 target database is not up to date

- 执行 `alembic current`、`alembic heads`、`alembic history`。
- 确认连接的是预期数据库，不要误操作生产。
- 检查是否出现多个迁移 head，需要明确 merge revision。
- 不要为“消除报错”随意 `stamp head`；stamp 只改版本记录，不执行 DDL。

### 19.7 启动时数据库连接失败

- `DATABASE_URL` 驱动是否为 `postgresql+asyncpg://`。
- DNS、端口、网络策略和 TLS 参数是否正确。
- 凭证是否被 URL 特殊字符破坏，是否正确编码。
- 数据库最大连接数是否已满。
- lifespan 的连接检测是否有合理超时与重试策略。

### 19.8 代理后生成 http 链接或客户端 IP 错误

- TLS 是否在代理终止。
- 代理是否正确设置 `X-Forwarded-Proto` / `Forwarded`。
- Uvicorn 是否只信任实际代理地址。
- 是否有多层代理覆盖或重复追加 Header。

### 19.9 502 / 504

- 502：上游进程未监听、崩溃、端口 / 协议错误或连接被拒绝。
- 504：请求超过代理等待时间，继续检查应用日志、慢 SQL 和下游超时。
- 对照同一个请求 ID 串联代理和应用日志。
- 检查应用是否在部署期间尚未 ready 就接收流量。

### 19.10 多 worker 下 WebSocket 消息不全

进程内连接列表只包含当前 worker 的连接。使用 Redis Pub/Sub、NATS 等跨实例通道广播，并确认代理支持 WebSocket、空闲超时和心跳。

## 20. 上线检查清单

### 代码与测试

- [ ] Ruff 格式、lint、类型检查和测试全部通过。
- [ ] 关键权限、认证、事务、迁移有自动化测试。
- [ ] OpenAPI 变更已审查，破坏性变更有版本策略。
- [ ] 没有遗留调试端点、默认账号和测试后门。

### 配置与安全

- [ ] `DEBUG=false`，真实密钥由受控渠道注入。
- [ ] CORS、Host、代理信任范围和上传限制已配置。
- [ ] TLS、认证、授权、限流和敏感日志脱敏已验证。
- [ ] 依赖、镜像和 secret scanning 无未处理高危问题。

### 数据库

- [ ] Alembic 迁移已人工审查并在相同主版本数据库演练。
- [ ] 大表 DDL 的锁和耗时已评估。
- [ ] 迁移是独立 Job，不由每个 worker 自动执行。
- [ ] 备份已验证可恢复，回滚 / 前向修复方案明确。

### 运行与观测

- [ ] Startup、liveness、readiness 探针职责正确。
- [ ] Worker / 实例数与数据库连接预算匹配。
- [ ] 日志包含版本、请求 ID，指标和 Trace 可关联。
- [ ] 延迟、错误率、饱和度和关键业务指标有告警。
- [ ] 优雅关闭时间大于正常请求完成所需时间。
- [ ] 值班、故障升级、回滚和安全事件流程明确。
