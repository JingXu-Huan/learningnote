## 29.1 隧道是在什么外面再套一层

隧道技术可以把原来的分组作为负载，再添加外层封装。

简化关系：

```text
原始内层 IP 分组
→ 外层首部 + 内层 IP 分组
→ 底层链路发送
```

底层路由器通常根据外层目的地址送到隧道出口；出口去掉相应封装后，再处理内层分组。

“外层 IP 的目的地址”和“内层 IP 的目的地址”可以不同，因为前者定位隧道端点，后者定位原始目标。

## 29.2 为什么封装影响 MTU

假设一个简化隧道的新增封装开销固定为 40 字节，底层路径 MTU=1500：

```text
可完整容纳的内层 IP 分组上限
= 1500 - 40
= 1460 字节
```

如果内层仍发一个 1500 字节分组，加上封装后为 1540，超过底层路径 MTU。

实际隧道开销因协议、选项、加密填充等而异；40 只是本例给定值，不是 VPN 的统一常数。

## 29.3 分片和 TCP 分段的区别

| 机制 | 发生层次 | 拆分的对象 | 接收侧处理 |
|---|---|---|---|
| TCP 分段 | 传输层 | 字节流中的数据 | TCP 恢复有序字节流 |
| IP 分片 | 网络层 | 一个 IP 数据报 | 重组原 IP 数据报后交给上层 |

如果 TCP 一开始就发送适合路径大小的段，就可能避免对相应 IP 数据报进行分片。

一个丢失的 IP 分片可能使整个原 IP 数据报重组失败；TCP 分段则以 TCP 自己的确认和重传机制恢复数据。

## 29.4 为什么小包能通、大包卡住

在某个具体故障中可能发生：

1. 小的连接建立或探测分组能通过路径。
2. 较大的数据分组超过瓶颈 MTU。
3. 分组不能按相应规则分片，被丢弃。
4. 必要的 ICMP／ICMPv6 反馈被阻断。
5. 发送方没能及时调整大小，反复尝试仍然失败。

这说明“连接建立成功”或“默认大小 ping 成功”不能排除 MTU 问题。[13]

但大包失败也可能来自其他原因，应通过包大小变化、相关反馈和抓包等证据判断，不能只凭现象断言。

## 29.5 MSS 调整解决什么

在特定 TCP 转发场景中，设备可以调整连接建立时通告的 MSS，让端点避免发送过大的 TCP 数据段。

在本例给定的内层 MTU=1460、内层 IPv4 首部 20、TCP 首部 20、没有选项的条件下：

```text
对应的 TCP 数据大小上限 = 1460 - 20 - 20 = 1420 字节
```

需要注意：

- MSS 是 TCP 的概念，不直接约束普通 UDP 数据报。
- 调整 MSS 不改变物理链路 MTU。
- MSS 调整不能修复全部隧道、路由或访问控制问题。
- 实际发送大小还应考虑选项、路径变化和封装开销。

## 29.6 回顾三个大小

```text
应用消息大小：一次应用数据可能多大
TCP MSS：单个 TCP 段中的 TCP 数据可多大
IP／路径 MTU：网络分组在相应链路／路径上可多大
```

应用写入较大的数据，不意味着网络一定发送同样大的单个 IP 分组。
