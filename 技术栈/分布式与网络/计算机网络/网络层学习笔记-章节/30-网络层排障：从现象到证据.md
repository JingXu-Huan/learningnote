> 本章给出排查顺序与判断依据，不依赖某个操作系统的固定命令。网络层故障与链路层、传输层、应用层现象之间有联系，应逐层定位。

## 30.1 先把“不能上网”描述具体

至少区分：

- 所有目标都失败，还是某一个目标失败？
- IP 访问失败，还是域名访问失败？
- 同网段失败，还是只有跨网段失败？
- ICMP 失败，还是某个 TCP／UDP 服务失败？
- 小数据失败，还是仅较大的传输失败？
- 单向正常，还是往返都正常？

范围描述越准确，后续检查越有针对性。

## 30.2 一个实用的检查顺序

| 步骤 | 检查内容 | 要回答的问题 |
|---|---|---|
| 1 | 接口、链路、VLAN | 设备是否接入了预期网络？ |
| 2 | IP、掩码、重复地址 | 本地地址配置是否合理？ |
| 3 | 实际路由查找 | 这个目标会从哪个接口、经谁发送？ |
| 4 | ARP／NDP | 当前链路上的下一跳是否可解析和交付？ |
| 5 | 逐跳路由、回程、策略 | 中途与回程是否能到达？ |
| 6 | NAT、MTU 等状态 | 转换和大小条件是否满足？ |
| 7 | DNS、端口、TLS、应用 | 网络以外还有哪一步失败？ |

这个顺序不是必须机械执行的流程。如果错误信息已经明确指向某一步，可以先验证该处。

## 30.3 情形一：同网段主机也访问不了

可能原因：

- 两台主机实际上在不同 VLAN。
- IP 或掩码错误。
- 地址冲突。
- ARP／邻居解析失败。
- 主机防火墙过滤探测或服务。
- 链路故障、隔离策略或无线客户端隔离。

先查看预期路由和邻居信息。邻居解析失败说明需要调查本地交付，不能直接归因于远端运营商。

ARP 成功也不保证应用端口开放；它只能为相应链路地址解析提供证据。

## 30.4 情形二：同网段正常，跨网段失败

优先检查：

- 有没有匹配路由，包括默认路由。
- 选择的网关是否正确。
- 网关是否能被本地链路交付。
- 网关是否允许转发并具有后续路由。
- 远端有没有回到本地源网段的路由。
- 防火墙与 NAT 是否符合通信需求。

仅能 ping 通网关，不代表网关外侧路由和远端回程一定正常。

## 30.5 情形三：按 IP 正常，按域名失败

若已用适当方法验证同一目标 IP 和相同服务可达，应进一步调查名称解析、记录选择和应用使用的地址。

还要考虑域名可能返回多个地址、IPv4／IPv6 路径差异，以及应用对域名、证书和虚拟主机的依赖。

直接把 HTTPS URL 的域名换成 IP，可能因证书或服务配置失败，因此不能把这种失败一律当成网络层不可达。

## 30.6 情形四：traceroute 中间有星号，最终目标能到

如果后续跳或目标有正常响应，中间设备可能只是不回应相应探测，或限制了控制报文。

**它没有回应探测，不等于它没有转发业务分组。**

要结合终点结果与业务流量判断，不能看到第一个 `*` 就把故障定位在那里。

## 30.7 情形五：A 能发到 B，但 B 回复不到 A

调查：

- B 的路由表和默认网关。
- 中间设备到 A 源网段的回程路由。
- 回复是否经过有状态设备的另一条路径。
- NAT 是否保留了必要映射。
- 源地址检查或访问策略是否丢弃流量。

“请求到了”只是去程证据，不是往返通信完成的证据。

## 30.8 抓包时应该寻找什么

不需要先研究底层代码，也可以围绕具体问题观察：

| 怀疑的问题 | 可以寻找的证据 |
|---|---|
| ARP 失败 | 是否反复请求下一跳 IP，却没有相应回复 |
| 下一跳选错 | 实际发出接口、帧目的 MAC 与预期是否一致 |
| 路由环路 | 相关 ICMP 超时、重复路径、递减 TTL 等 |
| MTU 问题 | 大包丢弃、分片信息、需要分片／Packet Too Big 反馈 |
| NAT 问题 | 转换前后地址／端口及回包映射是否匹配 |
| 上层服务问题 | TCP 建连、复位、握手和应用响应处于哪一步 |

抓包位置也影响能看到什么：客户端、NAT 内侧和外侧看到的地址可能不同。

主机上的抓包还可能受网卡卸载影响，看到尚未完成校验和计算或分段的数据。不能仅凭本机抓包的一条“校验和异常”就断言线路上的分组损坏。

## 30.9 如何写一段有依据的排障结论

可以按下面的格式组织：

```text
现象：同网段可达，远端服务访问失败。
已确认：本机地址正常；路由选择到预期网关；下一跳 ARP 成功。
新证据：远端收到请求，但回复缺少到源网段的匹配路由。
判断：问题位于回程路由。
验证：补齐正确回程路由后，往返探测和目标服务恢复。
```

不要把“重启后好了”当成已经证明了某个具体根因。
