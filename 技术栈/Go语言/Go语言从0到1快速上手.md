# 1. 先看终点：14 天后应该会什么

不是把所有 Go 语法背完，而是交付一个有完整后端链路的小服务：

~~~text
HTTP 请求
   ↓
Handler / Middleware
   ↓  传递 r.Context()
Service（业务规则）
   ↓
Repository（参数化 SQL）
   ↓
MySQL

并发通知：Context → 有界 worker pool → 外部通知接口
~~~

完成后，应具备下面这些可验证的能力：

| 能力 | 最低交付标准 |
| --- | --- |
| 环境与依赖 | 能创建 Go Module，解释 go.mod、go.sum、go mod tidy 的作用 |
| 语言基础 | 能使用 struct、slice、map、接口、错误、多返回值与 defer 写一个业务模块 |
| Web | 能用 net/http 写出 JSON REST API；知道 Gin 只是路由与中间件工具，不是业务层 |
| 数据库 | 能用 database/sql 连接 MySQL、执行参数化 SQL、传递 Context、管理事务 |
| 并发 | 能区分 goroutine、channel、Mutex、WaitGroup 的职责，并能避免 goroutine 泄漏 |
| 质量 | 能写表驱动单测，执行 gofmt、go test、go vet、race detector |
| 项目表达 | 能向面试官说明：请求如何经过 Handler、业务层、SQL、超时和异步通知 |

每天按 “20 分钟读官方资料 + 80 分钟手写代码 + 20 分钟复盘” 执行。代码时间至少占 70%；看到一个概念，就在自己的项目里用一次。

一开始不要同时学习 Gin、GORM、JWT、Redis、Docker、Kafka、gRPC。先把一条 “请求 → 业务 → SQL → 响应” 的链路用标准库跑通，再逐项引入工具。

已有的跨技术栈笔记可作为补充阅读：[Java / Spring Boot + Vue → NestJS + Go 快速迁移指南](../NestJS/迁移.md)。本文更侧重可直接执行的 Go 路线，不重复堆砌概念。

# 2. Java / Spring 到 Go 的心智模型转换

## 2.1 先保留你已有的能力

下面这些后端能力不会因为换语言而失效：

~~~text
HTTP 状态码、REST 设计、DTO 与参数校验
MySQL 表设计、索引、慢查询、事务、分页
Redis 缓存策略、消息可靠性、鉴权与安全边界
日志、监控、压测、排障、接口测试
业务拆分、领域建模、代码评审
~~~

真正要重新适应的是语言和运行模型。

| Java / Spring | Go 中的常见做法 | 迁移时要改的思路 |
| --- | --- | --- |
| JVM + JAR | 编译为单个原生可执行文件 | 部署通常更直接；仍要关注配置、日志和系统依赖 |
| Maven 的 pom.xml | Go Modules 的 go.mod / go.sum | 一个模块是一组一起版本化、一起发布的包 |
| class、继承 | struct、方法、组合 | Go 没有类继承，优先组合 |
| implements 接口 | 隐式实现 interface | 不需要写 implements；方法集匹配即可 |
| try/catch、throws | 返回值中的 error | 错误是正常控制流的一部分，必须显式处理 |
| Spring DI 容器 | 构造函数注入，在 main 中组装 | 依赖关系更显式、更容易测试 |
| Bean / 注解 / AOP | 显式代码、接口、函数、中间件 | 少一些“魔法”，多一些直接可见的代码 |
| Thread / 线程池 | goroutine + WaitGroup / channel / Mutex | 启动很轻，但生命周期和共享状态仍要治理 |
| CompletableFuture | goroutine + channel + Context | 重点不只在并发，还在取消、超时和收尾 |
| MyBatis / JPA | database/sql + SQL；按需选 sqlx、sqlc、ORM | 先掌握标准库与 SQL，再决定抽象层 |
| Spring MVC | net/http；需要时再用 Gin | Handler 就是一次 HTTP 请求的入口 |

## 2.2 最重要的四个变化

### 变化 1：错误不再“抛出去等别人接”

Go 用多返回值返回结果和错误：

~~~go
alert, err := service.GetByID(ctx, id)
if err != nil {
    writeError(w, err)
    return
}
~~~

这不是繁琐的样板代码。它要求调用者在错误发生的位置决定：记录、包装、转换为 HTTP 状态码、重试，还是直接返回。

### 变化 2：接口由使用方定义，类型隐式实现

~~~go
type AlertRepository interface {
    FindByID(ctx context.Context, id int64) (Alert, error)
}

type MySQLAlertRepository struct {
    db *sql.DB
}

func (r *MySQLAlertRepository) FindByID(ctx context.Context, id int64) (Alert, error) {
    // 方法签名满足 AlertRepository，因此它自动实现该接口。
    return Alert{}, nil
}
~~~

接口通常应当小，并靠近使用它的业务代码。不要像 Java 一样，为每一个 struct 先造一个同名 Interface。

### 变化 3：依赖在 main 中明确组装

~~~go
repo := alert.NewMySQLRepository(db)
service := alert.NewService(repo, notifier)
handler := alert.NewHandler(service)
~~~

这相当于把 Spring 容器自动做的装配写清楚。初期不需要追求复杂 DI 框架；构造函数注入已经足够清晰、容易写测试。

### 变化 4：并发不是“开一个 goroutine 就结束”

~~~go
go sendNotification(ctx, alert)
~~~

这行只表示启动了一个并发任务。它并不会自动处理超时、取消、错误、数量上限或任务回收。真实服务里，要用 Context、有界并发、WaitGroup、channel 或同步原语给任务定义生命周期。

# 3. 第 0 天：Windows 环境、Go Modules 与第一个程序

## 3.1 安装原则

截至 2026-08-24，Go 官方下载页展示的最新稳定版是 Go 1.27.0；以后新建项目时不要死记这个数字，直接从 [Go 官方下载页](https://go.dev/dl/) 选择页面标记为 Stable 的版本，并结合 [Release Notes](https://go.dev/doc/devel/release) 判断升级影响。

Windows 11 常见流程：

1. 在官方下载页下载 Windows x64 的 MSI 安装包。
2. 按安装向导完成安装；默认目录通常是 <code>C:\Program Files\Go</code>，可按磁盘规划调整。
3. 关闭并重新打开 PowerShell。
4. 运行下面命令确认安装。

~~~powershell
go version
go env GOROOT GOPATH GOMODCACHE GOCACHE
go env GOOS GOARCH
~~~

预期第一行能看到 Go 版本。若找不到 <code>go</code> 命令，先重开终端；仍失败再检查安装程序是否把 Go 的 bin 目录加入 PATH。官方 Windows 安装流程见 [Download and install](https://go.dev/doc/install)。

如果使用 GoLand：

~~~text
Ctrl + Alt + S
→ Go
→ GOROOT
→ Add SDK
→ Download（由 GoLand 下载）或 Local（选择已安装 SDK）
~~~

Local 目录应包含 <code>bin</code> 与 <code>src</code>。不要把 GOROOT 当作项目目录。

## 3.2 现代 Go 项目只关心 Go Modules

过去的教程常要求把代码放进 <code>GOPATH/src</code>。这是旧的 GOPATH 工作模式；现代项目以模块根目录中的 <code>go.mod</code> 为中心，项目可以放在任意工作目录。

| 名称 | 初学者要知道什么 |
| --- | --- |
| GOROOT | Go SDK 的安装目录，由安装器或 IDE 管理，不要改成项目目录 |
| GOPATH | 主要存放工具二进制和模块缓存，不需要把业务项目放进去 |
| go.mod | 模块名、Go 版本和直接依赖的声明文件，应提交到 Git |
| go.sum | 依赖内容校验记录，应提交到 Git |
| GOMODCACHE | 模块下载缓存；遇到依赖问题可以先查看，但不要把它当源码仓库修改 |

Go Modules 的官方定义和命令细节见 [Go Modules Reference](https://go.dev/ref/mod)。

## 3.3 创建第一个模块

在你平时保存代码的目录中执行：

~~~powershell
New-Item -ItemType Directory -Name 'go-zero-to-one'
Set-Location .\go-zero-to-one
go mod init github.com/<你的 GitHub 用户名>/go-zero-to-one
~~~

如果只是本地练习，也可以暂用 <code>example.com/go-zero-to-one</code>。真正发布到 GitHub 时，模块名应与可访问的仓库路径一致。

新建 <code>main.go</code>：

~~~go
package main

import "fmt"

func main() {
    fmt.Println("Hello, Go!")
}
~~~

执行完整的最小质量闭环：

~~~powershell
go fmt ./...
go run .
go test ./...
go vet ./...
go build ./...
~~~

| 命令 | 作用 |
| --- | --- |
| go run . | 编译并立即运行当前模块主包，适合本地开发 |
| go build ./... | 编译当前模块及所有子包，生成可执行文件或做编译校验 |
| go test ./... | 运行当前模块所有包的测试 |
| go fmt ./... | 按 Go 统一格式化代码；提交前必做 |
| go vet ./... | 检查一批常见、可疑的代码用法 |
| go mod tidy | 删除不再需要的依赖、补齐直接需要的依赖记录 |

从第一天起形成固定顺序：

~~~powershell
go fmt ./...
go test ./...
go vet ./...
go mod tidy
go build ./...
~~~

官方入门实践按 [Getting started](https://go.dev/doc/tutorial/getting-started) 进行即可。

# 4. 第一周前半：只学项目真正会用到的语法

不要按语言手册从头背到尾。先掌握下面这些内容，足以支撑一个 CRUD API。

## 4.1 语法速查：和 Java 最不同的地方

| 主题 | Go 写法 | 要点 |
| --- | --- | --- |
| 声明并推导类型 | <code>name := "JingXu"</code> | 只能在函数内部使用；至少要有一个新变量 |
| 显式声明 | <code>var count int</code> | 得到零值 0 |
| 常量 | <code>const timeout = 3 * time.Second</code> | 常用于业务常量、状态码、时间配置 |
| 条件 | <code>if err != nil { ... }</code> | 条件不写括号；花括号不可省略 |
| 循环 | <code>for i := 0; i < n; i++ {}</code> | Go 只有 for，没有 while |
| 分支 | <code>switch status { ... }</code> | 默认不自动 fallthrough |
| 延迟执行 | <code>defer file.Close()</code> | 当前函数返回前执行，后进先出 |
| 多返回值 | <code>value, err := fn()</code> | 把结果和错误一起返回 |

零值是 Go 的重要设计：<code>int</code> 是 0，<code>bool</code> 是 false，指针、slice、map、interface 等引用类值的零值通常是 nil。写代码前先问：这个字段的零值有没有业务含义？

## 4.2 struct、方法与指针接收者

Go 的 <code>struct</code> 可看作 Java 的普通数据对象，但没有构造器、getter/setter、继承这些强制形式。

~~~go
type Alert struct {
    ID        int64     `json:"id"`
    DeviceID  string    `json:"deviceId"`
    Status    string    `json:"status"`
    CreatedAt time.Time `json:"createdAt"`
}

func (a *Alert) Resolve() error {
    if a.Status == "resolved" {
        return errors.New("alert already resolved")
    }
    a.Status = "resolved"
    return nil
}
~~~

方法接收者写成 <code>*Alert</code> 时，方法可以修改原对象，也避免复制较大的 struct。经验规则：

- 需要修改对象时，用指针接收者。
- struct 内含 Mutex，必须避免复制，通常用指针接收者。
- 同一个类型的方法接收者尽量保持一致。
- 简单、只读、很小的值对象可以用值接收者，但不必刻意追求。

## 4.3 array、slice、map：最容易写出隐蔽 Bug 的三类容器

~~~go
// array：长度属于类型，实际项目中较少直接使用。
fixed := [3]int{1, 2, 3}

// slice：动态序列，是最常用的集合类型。
ids := []int64{101, 102}
ids = append(ids, 103)

// map：键值对，需要 make 后才能写入。
levels := make(map[string]string)
levels["high"] = "高优先级"

value, ok := levels["missing"]
if !ok {
    fmt.Println("键不存在")
}

_ = fixed
_ = value
~~~

记住：

- array 的长度是类型的一部分；slice 才更像 Java 的 List。
- slice 只是底层数组的一段视图，<code>append</code> 可能扩容并更换底层数组；不要假定两个 slice 一定共享数据。
- nil slice 可以直接 <code>append</code>；nil map 不能直接赋值，必须先 <code>make</code>。
- map 的遍历顺序不保证稳定；测试中不要依赖它的顺序。

## 4.4 package、可见性与组合

Go 用包组织代码，导出规则很简单：

~~~go
type AlertService struct{} // 首字母大写：其他包可访问
type alertStore struct{}   // 首字母小写：仅当前包可访问
~~~

包名通常全小写、简短、表达业务含义。不要创建万能的 <code>utils</code>、<code>common</code> 包；公共代码应按职责放置。包之间不能循环依赖。

Go 通过组合复用行为，而不是继承：

~~~go
type Notifier interface {
    Notify(ctx context.Context, alert Alert) error
}

type AlertService struct {
    notifier Notifier
}
~~~

这里的 <code>AlertService</code> 依赖能力（Notifier），而不是具体的邮件、短信实现。这样单测可以传入 fake notifier，生产环境可以传入真实实现。

## 4.5 error：Go 后端最需要练熟的基本功

用 <code>panic</code> 处理不可恢复的程序错误；普通的参数非法、记录不存在、数据库超时，都应返回 <code>error</code>。

~~~go
var ErrAlertNotFound = errors.New("alert not found")

func (s *Service) GetByID(ctx context.Context, id int64) (Alert, error) {
    alert, err := s.repo.FindByID(ctx, id)
    if err != nil {
        return Alert{}, fmt.Errorf("find alert %d: %w", id, err)
    }
    return alert, nil
}

func isNotFound(err error) bool {
    return errors.Is(err, ErrAlertNotFound)
}
~~~

实践规则：

1. 错误要在边界处处理：Handler 把业务错误映射成 HTTP 状态码；Repository 负责保留数据库上下文。
2. 需要保留根因时，用 <code>fmt.Errorf("操作说明: %w", err)</code> 包装。
3. 需要判断被包装的哨兵错误时，用 <code>errors.Is</code>；需要取出特定错误类型时，用 <code>errors.As</code>。
4. 不要吞掉错误：<code>_ = err</code> 只有在“确实可以忽略且有理由”时才使用。

## 4.6 JSON、DTO 与数据校验

JSON 编码只能看到导出的字段；字段首字母小写会导致看似“返回了空对象”的问题。

~~~go
type CreateAlertRequest struct {
    DeviceID string `json:"deviceId"`
    Level    string `json:"level"`
}

type AlertResponse struct {
    ID       int64  `json:"id"`
    DeviceID string `json:"deviceId"`
    Status   string `json:"status"`
}
~~~

输入 DTO、领域对象、数据库记录不一定是同一个 struct。初学项目可以少量转换；字段开始分化后要主动分开，避免把数据库内部字段或敏感字段直接返回给客户端。

# 5. 第一周后半：工程化、错误处理与测试

## 5.1 推荐的第一版目录

不要机械照搬 Java 的多层 package，也不要把所有文件堆进根目录。以业务为中心的轻量目录足够：

~~~text
water-alert-api/
├── cmd/
│   └── api/
│       └── main.go            # 程序入口，负责组装依赖和启动 HTTP 服务
├── internal/
│   ├── alert/
│   │   ├── model.go           # 领域对象、请求/响应 DTO
│   │   ├── service.go         # 业务规则
│   │   ├── repository.go      # Repository 接口
│   │   ├── mysql_repository.go
│   │   └── handler.go         # HTTP Handler
│   └── platform/
│       ├── config/
│       ├── database/
│       └── httpx/
├── migrations/
├── go.mod
├── go.sum
└── README.md
~~~

<code>internal</code> 是 Go 的语言级目录约束：其下包只能被父目录树内的代码导入，适合放业务实现，避免被外部模块误用。

## 5.2 先写测试，再堆功能

Go 原生测试包是 <code>testing</code>，约定测试文件以 <code>_test.go</code> 结尾。表驱动测试很常见：

~~~go
func TestNormalizeLevel(t *testing.T) {
    tests := []struct {
        name string
        in   string
        want string
        ok   bool
    }{
        {name: "high", in: "HIGH", want: "high", ok: true},
        {name: "invalid", in: "unknown", want: "", ok: false},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got, err := NormalizeLevel(tt.in)
            if (err == nil) != tt.ok {
                t.Fatalf("NormalizeLevel(%q) error = %v", tt.in, err)
            }
            if got != tt.want {
                t.Fatalf("NormalizeLevel(%q) = %q, want %q", tt.in, got, tt.want)
            }
        })
    }
}
~~~

第一阶段至少给下列场景写单测：

- 参数合法、非法、边界值。
- 记录不存在、状态不允许变更。
- 错误是否被正确包装和映射。
- 并发模块是否可以取消、等待、没有数据竞争。

HTTP 层测试可用 <code>net/http/httptest</code>，不需要先启动真实端口；数据库集成测试放到后面，并和单元测试区分。

## 5.3 每次提交前的质量命令

~~~powershell
go fmt ./...
go test ./...
go test -race ./...
go vet ./...
go mod tidy
go build ./...
~~~

<code>go test -race</code> 会用 race detector 检查数据竞争，开发机和 CI 都值得跑。它不能证明代码绝对线程安全，但能抓住很多共享 map、计数器和状态变量的错误。

# 6. 第二周前半：用标准库写 REST API，再接 Gin

## 6.1 为什么先写 net/http

先理解标准库，才能知道 Gin、Echo、Fiber 这类框架替你做了什么。Go 的 Web 基础并不复杂：

~~~text
http.Server
    ↓
ServeMux / Router
    ↓
Middleware（日志、恢复、请求 ID、鉴权）
    ↓
Handler
    ↓
Service
~~~

从本节开始，按前文的项目目录把下面代码保存为 <code>cmd/api/main.go</code>。第 0 天根目录的 Hello Go 程序可以保留作练习；启动 REST API 时则运行 <code>go run ./cmd/api</code>。

一个最小可启动服务：

~~~go
package main

import (
    "encoding/json"
    "log"
    "net/http"
    "time"
)

func main() {
    mux := http.NewServeMux()
    // Go 1.22 及以上支持带 HTTP 方法的路由模式。
    mux.HandleFunc("GET /healthz", healthz)

    server := &http.Server{
        Addr:              ":8080",
        Handler:           mux,
        ReadHeaderTimeout: 5 * time.Second,
    }

    log.Println("server listening on :8080")
    log.Fatal(server.ListenAndServe())
}

func healthz(w http.ResponseWriter, r *http.Request) {
    w.Header().Set("Content-Type", "application/json; charset=utf-8")
    _ = json.NewEncoder(w).Encode(map[string]string{"status": "ok"})
}
~~~

启动并验证：

~~~powershell
go run ./cmd/api
Invoke-RestMethod http://localhost:8080/healthz
~~~

真实业务 Handler 的职责应保持薄：解析输入、调用 Service、将成功或错误写为 HTTP 响应。SQL、事务、业务规则不要直接塞进 Handler。

## 6.2 Context 必须从请求一路向下传递

~~~go
func (h *Handler) GetAlert(w http.ResponseWriter, r *http.Request) {
    id, err := parseID(r.PathValue("id"))
    if err != nil {
        writeJSON(w, http.StatusBadRequest, map[string]string{"error": "invalid id"})
        return
    }

    alert, err := h.service.GetByID(r.Context(), id)
    if err != nil {
        writeError(w, err)
        return
    }

    writeJSON(w, http.StatusOK, alert)
}
~~~

从 <code>r.Context()</code> 传下去，客户端断开请求时，数据库查询、Redis 调用、下游 HTTP 调用才能有机会及时停止。不要在请求链路中随手换成 <code>context.Background()</code>。

## 6.3 API 最小边界

先实现下面五个接口，足够练到 REST、错误处理、数据库和测试：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | /healthz | 健康检查 |
| POST | /api/v1/alerts | 创建用水告警 |
| GET | /api/v1/alerts | 按状态、时间分页查询 |
| GET | /api/v1/alerts/{id} | 查询单条告警 |
| PATCH | /api/v1/alerts/{id}/resolve | 处理告警 |

统一响应不必设计得很花哨。成功时返回资源或列表；失败时至少返回稳定的错误码、可读消息与 request ID。不要把原始数据库错误直接暴露给前端。

## 6.4 什么时候引入 Gin

完成一版 <code>net/http</code> 后，路由、绑定、校验、中间件需求变多时再使用 Gin：

~~~powershell
go get github.com/gin-gonic/gin

~~~

~~~go
r := gin.New()
r.Use(gin.Logger(), gin.Recovery())
r.GET("/healthz", func(c *gin.Context) {
~~~

Gin 的 Context 适合处理 HTTP 细节；业务层和 Repository 仍应接收标准 <code>context.Context</code>，通常传入 <code>c.Request.Context()</code>。官方也提供从 [Gin REST API 教程](https://go.dev/doc/tutorial/web-service-gin) 开始的路线。

# 7. 第二周中段：MySQL、事务、配置与日志

## 7.1 先用 database/sql，不要一开始依赖 ORM

<code>database/sql</code> 是标准库的数据库抽象。它的 <code>*sql.DB</code> 代表连接池，通常在程序启动时创建一次、全局复用，并在退出时关闭；它不是“一条数据库连接”。

先安装 MySQL 驱动：

~~~powershell
go get github.com/go-sql-driver/mysql
go mod tidy
~~~

~~~go
import (
    "context"
    "database/sql"
    "time"

    _ "github.com/go-sql-driver/mysql"
)

func openDB(dsn string) (*sql.DB, error) {
    db, err := sql.Open("mysql", dsn)
    if err != nil {
        return nil, err
    }

    db.SetMaxOpenConns(20)
    db.SetMaxIdleConns(10)
    db.SetConnMaxLifetime(3 * time.Minute)

    ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
    defer cancel()

    if err := db.PingContext(ctx); err != nil {
        _ = db.Close()
        return nil, err
    }
    return db, nil
}
~~~

关键点：

- <code>sql.Open</code> 主要校验驱动和配置，不等于已经成功连库；用 <code>PingContext</code> 验证。
- 查询和写入使用 <code>QueryContext</code>、<code>QueryRowContext</code>、<code>ExecContext</code>，把请求 Context 传入。
- SQL 一律参数化，禁止字符串拼接用户输入。
- <code>rows</code> 用完要关闭，并检查 <code>rows.Err()</code>。
- 连接池参数要结合 MySQL 最大连接数和服务实例数调优，不能照抄一个“万能值”。

官方数据库教程见 [Accessing a relational database](https://go.dev/doc/tutorial/database-access)。

## 7.2 事务的最小正确模板

~~~go
var ErrAlertNotResolvable = errors.New("alert not found or not open")

func (s *Service) Resolve(ctx context.Context, id int64) error {
    tx, err := s.db.BeginTx(ctx, nil)
    if err != nil {
        return fmt.Errorf("begin transaction: %w", err)
    }
    defer func() {
        // Commit 成功后 Rollback 会返回 sql.ErrTxDone，忽略即可。
        _ = tx.Rollback()
    }()

    result, err := tx.ExecContext(
        ctx,
        "UPDATE water_alert SET status = ? WHERE id = ? AND status = ?",
        "resolved",
        id,
        "open",
    )
    if err != nil {
        return fmt.Errorf("resolve alert: %w", err)
    }

    affected, err := result.RowsAffected()
    if err != nil {
        return fmt.Errorf("read affected rows: %w", err)
    }
    if affected == 0 {
        return ErrAlertNotResolvable
    }

    if err := tx.Commit(); err != nil {
        return fmt.Errorf("commit transaction: %w", err)
    }
    return nil
}
~~~

因为更新条件同时限制了 <code>id</code> 与 <code>status = open</code>，受影响行数为 0 既可能是记录不存在，也可能是状态已被其他请求处理。上例返回一个通用的“不可处理”错误，避免把状态冲突误报为不存在；如果 API 必须严格区分 404 与 409，应在同一事务内读取并判断状态，或按团队的接口约定设计错误码。

事务中的所有 SQL 必须通过同一个 <code>tx</code> 执行，而不是混用 <code>db</code>。否则看似“开了事务”，实际部分操作仍在事务外。

## 7.3 配置和日志先保持简单

第一版使用环境变量即可：

~~~go

    addr = ":8080"

    return errors.New("MYSQL_DSN is required")
~~~

# 8. 第二周后半：goroutine、channel、Context 与并发治理

## 8.1 先区分四个工具的职责

| 工具 | 用途 | Java 中可类比的概念 |
| --- | --- | --- |
| goroutine | 启动一个并发执行单元 | 线程池任务，但调度和成本不同 |
| sync.WaitGroup | 等待一组 goroutine 结束 | CountDownLatch 的等待语义 |
| sync.Mutex / RWMutex | 保护共享内存 | synchronized / Lock |
| channel | 在 goroutine 之间传递数据或协调时序 | BlockingQueue 的一部分用途 |
| context.Context | 超时、取消、请求范围的传递 | 超时令牌、取消信号、显式上下文参数 |

“通过通信共享内存”是常见风格，但不是强制规则。共享 map、计数器、缓存状态等场景，用 Mutex 往往更直白；不要为了用 channel 而用 channel。

## 8.2 有界 worker pool：第一个必须手写的并发练习

需求：100 条告警要异步通知，但同时最多 5 个任务；请求取消或超时时要停止继续投递。

~~~go
func SendAll(
    ctx context.Context,
    alerts []Alert,
    workers int,
    send func(context.Context, Alert) error,
) error {
    if workers < 1 {
        return errors.New("workers must be positive")
    }

    jobs := make(chan Alert)
    var wg sync.WaitGroup
    var errMu sync.Mutex
    var errs []error

    allErrors := func() error {
        errMu.Lock()
        defer errMu.Unlock()
        return errors.Join(errs...)
    }

    worker := func() {
        defer wg.Done()
        for {
            select {
            case <-ctx.Done():
                return
            case alert, ok := <-jobs:
                if !ok {
                    return
                }
                jobCtx, cancel := context.WithTimeout(ctx, 3*time.Second)
                err := send(jobCtx, alert)
                cancel()
                if err != nil {
                    errMu.Lock()
                    errs = append(errs, err)
                    errMu.Unlock()
                }
            }
        }
    }

    wg.Add(workers)
    for i := 0; i < workers; i++ {
        go worker()
    }

    for _, alert := range alerts {
        select {
        case <-ctx.Done():
            close(jobs)
            wg.Wait()
            return errors.Join(ctx.Err(), allErrors())
        case jobs <- alert:
        }
    }

    // jobs 由发送方关闭；worker 只负责读取。
    close(jobs)
    wg.Wait()
    return allErrors()
}
~~~

这个例子练的是四件事：

1. worker 数量固定，所以不会为每条告警无限创建 goroutine。
2. 任务发送和 worker 读取都观察 <code>ctx.Done()</code>。
3. 每个通知还有独立的 3 秒超时，并用 <code>errors.Join</code> 汇总所有任务错误；示例会继续尝试其余任务，直到父 Context 取消。
4. 只有发送方关闭 channel，关闭后 worker 能自然退出。
5. 用 WaitGroup 确认所有 worker 已结束，避免后台任务“悄悄活着”。

Context 只会发出取消信号，**不能强制终止一个无视 Context 的阻塞函数**。因此 <code>send</code> 的实现必须使用传入的 Context：HTTP 请求用 <code>http.NewRequestWithContext</code>，数据库操作用 <code>ExecContext</code> / <code>QueryContext</code>；如果第三方 SDK 根本不支持取消，需要在接入时评估超时和隔离方案。

调用时设置明确超时：

~~~go
ctx, cancel := context.WithTimeout(parentCtx, 10*time.Second)
defer cancel()

err := SendAll(ctx, alerts, 5, notifier.Send)
~~~

## 8.3 Context 的硬规则

- 作为函数第一个参数传入：<code>func (s *Service) Do(ctx context.Context, ...)</code>。
- 由上游传下游；HTTP 请求从 <code>r.Context()</code> 开始。
- 创建 <code>WithCancel</code>、<code>WithTimeout</code>、<code>WithDeadline</code> 后，通常都要调用 cancel。
- 不要把 Context 长期存入 struct；不要用它传递正常业务参数。
- 不要向函数传 nil Context；没有可用上下文时用 <code>context.Background()</code>，但不要在请求链路里滥用它。

Context 的官方背景与约定见 [Go Concurrency Patterns: Context](https://go.dev/blog/context)。

## 8.4 并发代码的验收方式

~~~powershell
go test -race ./...
go test -run TestSendAll -count=100 ./...
~~~

如果测试偶发失败、race detector 报错、服务停止后仍有任务输出日志，就说明并发治理尚未完成。先把生命周期和共享状态梳理清楚，再考虑吞吐量优化。

# 11. Java 开发者最容易踩的坑

1. <code>:=</code> 会在内层作用域创建新变量，容易造成“外层 err / value 没更新”的阴影变量问题；复杂函数中尽量缩短作用域。
2. nil slice 可以 append，nil map 不能赋值；写 map 前先 make。
3. map 不是并发安全的；并发读写要加锁或调整设计。
4. interface 里装入“带类型的 nil 指针”后，interface 本身不一定等于 nil；不要只靠 <code>if x == nil</code> 猜测。
5. JSON 字段必须导出；首字母小写的字段不会被默认编码。
6. <code>defer</code> 后进先出，且 defer 语句中的参数在声明 defer 时就求值。
7. 不要用 panic 表示用户参数错误、数据库超时或记录不存在。
8. channel 通常由发送方关闭；不要关闭不属于自己的 channel，也不要重复关闭。
9. goroutine 不会因 HTTP 请求结束自动退出；必须用 Context、channel 或 WaitGroup 收尾。
10. Context 是取消 / 超时控制，不是 Java ThreadLocal，也不是放业务参数的 map。
11. 不要复制包含 Mutex 的 struct；否则锁的保护关系会失效。
12. 循环中启动 goroutine 时，显式把当前值作为参数传入，代码更清晰，也能兼容阅读旧版本 Go 代码时的捕获陷阱。
13. 数据库查询后要 close rows，并检查 rows.Err()；事务失败路径必须能回滚。
14. 不要把 Controller、Service、DAO、DTO、VO 等 Java 分层原样复制为大量空包；Go 更重视简单、显式和按业务聚合。
15. 不要跳过 gofmt。统一格式是 Go 生态的协作基础，不是可选的“代码风格偏好”。

> 我已有 Java / Spring 的 API、数据库、缓存和工程化基础，转 Go 时不需要重新学习后端问题本身。我的重点是适应 Go 的显式错误处理、组合式设计、Context 和并发模型。我会先用标准库完成一条 REST + MySQL + 测试的完整链路，再根据项目选择 Gin、Redis 或 gRPC，而不是只停留在语法层面。

### “Go 的 interface 和 Java 有什么不同？”

> Java 通常在类型声明时显式 implements 接口；Go 是隐式实现，只要方法集满足接口即可。实际设计中我会让接口保持小，并尽量由使用方定义，这样业务层依赖能力而不是具体实现，测试时也容易替换 fake。

### “为什么 Go 服务里到处传 context.Context？”

> Context 用来沿调用链传递取消和超时。HTTP Handler 从 r.Context() 开始向 Service、Repository 和下游调用传递，客户端断开或超时后，数据库、Redis 或外部 HTTP 调用就能及时停止，避免无效工作和 goroutine 泄漏。

### “goroutine 很轻，是不是可以无限开？”

> 不可以。轻量不等于不受限制。大量 goroutine 仍会占用内存、连接、CPU 和下游资源。对于批处理或通知场景，我会用有界 worker pool、Context 超时、WaitGroup 回收和 race detector，把并发数量、取消和收尾都明确下来。

**会 Go 语法不等于会用 Go 做后端。真正的分水岭是：错误处理、Context、测试、SQL、并发收尾，以及能否交付一个可运行、可解释的服务。**
