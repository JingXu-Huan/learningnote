# 07：包、接口与组合

> 预计：45～60 分钟<br>
> 本章目标：学会把代码拆到多个文件与包，并理解 Go 的隐式接口和构造函数注入。

------

## 1. 包与导出规则

同一目录下、同一个 <code>package</code> 的 Go 文件可以互相访问。跨包访问时，首字母决定可见性：

~~~go
type AlertService struct{} // 大写：导出，其他包可以使用
type alertStore struct{}   // 小写：仅当前包可见

func NewAlertService() *AlertService { return &AlertService{} }
func (s *AlertService) Create()      {}
~~~

包名通常小写、简短、表达业务含义。不要一开始就创建万能的 <code>utils</code> 或 <code>common</code> 包。

## 2. interface 是“能力约定”

~~~go
type Notifier interface {
    Send(message string) error
}

type ConsoleNotifier struct{}

func (ConsoleNotifier) Send(message string) error {
    fmt.Println("发送：", message)
    return nil
}
~~~

<code>ConsoleNotifier</code> 没有写 <code>implements Notifier</code>，但它拥有同名、同参数、同返回值的方法，因此自动实现了 Notifier。

## 3. 组合与构造函数注入

~~~go
type AlertService struct {
    notifier Notifier
}

func NewAlertService(notifier Notifier) *AlertService {
    return &AlertService{notifier: notifier}
}

func (s *AlertService) Notify(message string) error {
    return s.notifier.Send(message)
}
~~~

这相当于 Java 中“依赖接口、由构造器注入实现”。区别是 Go 不需要 Spring 容器自动扫描；通常在 <code>main</code> 里明确组装依赖。

## 4. 接口不要提前滥用

不推荐这样做：

~~~text
先为每一个 struct 创建一个同名 Interface，
即使项目里根本没有第二个实现，也没有测试替身需求。
~~~

更好的做法：

1. 先写具体实现。
2. 当业务层只需要某个能力、或者单测需要 fake 实现时，再提取小接口。
3. 让接口靠近使用它的代码，而不是都堆进 common。

## 5. 为小项目准备的目录

下一章开始创建第一个小项目。建议结构：

~~~text
alert-cli/
├── cmd/
│   └── alert-cli/
│       └── main.go
├── internal/
│   └── alert/
│       ├── model.go
│       └── store.go
├── go.mod
└── README.md
~~~

<code>internal</code> 下的包只能被父目录树中的代码导入，适合放项目内部业务实现。

第 08 章会新建一个独立的 <code>alert-cli</code> Module，因此会在 <code>internal/alert</code> 中重新定义项目用的 Alert 与 Status。把第 04 章当作语法练习；从第 08 章开始，以小项目目录中的模型代码为准。

## 6. 动手练习

1. 写一个 <code>Notifier</code> 接口。
2. 写一个只打印日志的实现。
3. 让 <code>AlertService</code> 通过构造函数接收它。
4. 把实现替换为一个 fake notifier，确认业务代码不需要修改。
