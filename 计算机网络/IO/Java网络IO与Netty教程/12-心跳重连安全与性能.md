# 十二、心跳、重连、安全与性能

## 12.1 心跳检测的是“长期无有效活动”

`IdleStateHandler` 可以产生读空闲、写空闲、全空闲事件：

```java
pipeline.addLast(new IdleStateHandler(
        60, // 60 秒没有读
        20, // 20 秒没有写
        0, TimeUnit.SECONDS));
pipeline.addLast(new HeartbeatHandler());
```

```java
public final class HeartbeatHandler
        extends ChannelInboundHandlerAdapter {

    @Override
    public void userEventTriggered(
            ChannelHandlerContext ctx, Object event) {
        if (event instanceof IdleStateEvent idle) {
            if (idle.state() == IdleState.WRITER_IDLE) {
                ctx.writeAndFlush(Ping.INSTANCE);
                return;
            }
            if (idle.state() == IdleState.READER_IDLE) {
                ctx.close(); // 长时间收不到任何数据
                return;
            }
        }
        ctx.fireUserEventTriggered(event);
    }
}
```

心跳间隔必须小于判死阈值，并容忍网络抖动。心跳包也应经过正常的帧限制、版本验证和速率限制。

## 12.2 重连必须退避并加抖动

客户端断线后立即无限重连会在服务恢复时形成惊群：

```java
private void reconnect(int attempt) {
    long base = Math.min(30_000L, 500L << Math.min(attempt, 6));
    long jitter = ThreadLocalRandom.current().nextLong(base / 4 + 1);
    group.schedule(() ->
            connect().addListener(future -> {
                if (!future.isSuccess()) {
                    reconnect(attempt + 1);
                }
            }),
            base + jitter, TimeUnit.MILLISECONDS);
}
```

还需要：

- 成功连接后重置 attempt；
- 防止同一客户端同时存在多个重连任务；
- 应用停机时取消重连；
- 区分认证失败、限流和临时网络失败，永久错误不应重试；
- 请求是否重放由幂等性和协议语义决定。

## 12.3 TLS 放在 Pipeline 前端

```java
SslContext sslContext = SslContextBuilder.forServer(certFile, keyFile)
        .protocols("TLSv1.3", "TLSv1.2")
        .build();

pipeline.addFirst("tls",
        sslContext.newHandler(channel.alloc()));
```

TLS Handler 必须先解密入站字节，后续帧解码器才能看到明文协议。客户端要验证服务端证书和主机名；教程/测试中的 `InsecureTrustManagerFactory` 不能用于生产。

生产安全清单：

- 私钥不进入仓库，证书支持轮换；
- 配置握手超时和最大帧；
- 鉴权早于昂贵业务；
- 日志脱敏，不记录 token 和完整敏感正文；
- 依赖版本跟进 Netty 安全公告；
- 公网服务配合连接数、握手、消息速率与 IP 级限制。

## 12.4 文件传输与零拷贝

非 TLS 的文件通道可以：

```java
FileChannel file = FileChannel.open(path, StandardOpenOption.READ);
DefaultFileRegion region =
        new DefaultFileRegion(file, 0, file.size());
ctx.write(region);
ctx.writeAndFlush(LastHttpContent.EMPTY_LAST_CONTENT)
        .addListener(future -> file.close());
```

`FileRegion` 可走 `transferTo` 路径。TLS 需要加密明文字节，通常不能直接使用同样的内核零拷贝路径，可用 `ChunkedNioFile` 等分块发送。

## 12.5 Native transport

Netty 可在支持的平台使用 epoll、kqueue 等 transport；它们提供平台能力和特定优化，但会增加原生依赖与部署矩阵。先用 NIO 得到正确基线，再用相同负载压测后决定。

选择 transport 时检查：

- 运行平台与架构；
- native 依赖是否正确加载；
- 容器文件描述符和内核参数；
- 行为是否在降级为 NIO 后仍正确；
- CI 是否覆盖真实目标平台。

## 12.6 性能优化顺序

```text
先正确分帧和限制资源
-> 消除 EventLoop 阻塞
-> 建立延迟/吞吐/错误/内存基线
-> 定位 CPU、分配、锁、系统调用或网络瓶颈
-> 一次只改一个参数并复测
```

优先观测：

- 活跃连接、建连/断连速率；
- EventLoop 任务排队时间；
- 请求 P50/P95/P99/P999；
- 待写字节和不可写 Channel 数；
- Direct Memory、池化分配器指标和泄漏；
- 解码失败、超长帧、TLS 握手失败；
- CPU、GC、上下文切换、重传和丢包。

## 12.8 知识问答

**问：收到业务消息是否应重置读空闲计时？**

答：默认任何读取活动都会重置。若只认可完整协议消息或心跳 ACK，应在业务层额外维护“最后有效消息时间”。

**问：重连后能直接重发所有未确认请求吗？**

答：不能一概而论。必须根据幂等键、服务端去重、请求截止时间和业务副作用决定。

**问：TLS 会让 Netty 变成阻塞 IO 吗？**

答：不会，但握手、加解密和证书处理增加 CPU 与缓冲区成本，必须监控和压测。

**问：调大 Socket 缓冲区一定提高吞吐吗？**

答：不一定。它会改变带宽时延积适配和内存占用，还可能掩盖背压。应以真实 RTT、带宽和消息模式验证。

### 动手题

让服务端 10 秒读空闲关闭连接；客户端只在写空闲时发 Ping。然后故意丢弃 Pong，验证客户端能识别“TCP 仍连接但业务已失活”。
