# 十一、异步任务、背压与线程切换

> 白话翻译：如果客户端一直往店里送货，但网络来不及发出去，门口就会堆箱子。`Future` 是取货凭条，背压是“堆太多就先让上游慢一点”。

## 11.1 Future 表示结果，Promise 负责完成结果

Netty 的 IO 操作通常立即返回 `ChannelFuture`：

```java
ChannelFuture future = ctx.writeAndFlush(response);
future.addListener(result -> {
    if (!result.isSuccess()) {
        log.warn("write failed", result.cause());
        result.channel().close();
    }
});
```

`Future` 供调用方观察；`Promise` 还暴露 `setSuccess`/`setFailure`，通常由实现异步操作的一方持有。

## 11.2 不要在 EventLoop 阻塞等待

错误写法：

```java
public void channelRead(ChannelHandlerContext ctx, Object msg)
        throws InterruptedException {
    ctx.writeAndFlush(msg).sync(); // 可能阻塞 EventLoop，甚至死锁
}
```

正确思路是监听：

```java
ctx.writeAndFlush(msg).addListener(ChannelFutureListener.FIRE_EXCEPTION_ON_FAILURE);
```

`sync` 适合 main 启动线程等待 bind/close，不适合 EventLoop 中等待所属 Channel 的操作。

## 11.3 组合外部异步结果

外部服务返回 `CompletionStage` 时，不要在 EventLoop `join`：

```java
CompletionStage<User> stage = userService.findAsync(userId);
stage.whenComplete((user, error) -> {
    ctx.executor().execute(() -> {
        if (error != null) {
            ctx.fireExceptionCaught(error);
        } else if (ctx.channel().isActive()) {
            ctx.writeAndFlush(toResponse(user));
        }
    });
});
```

回到 `ctx.executor()` 后再修改连接相关状态，可维持该 Channel 的顺序和线程所有权。还要处理连接先关闭、请求超时、重复完成等竞态。

## 11.4 什么是出站背压

生产速度高于网络发送速度时，消息进入 `ChannelOutboundBuffer`，待写字节持续增长。Netty 用高低水位线改变 `Channel.isWritable()`：

```java
bootstrap.childOption(ChannelOption.WRITE_BUFFER_WATER_MARK,
        new WriteBufferWaterMark(32 * 1024, 64 * 1024));
```

- 超过 high water mark：`isWritable()` 变 false；
- 降到 low water mark 以下：恢复 true；
- 水位是信号，不会自动替业务限流或丢弃消息。

## 11.5 教程代码：响应可写状态

```java
public final class BackpressureHandler
        extends ChannelInboundHandlerAdapter {

    @Override
    public void channelWritabilityChanged(ChannelHandlerContext ctx) {
        boolean writable = ctx.channel().isWritable();
        ctx.channel().config().setAutoRead(writable);
        if (writable) {
            ctx.read();
        }
        System.out.printf("channel=%s writable=%s pending=%d%n",
                ctx.channel().id().asShortText(),
                writable,
                ctx.channel().unsafe().outboundBuffer() == null
                        ? 0
                        : ctx.channel().unsafe().outboundBuffer()
                                .totalPendingWriteBytes());
        ctx.fireChannelWritabilityChanged();
    }
}
```

上例为教学展示。生产代码不应依赖 `unsafe()` 内部接口做业务逻辑；观测待写字节应优先使用稳定指标或版本适配层。暂停读适合“请求产生响应”的链路，但双向独立流、控制帧和心跳可能需要更细粒度策略。

更通用的背压策略：

- 限制每连接待处理请求数和待写字节；
- 上游暂停生产或返回“系统繁忙”；
- 对可丢数据按优先级丢弃/合并；
- 超过绝对上限主动关闭慢连接；
- 给业务任务设置截止时间，过期结果不再写回。

## 11.6 AUTO_READ 与手动读取

```java
channel.config().setAutoRead(false);
channel.read(); // 请求读取一轮
```

关闭 `AUTO_READ` 后由应用决定何时继续读，可把网络入口速度与业务消费能力绑定。忘记再次 `read()` 会让连接看似“卡死”。

## 11.7 Flush 策略

- 低延迟：每个响应 `writeAndFlush`，系统调用更多。
- 高吞吐：多次 `write` 后统一 `flush`。
- Netty 提供 `FlushConsolidationHandler` 合并一定条件下的 flush。

批量不能无限等待，应设置条数、字节数或时间上限。

## 11.9 知识问答

**问：`writeAndFlush` 成功是否代表对端业务已经处理？**

答：不是。它通常只表示本地出站操作成功推进。端到端确认需要应用协议 ACK、requestId 和超时。

**问：Channel 不可写时写入会立刻失败吗？**

答：通常仍可入队，所以必须主动响应 `isWritable`。不处理只会继续扩大内存压力。

**问：关闭 AUTO_READ 能防止所有内存增长吗？**

答：不能。已经读取、正在业务线程排队、待写和外部系统中的数据仍占内存，需要全链路容量控制。

**问：水位线设得越小越安全吗？**

答：过小会频繁切换可写状态、降低吞吐；过大又增加单连接内存。应结合消息大小、连接数和延迟目标压测。
