# 一、网络 IO 基本功与常见模型

## 1.1 先建立分层视角

一次 `read` 不是“直接从网线读到 Java 对象”，而是：

```text
对端应用
  -> TCP 发送缓冲区
  -> 网络
  -> 本机内核接收缓冲区
  -> Socket/Channel
  -> byte[] / ByteBuffer / ByteBuf
  -> 解码器
  -> 业务对象
```

TCP 提供可靠、有序的**字节流**，不保留发送端每次 `write` 的消息边界。发送两次不代表接收端恰好读取两次，这是后面粘包/拆包问题的根源。

## 1.2 四个容易混淆的概念

| 维度 | 问的问题 | 典型含义 |
| --- | --- | --- |
| 同步/异步 | 谁确认操作最终完成？ | 同步由调用方推进；异步完成后通知调用方 |
| 阻塞/非阻塞 | 线程不能立刻推进时是否等待？ | 阻塞让出 CPU 等待；非阻塞立即返回 |
| 多路复用 | 谁同时观察大量连接的就绪状态？ | `Selector`/epoll 集中等待多个连接 |
| Reactor/Proactor | 收到“就绪”还是“已完成”事件？ | Reactor 处理就绪；Proactor 消费完成结果 |

因此“同步”不等于“阻塞”，“异步”也不等于“开一个线程执行阻塞 IO”。

## 1.3 Java 中的三条主线

```text
BIO：Socket + InputStream/OutputStream
NIO：SocketChannel + ByteBuffer + Selector
AIO：AsynchronousSocketChannel + CompletionHandler/Future
```

Netty 最常用的 transport 采用 NIO/Reactor 思路：EventLoop 收到 Channel 就绪事件后执行读取、解码和 Pipeline 传播。

## 1.4 教程代码：证明 TCP 没有消息边界

发送端连续写两段：

```java
try (Socket socket = new Socket("127.0.0.1", 9000)) {
    OutputStream out = socket.getOutputStream();
    out.write("HELLO".getBytes(StandardCharsets.UTF_8));
    out.write("NETTY".getBytes(StandardCharsets.UTF_8));
    out.flush();
}
```

接收端每次只读 3 字节：

```java
byte[] buffer = new byte[3];
int n;
while ((n = socket.getInputStream().read(buffer)) != -1) {
    System.out.println(new String(buffer, 0, n, StandardCharsets.UTF_8));
}
```

可能看到 `HEL`、`LON`、`ETT`、`Y`。具体分段不稳定，所以应用协议必须自行定义边界，不能依赖一次 `write` 对应一次 `read`。

## 1.5 必须牢记的返回值

- 阻塞 `InputStream.read`：无数据时等待，EOF 返回 `-1`。
- 非阻塞 `SocketChannel.read`：可能返回 `0`；EOF 仍返回 `-1`。
- `write` 返回实际写入字节数，不能假设一次写完。
- 就绪事件只是“现在大概率可以推进”的提示，处理代码仍须接受返回 `0`。

## 1.7 知识问答

**问：非阻塞 IO 是否一定更快？**

答：不一定。它的主要价值是让少量线程管理大量连接。连接很少、业务简单时，BIO 代码可能更直接，吞吐也足够。

**问：`read() == 0` 和 `read() == -1` 有什么区别？**

答：`0` 表示这次没有读到字节，连接仍可能有效；`-1` 表示对端正常结束输入流，通常应取消注册并关闭连接。

**问：线程被阻塞是否一直占用 CPU？**

答：通常不会持续占用 CPU，但线程仍占用栈内存和调度资源；大量线程还会增加上下文切换成本。

**问：UDP 也有粘包吗？**

答：UDP 是数据报协议，保留报文边界；但可能丢失、乱序、重复，且单个数据报大小受限。TCP 的边界问题与 UDP 的可靠性问题不是一回事。
