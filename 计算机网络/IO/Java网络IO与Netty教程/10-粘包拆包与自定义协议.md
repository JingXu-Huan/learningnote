# 十、粘包拆包与自定义协议

> TCP 给 Netty 的是“可能长、可能短的一串字节”，不是 `Message` 列表。分帧器的工作就是从字节流中恢复一条条完整消息。

> 白话翻译：TCP 像把很多句话倒进同一个袋子里，可能半句话先到，也可能三句话一起到。分帧器就是“按换行或长度把袋子重新分成一条条消息”。

## 10.1 先定义“帧”

TCP 只有字节流，应用协议需要一种分帧方式：

| 方式 | Netty 解码器 | 优点 | 风险/限制 |
| --- | --- | --- | --- |
| 固定长度 | `FixedLengthFrameDecoder` | 简单 | 浪费空间、长度不灵活 |
| 分隔符 | `LineBasedFrameDecoder` / `DelimiterBasedFrameDecoder` | 文本直观 | 要转义分隔符并限制最大帧 |
| 长度字段 | `LengthFieldBasedFrameDecoder` | 二进制协议通用 | 参数易配错，必须校验长度 |
| 协议自描述 | 自定义 `ByteToMessageDecoder` | 最灵活 | 状态与安全责任都在自己 |

## 10.2 本教程协议

```text
 0               4 5 6   8          12          16
 +---------------+-+-+---+-----------+-----------+
 | magic "LNIO"  |v|t|flag| requestId | bodyLength|
 +---------------+-+-+---+-----------+-----------+
 | body (UTF-8, bodyLength bytes)                 |
 +------------------------------------------------+

magic      4 bytes
version    1 byte
type       1 byte
flags      2 bytes
requestId  4 bytes
bodyLength 4 bytes
固定头共 16 bytes
```

约束：

- 最大正文 1 MiB；
- 当前版本只能是 1；
- magic 不匹配立即关闭；
- `bodyLength < 0` 或超过上限立即拒绝；
- requestId 用于请求/响应关联和日志追踪。

## 10.3 使用通用长度字段解码器

正文长度字段位于偏移 12，长度 4；字段值只表示正文长度，完整帧还要加 16 字节头：

```java
pipeline.addLast(new LengthFieldBasedFrameDecoder(
        1024 * 1024 + 16, // maxFrameLength
        12,               // lengthFieldOffset
        4,                // lengthFieldLength
        0,                // lengthAdjustment
        0));              // initialBytesToStrip
pipeline.addLast(new MessageDecoder());
pipeline.addLast(new MessageEncoder());
```

计算公式：

```text
frameLength =
lengthFieldValue
+ lengthFieldOffset
+ lengthFieldLength
+ lengthAdjustment
```

这里是 `bodyLength + 12 + 4 + 0`，恰好得到 `16 + bodyLength`。

## 10.4 教程代码：编码器

完整代码位于 `示例代码/.../netty/protocol/`。

```java
public final class MessageEncoder
        extends MessageToByteEncoder<Message> {

    private static final int MAGIC = 0x4C4E494F; // LNIO
    private static final int MAX_BODY = 1024 * 1024;

    @Override
    protected void encode(
            ChannelHandlerContext ctx, Message msg, ByteBuf out) {
        byte[] body = msg.body().getBytes(StandardCharsets.UTF_8);
        if (body.length > MAX_BODY) {
            throw new EncoderException("body too large: " + body.length);
        }
        out.writeInt(MAGIC);
        out.writeByte(1);
        out.writeByte(msg.type());
        out.writeShort(0);
        out.writeInt(msg.requestId());
        out.writeInt(body.length);
        out.writeBytes(body);
    }
}
```

`MessageToByteEncoder` 管理输出 ByteBuf；通常不要在 `encode` 中释放 `out` 或手动 flush。

### `encode` 参数和字段分别表示什么

| 名称 | 含义 | 来自哪里 |
| --- | --- | --- |
| `ctx` | 当前编码器的上下文 | Netty 回调参数 |
| `msg` | 待发送的 `Message` 业务对象 | 业务 Handler 的 `writeAndFlush` |
| `out` | Netty 分配好的输出 `ByteBuf` | 编码器写入最终网络字节的地方 |
| `MAGIC` | 协议魔数，固定值 `LNIO` | 用于快速判断对端是不是本协议 |
| `type` | 消息类别，如请求/响应/心跳 | 由业务协议定义，不能只看字段名猜含义 |
| `requestId` | 请求关联号 | 客户端并发多个请求时，用它找到对应响应 |
| `bodyLength` | 正文 UTF-8 字节数 | 不是 Java 字符串 `length()`；中文通常占多个字节 |

### 把一条消息代入协议

例如 `new Message(1, 42, "你好")`：`type=1`、`requestId=42`；UTF-8 下“你好”是 6 字节，因此 `bodyLength=6`。网络中先写 16 字节固定头，再写 6 字节正文。解码时必须依据 **bodyLength 的字节数**，不能依据 Java 字符数量读取。

## 10.5 教程代码：解码器

因为上游已交付完整帧，这里只需验证并解析：

```java
public final class MessageDecoder
        extends MessageToMessageDecoder<ByteBuf> {

    private static final int MAGIC = 0x4C4E494F;
    private static final int MAX_BODY = 1024 * 1024;

    @Override
    protected void decode(
            ChannelHandlerContext ctx, ByteBuf in, List<Object> out) {
        int magic = in.readInt();
        int version = in.readUnsignedByte();
        int type = in.readUnsignedByte();
        in.skipBytes(2);
        int requestId = in.readInt();
        int bodyLength = in.readInt();

        if (magic != MAGIC || version != 1) {
            throw new CorruptedFrameException("bad magic/version");
        }
        if (bodyLength < 0 || bodyLength > MAX_BODY
                || bodyLength != in.readableBytes()) {
            throw new CorruptedFrameException(
                    "invalid body length: " + bodyLength);
        }
        String body = in.readCharSequence(
                bodyLength, StandardCharsets.UTF_8).toString();
        out.add(new Message(type, requestId, body));
    }
}
```

`MessageToMessageDecoder` 默认释放输入帧，所以输出应是独立业务对象；若输出输入 ByteBuf 的视图，必须 retain。

### 解码代码按执行顺序翻译

1. `readInt()` 读取并推进游标 4 字节，得到 `magic`。
2. `readUnsignedByte()` 把 0～255 的一个字节读成不会为负数的 `int`，适合 version/type。
3. `skipBytes(2)` 跳过当前暂未使用的 flags。
4. 读取 `requestId`、`bodyLength` 后，先校验长度和剩余字节数。
5. 最后把正文按 UTF-8 转成 String，并 `out.add(...)` 交给下游业务 Handler。

`out` 是一个列表而不是单个对象，是因为一次解码调用理论上可以产出 0、1 或多条业务消息。框架会把列表中的每一个对象依次触发到下游。

## 10.6 自己继承 ByteToMessageDecoder 时

若没有上游帧解码器，必须采用“数据不足就 return，且不要破坏 readerIndex”的方式：

```java
if (in.readableBytes() < 16) {
    return;
}
in.markReaderIndex();
int magic = in.readInt();
// 读取头...
if (in.readableBytes() < bodyLength) {
    in.resetReaderIndex();
    return;
}
// 到这里才能消费完整帧并 out.add(...)
```

一个 `decode` 调用可能收到 0 条、1 条或多条完整帧。不要在数据不足时抛异常，也不要无限循环而不消费字节。

## 10.7 安全边界

- 最大帧长度必须在分配大内存之前验证。
- 不要信任客户端给出的版本、类型、压缩标记和长度。
- 压缩协议要限制解压后大小，防御压缩炸弹。
- 认证应在昂贵反序列化或业务处理之前完成。
- Java 原生序列化不适合作为不可信网络边界。

## 10.9 知识问答

**问：粘包是 Netty 的 Bug 吗？**

答：不是。它是把 TCP 字节流误当消息流后的现象。Netty 解码器负责按应用协议恢复边界。

**问：设置 `TCP_NODELAY` 能解决粘包吗？**

答：不能。它影响小包发送延迟，不恢复应用层消息边界。

**问：为什么长度字段也要设置最大帧？**

答：攻击者可声明极大长度，让服务端长期累积或尝试分配巨量内存。最大帧是网络入口的重要安全边界。

**问：解码器为什么可能一次输出多条消息？**

答：一次网络读取可能包含多个完整帧。累积解码器会反复调用解码逻辑，直到数据不足或本轮限制到达。
