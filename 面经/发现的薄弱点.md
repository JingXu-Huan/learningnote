# 发现的薄弱点

## 一、计算机网络

### 1. HTTPS 加密过程

#### 答案

HTTPS = HTTP + TLS。

核心过程如下：

1. 客户端发起 `ClientHello`，告诉服务端自己支持的 TLS 版本、加密套件、随机数。
2. 服务端返回 `ServerHello`，选择一个双方都支持的加密套件，并返回服务端证书、公钥、随机数。
3. 客户端验证证书是否合法。
4. 验证通过后，客户端生成一个 `pre-master` 或直接参与密钥协商，并用服务端公钥加密后发给服务端。
5. 双方根据协商材料计算出同一个 `session key`。
6. 后续 HTTP 数据都使用这个对称密钥加密传输。

面试里可以再补一句：

- 非对称加密：解决密钥交换问题。
- 对称加密：解决后续大数据量传输效率问题。
- 数字证书：解决“你连的是不是真服务器”的身份认证问题。

### 2. TCP/IP 协议分层

#### 答案

TCP/IP 常见四层模型：

1. 应用层：HTTP、HTTPS、DNS、FTP、SMTP
2. 传输层：TCP、UDP
3. 网络层：IP、ICMP
4. 网络接口层：以太网、Wi-Fi

如果按 OSI 七层说，也可以对应为：

1. 应用层
2. 表示层
3. 会话层
4. 传输层
5. 网络层
6. 数据链路层
7. 物理层

面试里重点说清楚：

- TCP/UDP 属于传输层
- IP 属于网络层
- HTTP 属于应用层

## 二、MySQL / 存储引擎

### 3. 数据库索引为什么是前缀匹配的

#### 答案

本质原因是 B+ 树索引按照“最左前缀”有序存储。

比如联合索引 `(a, b, c)`，实际排序规则是先按 `a` 排，再按 `b` 排，最后按 `c` 排。

所以它天然支持：

- `a`
- `a, b`
- `a, b, c`

但不天然支持：

- `b`
- `b, c`
- `c`

因为跳过了最左列后，B+ 树无法直接利用已有的有序性快速定位。

面试可直接总结：

- 联合索引遵循最左前缀匹配原则
- 原因是底层 B+ 树节点的排序方式决定的
- 遇到范围查询后，后面的列利用率通常会下降

### 4. 事务出现异常，为什么看 binlog 而不是 redo log

#### 答案

两者作用不同：

- `redo log`：InnoDB 存储引擎级别，主要用于崩溃恢复，保证事务的持久性
- `binlog`：MySQL Server 层日志，记录的是实际执行过的逻辑操作，主要用于主从复制、数据恢复、问题排查

为什么排查业务异常更常看 `binlog`：

1. `binlog` 更接近真实 SQL 操作
2. 可以看到数据“被改成了什么”
3. 更适合按时间、按事务、按表去追踪问题
4. `redo log` 偏底层，主要是页的物理修改信息，不适合直接看业务语义

一句话回答：

排查“业务数据为什么错了”，优先看 `binlog`；排查“宕机后数据怎么恢复”，更偏向 `redo log`。

### 5. explain 这个关键字，看的话关注哪几个字段

#### 答案

`EXPLAIN` 用来分析 SQL 执行计划。

面试里重点关注这些字段：

1. `type`
   表示访问类型，性能从好到差大致是：
   `system > const > eq_ref > ref > range > index > ALL`

   其中：
   - `ALL` 表示全表扫描，通常要警惕
   - `range` 表示范围扫描，常见于索引范围查询
   - `ref` / `eq_ref` 一般说明索引用得不错

2. `key`
   实际使用了哪个索引。

3. `possible_keys`
   可能会使用哪些索引。

4. `rows`
   预估扫描行数，越小越好。

5. `Extra`
   很关键，常关注：
   - `Using filesort`
   - `Using temporary`
   - `Using where`
   - `Using index`

一句话总结：

先看有没有走索引，再看扫描行数大不大，最后看 `Extra` 里有没有 `Using filesort` 和 `Using temporary`。

## 三、Java 基础与 JVM

### 6. 红黑树

#### 答案

红黑树是一种自平衡二叉搜索树，用来保证查找、插入、删除的时间复杂度接近 `O(log n)`。

它的核心性质：

1. 节点非红即黑
2. 根节点是黑色
3. 叶子空节点是黑色
4. 红色节点的两个子节点必须是黑色，不能有连续红节点
5. 从任意节点到其所有叶子节点的黑色节点数量相同

这样做的好处是：

- 不会像普通二叉搜索树那样退化成链表
- 通过颜色约束，保证树的高度不会太离谱

Java 中常见应用：

- `HashMap` 在链表过长时转红黑树
- `TreeMap` 底层就是红黑树

### 7. MD5 算法

#### 答案

MD5 是一种摘要算法，用来把任意长度的数据计算成固定长度的摘要值，通常是 128 位。

特点：

- 不可逆
- 输入稍微变化，结果差异很大
- 计算快

但它已经不安全了，因为存在碰撞风险，所以：

- 不适合直接用于密码存储
- 也不适合安全要求高的签名场景

如果面试问密码存储：

- 不能直接存 MD5
- 应该加盐
- 更推荐 `BCrypt`、`scrypt`、`Argon2`

### 8. JVM 内存模型

#### 答案

如果面试官问的是 JVM 运行时内存区域，一般回答：

1. 程序计数器
2. Java 虚拟机栈
3. 本地方法栈
4. 堆
5. 方法区

各自作用：

- 程序计数器：记录当前线程执行到哪条字节码指令
- 虚拟机栈：方法调用时的栈帧
- 本地方法栈：给 Native 方法使用
- 堆：对象实例主要都在这里
- 方法区：类信息、常量、静态变量、即时编译后的代码等

如果面试官问的是 JMM，也就是 Java Memory Model，要区分开：

- 主内存
- 工作内存
- `volatile`
- `synchronized`
- happens-before

所以回答前最好先确认：

“您说的是 JVM 运行时内存区域，还是 Java 内存模型 JMM？”

## 四、系统设计 / 工程实践

### 9. 断点续传怎么实现，上传文件并发控制怎么解决

#### 答案

断点续传的核心是“分片上传 + 状态记录 + 续传校验”。

实现思路：

1. 前端把大文件切成多个分片
2. 每个分片带上文件唯一标识、分片序号、总分片数
3. 服务端记录已经上传成功的分片
4. 中断后，前端先询问服务端哪些分片已存在
5. 前端只补传缺失分片
6. 全部分片上传完后，服务端再合并文件

上传并发控制可以这样答：

1. 前端限制并发数，比如一次只传 3 到 5 个分片，避免把浏览器和网络打满
2. 服务端对同一个文件 ID 做幂等控制，防止重复写入
3. 合并文件时加锁，避免多个合并任务并发执行
4. 分片状态表加唯一约束，如 `(file_id, chunk_no)`，防止重复上传

面试加分点：

- 文件唯一标识常用文件 hash
- 秒传本质是服务端已经存在完整文件，无需再传

### 10. 刚下完单，订单信息还在消息队列中未写入数据库时，怎么通过订单 ID 查询订单信息

#### 答案

这是一个“最终一致性 + 写后短暂不可见”的问题。

常见方案：

1. 下单成功后，先把订单基础信息写入 Redis，状态标记为“处理中”
2. 消费 MQ 后再落库，成功后更新 Redis 或删除临时缓存
3. 用户按订单 ID 查询时，先查 Redis，再查数据库
4. 如果数据库还没有，但 Redis 有，就返回“处理中”的订单视图

也可以这样设计：

- 先落库，再发 MQ，保证查订单时数据库一定有记录
- MQ 只做后续异步动作，比如扣库存、发优惠券、发通知

面试回答建议：

- 如果订单查询是强需求，主链路最好先落库
- 如果必须异步落库，就要引入缓存兜底或“处理中”状态页
- 核心目标不是绝对实时一致，而是用户查询时不能直接查无此单

## 六、工具 / AI 工程

### 12. skills 的组成形式？有什么作用？

#### 答案

如果这里说的是 Codex / Claude 这一类工具里的 `skill`，可以理解成“可复用的任务说明书 + 资源入口”。

组成形式通常包括：

1. `SKILL.md`
   定义这个 skill 什么时候用、怎么用、有哪些限制。

2. `scripts/`
   放辅助脚本，避免每次重复手写。

3. `templates/` 或 `assets/`
   放模板、示例、固定资源。

4. `examples/`
   放参考输入输出，帮助稳定产出。

作用：

1. 沉淀固定工作流
2. 降低重复提示成本
3. 让复杂任务执行得更稳定
4. 让 agent 知道什么时候该读哪些说明、调用哪些工具

一句话总结：

skill 本质上是把“经验、步骤、模板、脚本”打包成一个可重复执行的能力单元。
