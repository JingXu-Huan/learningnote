#### ✅ 推荐方案：**先更新数据库，再删除缓存**

这是 Redis 官方文档也推荐的方式。

逻辑：

```
更新数据库 → 删除缓存
```

优点：

- 删除缓存失败的概率比写缓存小得多；
- 即便删除缓存失败，下次写操作仍会刷新。

缺点：

- 如果“删除缓存失败”，会短暂存在脏数据；
- 在极端并发场景中仍可能出现竞态。

------

### 四、竞态问题的进一步解决方案

1. **延迟双删策略**
    更新数据库 → 删除缓存 → 延迟一段时间后再删一次缓存。
    伪代码：

   ```
   updateDB();
   deleteCache();
   Thread.sleep(500);
   deleteCache();
   ```

   延迟时间 > 并发读写峰值延迟，保证旧缓存被覆盖的概率极低。

------

1. **异步消息队列（MQ）保证最终一致**
    数据库更新成功后，发送一个“清除缓存”的消息到 MQ，
    Redis 消费者监听并删除对应缓存。
    适用于高并发或异步系统。

------

1. **缓存更新加分布式锁**
    当某个 key 正在被更新或删除时，加分布式锁（如 Redis 的 setnx）。
    防止多个线程同时修改导致竞态。
    缺点是实现复杂，性能略低。

------

1. **TTL 兜底**
    给缓存设置过期时间（如 5 分钟、10 分钟）。
    即使偶发不一致，也能在过期后恢复正确数据。
    ——这是所有方案的“最后保险丝”。

------

### 五、总结方案选择

| 场景                    | 推荐策略                                            |
| ----------------------- | --------------------------------------------------- |
| 一般系统（中等并发）    | **更新数据库 → 删除缓存**                           |
| 高频读写 + 强一致性要求 | **延迟双删** 或 **MQ 异步删除**                     |
| 极端高并发写场景        | **加分布式锁** 或 **强一致性设计（如 Canal 同步）** |
| 容忍短暂不一致          | **加 TTL 过期兜底**                                 |

------

一句话总结：

> 缓存和数据库的一致性无法做到“实时完美”，只能在“性能与一致性”之间取平衡。
>  最佳实践是：**更新数据库后删除缓存 + TTL + 异步补偿机制**。
