#### ✅ 推荐方案：**先更新数据库，再删除缓存**

这是 Redis 官方文档也推荐的方式。

逻辑：

```
更新数据库 → 删除缓存
```

优点：

- 删除缓存失败的概率比写缓存小得多；
- 即便删除缓存失败，下次写操作仍会刷新。

缺点：

- 如果“删除缓存失败”，会短暂存在脏数据；
- 在极端并发场景中仍可能出现竞态。

------

### 四、竞态问题的进一步解决方案

1. **延迟双删策略**
    更新数据库 → 删除缓存 → 延迟一段时间后再删一次缓存。
    伪代码：

   ```
   updateDB();
   deleteCache();
   Thread.sleep(500);
   deleteCache();
   ```

   延迟时间 > 并发读写峰值延迟，保证旧缓存被覆盖的概率极低。

   这类策略能降低脏数据出现的概率，但不是强一致方案，落地时要重点考虑下面这些问题：

   - **延迟时间难确定**：太短会删不掉并发回填的旧缓存，太长会扩大脏读窗口。
   - **并发写竞争仍然存在**：多线程同时读写同一个 key 时，还是可能出现“旧值回填后又被写操作打掉”的竞态。
   - **第二次删除可能失败**：如果第二删依赖定时任务、异步线程或进程存活，一旦任务丢失就失去补偿效果。
   - **会放大回源压力**：第一次删缓存后，大量读请求会直接打到数据库，热点 key 容易出现瞬时回源峰值。
   - **不适合强一致业务**：库存、余额、订单状态这类场景，不能只靠延迟双删赌时间窗口。
   - **多级缓存更复杂**：如果前面还有本地缓存、网关缓存、CDN，单删 Redis 没法保证整体一致。
   - **事务边界要小心**：如果数据库事务最后回滚了，缓存可能已经被删掉，造成无谓的失效和回源。

   所以它更适合：

   - 读多写少
   - 允许短暂不一致
   - key 热点不极端
   - 有 TTL 兜底

   不太适合：

   - 金融、库存、交易状态
   - 高频写热点 key
   - 要求读后立刻一致的业务

------

2. **异步消息队列（MQ）保证最终一致**
    数据库更新成功后，发送一个“清除缓存”的消息到 MQ，
    Redis 消费者监听并删除对应缓存。
    适用于高并发或异步系统。

   这类方案的核心思路是：**把“删缓存”变成一个可靠的异步补偿动作**，常见的同类实现还有：

   - **事务消息 / Outbox 模式**：先把“需要删缓存”这件事写入本地事务表，再由后台任务或消费者异步处理，避免数据库更新成功但消息没发出去。
   - **Binlog / Canal 同步**：监听数据库变更日志，捕获写入事件后统一发消息或直接删缓存，适合多个服务都要感知同一份数据变更的场景。
   - **重试 + 死信队列**：缓存删除失败后自动重试，重试耗尽后进入死信队列，人工或补偿任务再处理。

   这类方案的优点是：

   - 能把缓存失效逻辑和业务写操作解耦
   - 可重试、可监控、可补偿
   - 适合高并发和跨服务一致性场景

   但要注意：

   - 最终一致不是强一致，仍然会有短暂脏窗口
   - 消息重复投递时，缓存删除必须幂等
   - 消息积压会拖慢一致性收敛速度
   - 消费失败、顺序错乱、重复消费都要提前设计

   适合：

   - 写入后允许短暂不一致
   - 有成熟 MQ、CDC 或任务平台
   - 需要可观测、可追踪、可补偿

   不太适合：

   - 业务链路很短但要求极低延迟
   - 没有可靠消息基础设施
   - 需要严格强一致的场景

   这里要额外注意一个常见误区：

   - **消息重复投递时，缓存删除要幂等**，所以一般是“直接删”，不用先查再删。
   - 但**直接删只解决一致性失效，不解决删完后的回源压力**。

   如果这个 key 是热点 key，删缓存后可能会出现大量请求同时打到数据库，导致缓存击穿甚至把 DB 打穿。
   所以“MQ 删除缓存”通常还要配合下面这些读路径保护：

   - **互斥锁重建**：缓存 miss 时只允许一个线程查数据库并回填，其他线程等待或快速失败。
   - **逻辑过期**：缓存里保留旧值，过期后先返回旧数据，再由后台线程异步重建。
   - **缓存预热**：在发布、更新或大促前提前把热点 key 写回缓存。
   - **限流 / 降级**：回源压力过大时，限制数据库访问，必要时返回兜底数据。

   所以这两类问题要分开看：

   - **幂等删除**解决的是“同一条删除消息来了多次怎么办”
   - **防击穿**解决的是“缓存没了以后，读流量怎么不把数据库打爆”

------

3. **缓存更新加分布式锁**
    当某个 key 正在被更新或删除时，加分布式锁（如 Redis 的 setnx）。
    防止多个线程同时修改导致竞态。
    缺点是实现复杂，性能略低。

------

4. **版本号 / 时间戳校验**
    在缓存值里带上版本号、更新时间戳，写入缓存前先比较新旧版本。
    如果回填的是旧数据，就直接丢弃，避免旧值覆盖新值。

   适用于：

   - 需要防止并发回填覆盖新值
   - 数据本身有明确版本号、更新时间

   代价是：

   - 读写逻辑变复杂
   - 缓存值结构要额外设计

------

5. **逻辑过期 + 后台重建**
    缓存里不直接依赖物理过期时间，而是存一个逻辑过期时间。
    读请求先返回旧值，后台异步线程负责重建缓存。

   优点：

   - 热点 key 不容易把数据库打爆
   - 用户感知更稳定

   缺点：

   - 允许短时间返回旧数据
   - 需要额外的重建线程和锁控制

------

6. **TTL 兜底**
    给缓存设置过期时间（如 5 分钟、10 分钟）。
    即使偶发不一致，也能在过期后恢复正确数据。
    ——这是所有方案的“最后保险丝”。

------

### 五、总结方案选择

| 场景                    | 推荐策略                                            |
| ----------------------- | --------------------------------------------------- |
| 一般系统（中等并发）    | **更新数据库 → 删除缓存**                           |
| 高频读写 + 强一致性要求 | **延迟双删**、**MQ 异步删除**、**Canal/Outbox**     |
| 极端高并发写场景        | **加分布式锁**、**版本号校验**、**逻辑过期**         |
| 容忍短暂不一致          | **加 TTL 过期兜底**                                 |

------

一句话总结：

> 缓存和数据库的一致性无法做到“实时完美”，只能在“性能与一致性”之间取平衡。
>  最佳实践是：**更新数据库后删除缓存 + TTL + 异步补偿机制**。
