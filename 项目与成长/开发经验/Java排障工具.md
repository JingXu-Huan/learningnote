# Java 排障工具：jstack

`jstack` 是 JVM 自带的线程栈导出工具，用来抓取某个 Java 进程在某一时刻的**线程快照**。
它更像“排障取证工具”，不是日常调优工具。

## 它能看到什么

- 线程状态：`RUNNABLE`、`BLOCKED`、`WAITING`、`TIMED_WAITING`
- 当前调用栈：线程卡在哪个方法、哪一层调用
- 锁信息：持有了什么锁、在等什么锁
- 死锁线索：`Found one Java-level deadlock` 之类的直接提示

## 什么时候用

适合用在下面这些场景：

- 接口 RT 突然升高，但 GC 和数据库看起来都正常
- 进程没挂，但请求一直超时、卡死、无响应
- 怀疑线程池耗尽，任务排队但不执行
- 怀疑死锁、锁竞争、外部调用阻塞
- 想确认某个高 CPU 线程到底在跑什么

不太适合单独使用的场景：

- 只想看内存占用，优先看堆 dump、GC 日志、`jstat`
- 只想看实时 CPU 热点，优先用 `top -H`、`async-profiler`、Arthas
- 问题是短暂抖动，单次 dump 很容易误判

## 基本用法

```bash
# 1. 找到 Java 进程
jps -l

# 2. 抓线程栈，通常先保留锁信息
jstack -l <pid> > dump-1.txt

# 3. 隔几秒再抓两次，方便对比线程是否一直卡在同一处
jstack -l <pid> > dump-2.txt
jstack -l <pid> > dump-3.txt
```

## 分析流程

1. 先抓多份线程栈，不要只看一份。
  - 最好间隔 3~5 秒连续抓 3 次，方便判断是瞬时抖动还是持续卡住。
  - 重点对比同一个线程在多份 dump 里的栈是否一致。

2. 先扫全局关键词，快速确认有没有明确结论。
  - `Found one Java-level deadlock`
  - `BLOCKED`
  - `waiting to lock`
  - `parking to wait for`
  - `WAITING`
  - `TIMED_WAITING`

3. 先看线程状态分布，再决定往哪类问题上收敛。
  - `BLOCKED`：优先怀疑锁竞争。
  - `WAITING` / `TIMED_WAITING`：优先怀疑条件等待、队列等待、线程池空闲、`park`、`sleep`。
  - `RUNNABLE`：不一定真在跑 CPU，也可能是死循环、JNI、系统调用或 I/O 阻塞。

4. 重点盯业务线程，不要一上来就看 JVM 后台线程。
  - 常见目标是 `http-nio`、`pool-`、`worker-`、自定义线程名。
  - `GC Thread`、`Finalizer`、`Reference Handler` 这类线程通常先放后面看。

5. 看每个线程栈顶在干什么，先抓“卡点”。
  - `SocketInputStream.socketRead0`：多半在等网络、数据库、远程调用。
  - `Object.wait` / `LockSupport.park`：多半在等通知、队列或同步器。
  - 你自己的业务方法：重点看有没有同步块、慢 SQL、死循环、递归或大批量处理。

6. 结合 `-l` 的锁信息看谁持有锁、谁在等锁。
  - `waiting to lock <...>`：当前线程在等哪把锁。
  - `locked <...>`：当前线程持有哪把锁。
  - `owned by "xxx"`：这把锁被哪个线程持有。
  - 如果多个线程都在等同一把锁，基本就是锁竞争或锁设计问题。

7. 把线程栈和其他观测手段对齐。
  - `top -H -p <pid>`：确认高 CPU 线程。
  - 慢日志 / SQL 日志：确认是不是下游慢。
  - 链路追踪：确认是不是某个外部接口拖慢了整个调用链。

8. 最后回到代码和配置上定位根因。
  - 是否有 `synchronized`、`ReentrantLock`、共享集合或全局缓存。
  - 是否线程池参数不合理，导致任务堆积。
  - 是否下游依赖超时过长、连接池耗尽或重试风暴。

## 一个实用判断顺序

1. 先看有没有死锁提示。
2. 再看是否大量线程卡在同一个锁、同一个方法或同一个外部调用上。
3. 再把可疑线程和 `top -H`、慢日志、链路追踪一起对齐。
4. 最后再决定是改代码、改线程池、改锁设计，还是改下游依赖。

## 最佳实践

- 一次不要只看一份，连续抓 2~3 次更容易区分“瞬时忙碌”和“真正卡死”
- 先结合 `top -H -p <pid>` 或 `ps -L` 找高 CPU 线程，再把线程号转成十六进制，对照 `jstack` 里的 `nid`
- 重点看长期停留在同一方法的线程，尤其是：
  - `BLOCKED`：在等锁
  - `WAITING` / `TIMED_WAITING`：在等通知、队列、条件变量、sleep、park
  - `RUNNABLE` 但栈不变：可能在忙等、死循环、热循环、JNI、系统调用
- 如果输出里直接出现 deadlock 提示，先处理锁顺序问题，再看其他现象
- 生产环境尽量在低峰抓取，避免频繁执行；单次 `jstack` 通常可接受，但别高频轮询
- `-F` 强制模式慎用，只有常规 `jstack` 无法获取时再考虑
