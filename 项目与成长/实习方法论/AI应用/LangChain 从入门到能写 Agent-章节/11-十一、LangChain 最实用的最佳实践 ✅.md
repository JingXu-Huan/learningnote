# 十一、LangChain 最实用的最佳实践 ✅

下面这些不是教条，但非常值得默认遵守。

## 1. 先把模型调用写稳，再接 agent

顺序不要反：

- 先 `llm.invoke(...)`
- 再 `create_agent(...)`

因为如果最基础的模型调用都没稳住，后面 agent 报错时你会完全不知道是哪层问题。

## 2. 每个 tool 只做一件事

不要把一个工具写成：

- 既查 Redis
- 又查天气
- 又生成计划

tool 最好是单一职责。

这样有 3 个好处：

- 模型更容易选对工具
- LangSmith trace 更清晰
- 后面出错更好排查

## 3. tool 的描述要像接口文档，不要像宣传文案

推荐这种风格：

- “根据主题返回学习笔记摘要”
- “根据城市名返回天气信息”

不推荐这种风格：

- “这是一个超级强大的知识助手工具”

模型不需要营销文案，它需要明确边界。

## 4. 默认给结构化字段写 description

这是小投入高回报的实践。

比如：

```python
class QuestionTag(BaseModel):
    topic: str = Field(description="主题，例如 redis、mysql、spring")
```

字段描述越具体，模型越容易稳定输出。

## 5. 先做 fake tool / fake retrieval，再接真实依赖

新手最容易一上来就接：

- 数据库
- 向量库
- 搜索 API

结果一报错，根本不知道是模型问题还是基础设施问题。

更稳的顺序是：

1. 先用字典 / 假函数跑通流程
2. 再换成真实依赖

## 6. 对 agent 的最终输出做“后处理”

不要迷信模型一次返回就完事。

真实项目里通常还要做：

- schema 校验
- 空值兜底
- 字段归一化
- 枚举映射

## 7. 温度和 prompt 先保守配置

新手练手阶段建议：

- `temperature=0` 或较低
- prompt 先短、先明确

理由很简单：

- 稳定性更重要

## 8. 先用 LangSmith 观察，再优化 prompt

很多人一回答不对就开始乱改 prompt。

更好的顺序是：

1. 先看 trace
2. 确认是模型理解错了、工具选错了，还是工具结果差
3. 再决定改哪里

## 9. 不要过早追求“全自动 Agent”

很多业务场景更合理的做法是：

- 先半自动
- 关键结果结构化
- 复杂决策保留人工兜底

这比一上来追求全自动稳定得多。
