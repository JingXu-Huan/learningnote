# 十、LangChain 的核心技术细节，你至少要知道这些 ⚙️

这一节不是让你背源码，而是让你避免“会写 demo，但不知道框架在干什么”。

## 1. LangChain 里的消息不是普通字符串

在聊天模型场景里，框架内部更偏向“消息列表”而不是“一个大 prompt 字符串”。

常见消息类型有：

- `SystemMessage`
- `HumanMessage`
- `AIMessage`
- `ToolMessage`

这意味着什么？

- 系统规则、用户输入、模型回复、工具结果，在框架里是不同角色
- 这比手动拼接字符串更稳定，也更方便做多轮对话

## 2. Tool calling 本质上是一轮“模型决定调用 + 你的代码执行工具 + 再把结果喂回模型”

很多新手以为调用工具就是一次函数执行，实际上至少包含两层：

1. 模型先判断要不要调工具
2. 工具执行后，结果再回到上下文里

所以调试 tool 问题时，不要只看工具本身，也要看：

- tool 描述是否清晰
- tool 参数名是否直观
- 模型是否有足够上下文决定调用它

## 3. 结构化输出依赖 schema，不是依赖“你说得够不够狠”

你如果只是写：

```text
请严格返回 JSON
```

这还是软约束。

而真正更稳定的路线是：

- 用 `Pydantic` / `TypedDict` / JSON schema 定义结构
- 用 `with_structured_output(...)`
- 再用字段描述补充语义

## 4. Agent 返回结果通常不是“最终纯文本”

你打印 `result` 时会发现，它经常包含：

- 最终消息
- 中间步骤
- 工具调用结果

这件事很重要，因为后面接 LangSmith 时，你看到的 trace 本质上也是这些执行单元的展开。

## 5. Short-term memory 和 long-term memory 不是同一个层级的问题

很多人把“带历史消息”就叫 memory，这不够准确。

- short-term memory：当前 thread 的上下文延续
- long-term memory：跨 thread 的事实、偏好、资料

如果你后面学 LangGraph，会发现：

- 这两者的底层落点并不一样

## 6. LangChain 适合做“高层开发入口”，不适合包治百病

它很适合：

- 快速起步
- 组织 agent
- 接工具
- 做结构化输出

但它不替你解决：

- 业务规则设计
- 数据质量问题
- 检索结果质量问题
- 线上容错策略

这也是很多新手最容易误判的地方。
