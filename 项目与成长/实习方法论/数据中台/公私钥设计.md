# 独立 API 服务 RSA 公私钥验签流程设计

## 1. 背景

当你的系统需要作为一个独立 API 服务，供外部用户、第三方系统或企业客户调用时，需要解决几个核心问题：

1. 如何识别调用方是谁；
2. 如何确认请求确实由合法调用方发出；
3. 如何防止请求参数被篡改；
4. 如何防止抓包后重复请求，也就是重放攻击；
5. 如何支持一个 AppId 下多把公钥，方便密钥轮换。

如果采用 RSA 公私钥方案，推荐使用：

```text
AppId + KeyId + RSA 签名 + Timestamp + Nonce
```

其中：

| 字段 | 作用 |
|---|---|
| `AppId` | 标识调用方应用 |
| `KeyId` | 标识当前使用哪一把公钥 |
| `PrivateKey` | 调用方自己保存，用于签名 |
| `PublicKey` | 服务端保存，用于验签 |
| `Timestamp` | 防止旧请求长期有效 |
| `Nonce` | 防止同一个请求被重复提交 |
| `Signature` | 调用方用私钥生成的签名 |

---

## 2. 核心原则

### 2.1 服务端不要保存用户私钥

在 RSA 非对称签名方案中：

```text
客户端保存 privateKey
服务端保存 publicKey
```

客户端用私钥签名，服务端用公钥验签。

服务端不应该接触用户私钥，否则非对称签名的意义就没了。

---

### 2.2 服务端不是根据私钥找公钥

服务端收到请求后，不能也不应该根据用户私钥找公钥。

正确方式是：

```text
根据 AppId + KeyId 找到 publicKey
```

也就是说，服务端保存的是类似下面的映射关系：

```text
app_001 + key_202607 -> publicKey_A
app_001 + key_202608 -> publicKey_B
```

请求进来时，调用方必须告诉服务端自己用的是哪一把密钥。

---

## 3. 为什么需要 KeyId

如果一个用户只有一个 AppId，但是这个 AppId 下面有多把 publicKey，例如：

```text
app_001 -> publicKey_A
app_001 -> publicKey_B
app_001 -> publicKey_C
```

如果请求里只带：

```http
X-App-Id: app_001
X-Signature: xxxxx
```

服务端并不知道应该用哪一把 publicKey 验签，只能轮询：

```text
用 publicKey_A 验签
失败，再用 publicKey_B 验签
失败，再用 publicKey_C 验签
成功，放行
```

这种方案可以实现，但不推荐。

---

## 4. 不推荐轮询 publicKey 的原因

| 问题 | 说明 |
|---|---|
| 性能差 | RSA 验签比 HMAC 更重，多把 key 轮询会浪费 CPU |
| 逻辑不清晰 | 服务端不知道客户端本来想用哪一把 key |
| 不利于密钥轮换 | 新旧 key 并存时不好管理 |
| 不利于审计 | 日志里不好记录具体使用了哪把 key |
| 风险扩大 | 一个 AppId 下挂太多历史 key，会扩大安全边界 |

因此，推荐在请求头中增加：

```http
X-Key-Id: key_202607
```

这样服务端可以通过：

```text
AppId + KeyId
```

精准找到对应的 publicKey，只验签一次。

---

## 5. 推荐请求头设计

推荐所有需要验签的 API 请求都带上以下请求头：

```http
X-App-Id: app_001
X-Key-Id: key_202607
X-Timestamp: 1752033600000
X-Nonce: abc123
X-Body-Sha256: xxxxx
X-Signature: xxxxx
```

字段说明：

| 请求头 | 说明 |
|---|---|
| `X-App-Id` | 调用方应用 ID |
| `X-Key-Id` | 当前使用的密钥 ID |
| `X-Timestamp` | 请求发起时间戳，通常使用毫秒级时间戳 |
| `X-Nonce` | 随机字符串，每次请求唯一 |
| `X-Body-Sha256` | 请求体的 SHA-256 摘要 |
| `X-Signature` | 调用方使用私钥生成的 RSA 签名 |

## 6. 数据库设计

### 6.1 应用表

```sql
CREATE TABLE api_app (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    app_id VARCHAR(64) NOT NULL UNIQUE COMMENT '应用ID',
    app_name VARCHAR(128) NOT NULL COMMENT '应用名称',
    status TINYINT NOT NULL DEFAULT 1 COMMENT '1启用 0禁用',
    create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
    update_time DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

---

### 6.2 应用密钥表

```sql
CREATE TABLE api_app_key (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    app_id VARCHAR(64) NOT NULL COMMENT '应用ID',
    key_id VARCHAR(64) NOT NULL COMMENT '密钥ID',
    public_key TEXT NOT NULL COMMENT 'RSA公钥',
    status TINYINT NOT NULL DEFAULT 1 COMMENT '1启用 0禁用',
    expire_time DATETIME NULL COMMENT '过期时间',
    create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
    update_time DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_app_key (app_id, key_id),
    INDEX idx_app_id (app_id)
);
```

这样一个 AppId 可以绑定多把公钥：

```text
app_001 + key_202601 -> publicKey_A
app_001 + key_202607 -> publicKey_B
app_001 + key_202612 -> publicKey_C
```

## 7. 整体注册流程

### 7.1 调用方生成 RSA 密钥对

调用方在自己的环境中生成：

```text
privateKey
publicKey
```

调用方自己保存 `privateKey`，并把 `publicKey` 提交给你的 API 平台。

---

### 7.2 服务端保存公钥

服务端为调用方创建应用：

```text
AppId = app_001
```

然后保存调用方提交的公钥：

```text
app_001 + key_202607 -> publicKey
```

---

### 7.3 服务端返回 AppId 和 KeyId

服务端可以把下面两个值返回给调用方：

```text
AppId = app_001
KeyId = key_202607
```

调用方后续请求 API 时，需要带上这两个字段。

---

## 8. 客户端签名流程

假设调用方请求接口：

```http
POST /api/order/create?channel=web
```

请求体：

```json
{
  "orderNo": "202607080001",
  "amount": 100
}
```

客户端需要执行以下步骤。

---

### 8.1 生成 timestamp 和 nonce

```text
timestamp = 1752033600000
nonce = abc123
```

---

### 8.2 计算请求体摘要

对请求体原文计算 SHA-256：

```text
bodyHash = SHA256(body)
```

示例：

```text
X-Body-Sha256: 2cf24dba5fb0a30e26e83b2ac5b9e29e...
```

---

### 8.3 构造待签名字符串

推荐将以下内容纳入签名：

```text
HTTP Method
Request Path
Query String
AppId
KeyId
Timestamp
Nonce
BodySha256
```

示例：

```text
POST
/api/order/create
channel=web
app_001
key_202607
1752033600000
abc123
2cf24dba5fb0a30e26e83b2ac5b9e29e...
```

注意：`AppId` 和 `KeyId` 也要参与签名，防止请求头被替换。

---

### 8.4 使用私钥签名

调用方使用自己的 privateKey 对待签名字符串签名：

```text
signature = RSA_SIGN(privateKey, signContent)
```

签名算法推荐：

```text
SHA256withRSA
```

最终请求头：

```http
X-App-Id: app_001
X-Key-Id: key_202607
X-Timestamp: 1752033600000
X-Nonce: abc123
X-Body-Sha256: 2cf24dba5fb0a30e26e83b2ac5b9e29e...
X-Signature: xxxxx
```

---

## 9. 服务端验签流程

服务端收到请求后，按以下流程处理。

```text
1. 读取 X-App-Id
2. 读取 X-Key-Id
3. 读取 X-Timestamp
4. 读取 X-Nonce
5. 读取 X-Body-Sha256
6. 读取 X-Signature
7. 根据 AppId 查询应用是否存在、是否启用
8. 根据 AppId + KeyId 查询 publicKey
9. 校验 key 是否启用、是否过期
10. 校验 timestamp 是否在允许时间窗口内
11. 校验 nonce 是否已使用过
12. 重新计算请求体 SHA-256
13. 对比服务端计算的 bodyHash 和请求头中的 X-Body-Sha256
14. 按相同规则构造待签名字符串
15. 使用 publicKey 验证 signature
16. 验签通过则放行，否则拒绝
```

## 10. 服务端验签伪代码

```java
String appId = request.getHeader("X-App-Id");
String keyId = request.getHeader("X-Key-Id");
String timestamp = request.getHeader("X-Timestamp");
String nonce = request.getHeader("X-Nonce");
String bodySha256 = request.getHeader("X-Body-Sha256");
String signature = request.getHeader("X-Signature");

if (isBlank(appId) || isBlank(keyId) || isBlank(timestamp)
        || isBlank(nonce) || isBlank(bodySha256) || isBlank(signature)) {
    throw new RuntimeException("缺少认证请求头");
}

ApiApp app = apiAppService.getByAppId(appId);

if (app == null || app.getStatus() != 1) {
    throw new RuntimeException("无效的 AppId");
}

ApiAppKey appKey = apiAppKeyService.getByAppIdAndKeyId(appId, keyId);

if (appKey == null || appKey.getStatus() != 1) {
    throw new RuntimeException("无效的 KeyId");
}

if (appKey.getExpireTime() != null && appKey.getExpireTime().before(new Date())) {
    throw new RuntimeException("密钥已过期");
}

long now = System.currentTimeMillis();
long requestTime = Long.parseLong(timestamp);

if (Math.abs(now - requestTime) > 5 * 60 * 1000) {
    throw new RuntimeException("请求已过期");
}

String nonceKey = "api:nonce:" + appId + ":" + keyId + ":" + nonce;
Boolean success = redisTemplate.opsForValue()
        .setIfAbsent(nonceKey, "1", Duration.ofMinutes(5));

if (Boolean.FALSE.equals(success)) {
    throw new RuntimeException("重复请求");
}

String requestBody = getRequestBody(request);
String serverBodySha256 = sha256Hex(requestBody);

if (!constantTimeEquals(serverBodySha256, bodySha256)) {
    throw new RuntimeException("请求体摘要不一致");
}

String signContent = buildSignContent(
        request.getMethod(),
        request.getRequestURI(),
        normalizeQuery(request.getQueryString()),
        appId,
        keyId,
        timestamp,
        nonce,
        bodySha256
);

boolean valid = RsaSignUtil.verify(
        signContent,
        signature,
        appKey.getPublicKey()
);

if (!valid) {
    throw new RuntimeException("签名错误");
}

// 验签通过，继续执行业务逻辑
return true;
```

## 11. 待签名字符串构造规则

签名规则必须严格统一，否则客户端和服务端会算出不同结果。

推荐规则：

```text
1. HTTP Method 转大写，例如 POST、GET
2. Request Path 不包含域名，例如 /api/order/create
3. Query 参数按 key 字典序排序
4. AppId 原样参与签名
5. KeyId 原样参与签名
6. Timestamp 原样参与签名
7. Nonce 原样参与签名
8. BodySha256 原样参与签名
9. 每一段使用 \n 分隔
```

Java 示例：

```java
public static String buildSignContent(
        String method,
        String path,
        String query,
        String appId,
        String keyId,
        String timestamp,
        String nonce,
        String bodySha256
) {
    return method.toUpperCase() + "\n"
            + path + "\n"
            + query + "\n"
            + appId + "\n"
            + keyId + "\n"
            + timestamp + "\n"
            + nonce + "\n"
            + bodySha256;
}
```

---

## 12. Query 参数排序规则

例如原始 query 是：

```text
b=2&a=1
```

签名前必须统一排序为：

```text
a=1&b=2
```

否则客户端签名内容和服务端签名内容可能不一致。

推荐规则：

```text
1. 按参数名 key 字典序升序排序
2. 如果同一个 key 有多个 value，value 也按字典序排序
3. 参数名和值都使用统一的 URL 编码规则
4. 空 query 使用空字符串
```

## 13. 防重放设计

只验签不能防止重放攻击。

攻击者如果抓到了完整请求：

```http
X-App-Id: app_001
X-Key-Id: key_202607
X-Timestamp: 1752033600000
X-Nonce: abc123
X-Signature: xxxxx
```

如果服务端不校验 `timestamp` 和 `nonce`，攻击者可以重复发送这份请求。

---

### 13.1 Timestamp 校验

服务端只允许一定时间窗口内的请求。

例如允许 5 分钟误差：

```text
abs(serverTime - requestTimestamp) <= 5分钟
```

超过时间窗口直接拒绝。

---

### 13.2 Nonce 校验

每次请求的 nonce 必须唯一。

服务端可以用 Redis 存储已经使用过的 nonce：

```text
api:nonce:{appId}:{keyId}:{nonce}
```

设置 5 分钟过期。

如果同一个 nonce 再次出现，说明可能是重复请求，直接拒绝。

---

## 14. 密钥轮换方案

为了方便密钥更换，推荐一个 AppId 支持多把 key。

### 14.1 正常状态

```text
app_001 + key_202607 -> 当前启用 publicKey
```

客户端请求时带：

```http
X-App-Id: app_001
X-Key-Id: key_202607
```

---

### 14.2 轮换状态

新增一把 key：

```text
app_001 + key_202607 -> 旧 publicKey，暂时仍启用
app_001 + key_202608 -> 新 publicKey，启用
```

客户端逐步切换到新 key。

---

### 14.3 下线旧 key

当确认所有客户端都切换完成后：

```text
app_001 + key_202607 -> 禁用
app_001 + key_202608 -> 启用
```

禁用旧 key 后，旧私钥签出来的请求全部拒绝。

---

## 15. 兼容老客户端的轮询兜底

如果老客户端没有传 `X-Key-Id`，服务端可以短期兼容：

```text
如果请求带了 X-Key-Id：
    使用 AppId + KeyId 精准查询 publicKey

如果请求没有 X-Key-Id：
    只尝试该 AppId 下最近的 1 到 2 把启用 key
```

注意：

```text
不要无限轮询所有历史 publicKey
```

建议最多尝试：

```text
1. 当前 key
2. 上一把 key
```

这只能作为过渡方案，不应作为长期设计。

## 16. 错误码设计

推荐统一返回结构：

```json
{
  "code": 401001,
  "message": "Missing authentication headers"
}
```

常见错误码：

| 错误码 | 含义 |
|---|---|
| `401001` | 缺少认证请求头 |
| `401002` | AppId 不存在 |
| `401003` | AppId 已禁用 |
| `401004` | KeyId 不存在 |
| `401005` | KeyId 已禁用 |
| `401006` | 密钥已过期 |
| `401007` | 请求已过期 |
| `401008` | Nonce 重复 |
| `401009` | 请求体摘要不一致 |
| `401010` | 签名错误 |
| `403001` | 没有接口权限 |
| `429001` | 调用频率超限 |

## 17. 最终推荐流程图

```text
调用方生成 RSA 密钥对
        ↓
调用方保存 privateKey
        ↓
调用方把 publicKey 提交给 API 平台
        ↓
服务端生成 AppId 和 KeyId
        ↓
服务端保存 AppId + KeyId + publicKey
        ↓
调用方请求 API
        ↓
调用方构造 timestamp、nonce、bodyHash
        ↓
调用方构造待签名字符串
        ↓
调用方用 privateKey 生成 signature
        ↓
请求头带上 AppId、KeyId、timestamp、nonce、bodyHash、signature
        ↓
服务端根据 AppId 查询应用
        ↓
服务端根据 AppId + KeyId 查询 publicKey
        ↓
服务端校验 timestamp
        ↓
服务端校验 nonce
        ↓
服务端重新计算 bodyHash
        ↓
服务端重新构造待签名字符串
        ↓
服务端用 publicKey 验证 signature
        ↓
验签成功：放行业务接口
验签失败：拒绝请求
```

---

## 18. 一句话总结

如果一个 AppId 下有多把 publicKey，**不要靠轮询验签来找 key**。

推荐设计是：

```text
AppId 识别调用方应用
KeyId 识别具体公钥
PrivateKey 由客户端保存并用于签名
PublicKey 由服务端保存并用于验签
Timestamp + Nonce 防止重放攻击
Signature 保证身份可信和请求未被篡改
```

最终服务端通过：

```text
AppId + KeyId -> PublicKey
```

精准找到公钥，然后完成验签。
