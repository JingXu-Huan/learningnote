# 报表相关 SQL 教程

## 一、报表设计模式：热冷分表

### 核心思想
```
热表（hot）  → 最近数据，频繁查询
冷表（cold） → 历史归档，减少查询压力
```

### 三类统计图表需求中的表设计

| 表名 | 用途 | 特点 |
|------|------|------|
| `ticket_stat_report_batch` | 批次控制表 | 记录统计任务的批次号、触发方式、状态 |
| `ticket_stat_chart_result_hot` | 热结果表 | 当期结果，支持频繁查询 |
| `ticket_stat_chart_result_cold` | 冷结果表 | 历史归档，多了 archive_time 字段 |

### 冷热分表的关键字段

```sql
-- 热表
KEY idx_ticket_stat_hot_query (chart_code, compare_group, object_type, object_id, period_type, period_start_date, bucket_index)

-- 冷表多了归档时间索引
KEY idx_ticket_stat_cold_archive (period_end_date, archive_time)
```

## 二、时间范围查询的 COALESCE 替身（重要！）
> coalesce 表示从左到右依次检查，返回第一个不为 NULL 的值。
### 原始写法（低效）
```sql
WHERE COALESCE(od_filter.ret_feedback_time, ol.update_time)
      BETWEEN '2026-04-27 00:00:00' AND '2026-04-27 23:59:59'
```
**问题**：`COALESCE` 导致索引失效，全表扫描。

### 优化后写法（高效）

```sql
-- 用 UNION ALL 拆分，精准命中索引
-- 情况1：A 不为 NULL，直接用 A 的值查范围
SELECT ol.order_detail_id
FROM order_log AS ol
JOIN order_detail AS od_filter ON od_filter.id = ol.order_detail_id
WHERE od_filter.ret_feedback_time IS NOT NULL
  AND od_filter.ret_feedback_time BETWEEN '2026-04-27 00:00:00' AND '2026-04-27 23:59:59'

UNION ALL

-- 情况2：A 为 NULL，用 B 的值查范围
SELECT ol.order_detail_id
FROM order_log AS ol
JOIN order_detail AS od_filter ON od_filter.id = ol.order_detail_id
WHERE ol.customer_service_id IS NOT NULL
  AND od_filter.ret_feedback_time IS NULL          -- 关键：与情况1互斥
  AND ol.update_time BETWEEN '2026-04-27 00:00:00' AND '2026-04-27 23:59:59'
```

**原理**：`COALESCE(A, B)` 等价于两种互斥情况：

| 情况 | 条件 | 用哪个值 |
| --- | --- | --- |
| 情况1 | A 不为 NULL | 用 A |
| 情况2 | A 为 NULL | 用 B |

拆成两个独立查询后，每个分支都能直接对有值的字段走索引查询范围，不再需要计算函数。

**为什么能命中索引？**

```
情况1：ret_feedback_time IS NOT NULL AND ret_feedback_time BETWEEN ...
      → 直接走 ret_feedback_time 的索引

情况2：ret_feedback_time IS NULL AND update_time BETWEEN ...
      → 直接走 update_time 的索引
```

**一句话总结**：`COALESCE(A, B) IN range` → 拆成 `A IN range UNION A IS NULL AND B IN range`，让每个分支都能独立走索引。

## 五、统计报表索引设计技巧

### 1. 覆盖索引
```sql
-- ticket_info 表，用于按 order_id 聚合 ticket_count
ADD INDEX idx_ti_order_id_ticket_count (`order_id`, `ticket_count`);
-- 顺序很重要：先等值查询字段，再范围/聚合字段
```

### 2. 组合索引顺序原则
```
等值字段 → 范围字段 → 排序字段 → 覆盖字段
```

### 3. 多维度统计索引
```sql
-- 供应商视图
ADD INDEX idx_ol_isdel_supplier_odid_isp_ps
  (`is_delete`, `supplier_info_id`, `order_detail_id`, `is_success`, `processing_status`);

-- 客服视图
ADD INDEX idx_ol_isdel_csid_odid_isp_ps
  (`is_delete`, `customer_service_id`, `order_detail_id`, `is_success`, `processing_status`);
```

## 六、菜单复制的 SQL 模式

### 场景：复制一个页面菜单
```sql
INSERT INTO sys_menu (
  menu_name, parent_id, order_num, path, component, ...
)
SELECT
  '新菜单名',              -- 改 name
  source.parent_id,        -- 同一父级
  source.order_num + 1,    -- 往后排
  'newPath',               -- 新路径
  'new/component',         -- 新组件
  source.`query`,
  ...
FROM sys_menu source
WHERE source.menu_id = xxx  -- 源菜单
  AND NOT EXISTS (          -- 防重复
    SELECT 1 FROM sys_menu target
    WHERE target.parent_id = source.parent_id
      AND target.path = 'newPath'
  );
```

## 七、核心避坑点

| 场景 | 错误写法 | 正确写法 |
|------|----------|----------|
| 时间字段可能为 NULL | `COALESCE(A, B) BETWEEN ...` | 用 UNION ALL 拆分 |
| 子查询嵌套过深 | 多层 FROM (SELECT ...) | 改用 CTE |
| 防重复插入 | 多次 INSERT | 用 NOT EXISTS 判断 |
| 优化前后验证 | 直接上线 | 必须 UNION ALL 比对结果 |

## 八、UNION ALL 与 UNION 的区别

| 特性 | `UNION ALL` | `UNION` |
| --- | --- | --- |
| **去重** | ❌ 不去重，保留所有记录 | ✅ 自动去重，合并相同记录 |
| **性能** | 更快（只做拼接） | 更慢（需要额外比较去重） |
| **结果集** | 行数 = 所有查询行数之和 | 行数 ≤ 所有查询行数之和 |

### 示例

```sql
-- 表A: {1, 2, 3}，表B: {2, 3, 4}

-- UNION ALL：不去重，保留所有行
SELECT id FROM A
UNION ALL
SELECT id FROM B;
-- 结果: {1, 2, 3, 2, 3, 4}  共6行

-- UNION：自动去重
SELECT id FROM A
UNION
SELECT id FROM B;
-- 结果: {1, 2, 3, 4}  共4行
```

### 使用建议

- **确认无重复** 或需要保留所有原始数据 → 用 `UNION ALL`（性能更好）
- 需要自动合并去重 → 用 `UNION`（会有排序开销）

> 💡 在 SQL 优化中（如第四章的校验场景），优先使用 `UNION ALL` 以避免不必要的去重开销。
