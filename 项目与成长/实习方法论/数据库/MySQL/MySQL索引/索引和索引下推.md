# 什么时候索引没有按预期使用？如何理解索引下推？😢

> “索引失效”是方便交流的说法，不是 MySQL 的正式状态。更准确的问题是：优化器选择了什么访问路径、哪些列用于确定扫描范围、哪些条件在索引层过滤、最终读取了多少行。

------

## 一、先分清四个容易混淆的概念

假设 InnoDB 有二级索引 `(a, b, c)`：

| 概念 | 回答的问题 | EXPLAIN 线索 |
| --- | --- | --- |
| 索引访问范围 | 从 B+ 树哪一段开始、扫到哪里 | `type`、`key`、`key_len` |
| ICP 索引条件下推 | 扫描索引项时，能否先过滤再回表 | `Extra: Using index condition` |
| 覆盖索引 | 查询需要的列是否都在索引中 | `Extra: Using index` |
| 回表 | 二级索引找到主键后，是否还要读聚簇索引整行 | 执行计划与实际读取行数 |

“某列没有用于缩小扫描范围”不等于“该列完全没用”。它可能参与 ICP，也可能在 Server 层执行 `Using where`。

## 二、B+ 树索引不容易直接定位的写法

### 2.1 前导通配符

```sql
SELECT * FROM user WHERE name LIKE '%旭';
```

B+ 树按字符串前缀排序，`%旭` 没有确定的起点，通常不能用普通索引做高效范围定位。优化器可能全表扫描；如果查询只需索引中的列，也可能选择扫描整个覆盖索引，所以不能简单说“一定不用索引”。

```sql
SELECT * FROM user WHERE name LIKE '景%';
```

固定前缀通常可以形成索引范围。大量任意位置文本搜索应评估全文索引或专门搜索引擎，而不是给所有 `%keyword%` 强加普通索引。

### 2.2 对索引列做函数或计算

```sql
SELECT * FROM user WHERE YEAR(create_time) = 2025;
SELECT * FROM user WHERE age + 1 = 20;
```

普通索引保存原始列值，以上表达式通常不能直接形成原值范围。优先改写：

```sql
SELECT *
FROM user
WHERE create_time >= '2025-01-01'
  AND create_time <  '2026-01-01';
```

MySQL 8 也支持函数索引，或通过生成列建立索引：

```sql
CREATE INDEX idx_create_year ON user ((YEAR(create_time)));
```

函数索引会增加写入、空间和维护成本，应确认查询稳定且选择性合适。

### 2.3 隐式类型转换

```sql
-- phone 是 VARCHAR，却传入数字字面量
SELECT * FROM user WHERE phone = 13800000000;
```

字符串列与数字比较时，MySQL 可能按数值规则转换列值，导致无法按字符串索引有序查找，还可能出现 `'00123'` 与 `123` 等语义问题。正确做法是让参数类型与列类型一致：

```sql
SELECT * FROM user WHERE phone = '13800000000';
```

预编译参数也要使用正确的 JDBC 类型。排查时同时检查字符集、排序规则和跨列比较，不能只看 SQL 文本有没有引号。

### 2.4 选择性太低

```sql
SELECT * FROM user WHERE status = 1;
```

即使 `status` 有索引，如果大部分行都是 `1`，走二级索引后大量回表可能比顺序扫描更贵。优化器选择全表扫描属于成本决策，不是索引结构坏了。

必要时更新统计信息并检查数据分布：

```sql
ANALYZE TABLE user;
```

不要一看到全表扫描就 `FORCE INDEX`。先验证估算与实际行数，再判断统计信息、索引设计或 SQL 是否需要调整。

## 三、OR 不等于一定全表扫描

```sql
SELECT * FROM user
WHERE phone = '13800000000'
   OR email = 'jingxu@example.com';
```

可能出现：

- 两列都有合适索引，优化器使用 `index_merge` 合并结果；
- 只选一个索引，再过滤另一条件；
- 判断合并代价过高，选择全表扫描；
- 改写 `UNION ALL/UNION` 后分别走索引。

所以 `OR` 的结论必须看执行计划和数据分布。拆成 `UNION ALL` 前还要确认两个分支是否可能返回同一行；需要去重时使用 `UNION` 会产生额外成本。

## 四、复合索引：最左前缀只描述“有序定位能力”

对于索引 `(a, b, c)`：

| 条件 | 常见访问方式 |
| --- | --- |
| `a = 1` | 用 `a` 定位范围 |
| `a = 1 AND b = 2` | 用 `(a,b)` 定位更小范围 |
| `a = 1 AND b = 2 AND c = 3` | 三列都可参与定位 |
| `b = 2` | 通常无法直接使用普通最左前缀定位；仍由优化器决定其他扫描策略 |
| `a = 1 AND c = 3` | `a` 定位范围，`c` 可能参与 ICP |
| `a = 1 AND b > 5 AND c = 10` | `(a,b)` 常用于范围，`c` 可能参与 ICP |

### 为什么范围列后的列不能继续缩小连续区间

在 `(a,b,c)` 中，满足 `a=1 AND b>5` 的索引项覆盖许多不同 `b` 值。每个 `b` 下的 `c` 才有序，不能把所有 `c=10` 合成一段连续区间。因此 `c` 通常不能继续缩小 B+ 树扫描边界，但可以在扫描每个索引项时提前过滤——这正是 ICP 的典型价值。

索引顺序要综合考虑：

- 高频等值条件；
- 范围条件；
- `ORDER BY/GROUP BY`；
- 选择性与数据分布；
- 是否能覆盖查询；
- 写入成本和索引数量。

“选择性最高的列永远放第一”也不是绝对规则。

## 五、索引下推 ICP 到底做了什么

无 ICP 时，InnoDB 使用二级索引的大致流程：

```text
读取二级索引项
  -> 取得主键
  -> 回聚簇索引读取整行
  -> Server 层判断其余 WHERE 条件
```

有 ICP 时：

```text
读取二级索引项
  -> 先用索引中已有列判断可下推条件
     -> 不满足：跳过，不回表
     -> 满足：取得主键并回表
  -> Server 层判断剩余条件
```

ICP 的收益是**减少不必要的完整行读取和 Server/存储引擎交互**，并不减少所有索引项扫描。

### 典型例子

索引：

```sql
CREATE INDEX idx_zip_last_first
    ON people(zipcode, lastname, firstname);
```

查询：

```sql
SELECT *
FROM people
WHERE zipcode = '45000'
  AND lastname LIKE '%xu%'
  AND address LIKE '%文华路%';
```

- `zipcode = '45000'` 用于定位索引范围；
- `lastname` 在索引中，虽然前导 `%` 不能缩小范围，但可在索引项上用 ICP 过滤；
- `address` 不在索引中，只能回表后判断。

执行计划出现：

```text
Using index condition
```

表示使用了 ICP。

## 六、什么时候通常不会使用 ICP

根据 MySQL 8.4 的适用条件，重点包括：

1. 访问类型不是 `range`、`ref`、`eq_ref`、`ref_or_null`；
2. 查询不需要读取完整行，例如已经是覆盖索引；
3. InnoDB 使用聚簇主键索引，完整记录本来就已读取；
4. 可过滤条件依赖非索引列；
5. 条件含不能下推的存储函数或子查询；
6. 使用虚拟生成列上的二级索引等不支持场景；
7. `optimizer_switch` 关闭了 `index_condition_pushdown`。

```sql
SET optimizer_switch = 'index_condition_pushdown=off';
SET optimizer_switch = 'index_condition_pushdown=on';
```

`OR`、范围条件或“跳过复合索引中间列”本身不代表 ICP 必然关闭。只要某部分条件能用当前索引项计算，优化器就可能下推；是否采用仍以当前版本和执行计划为准。

## 七、覆盖索引与 ICP 的区别

```sql
SELECT zipcode, lastname
FROM people
WHERE zipcode = '45000'
  AND lastname LIKE '%xu%';
```

如果 `(zipcode, lastname, firstname)` 已覆盖查询需要的列，InnoDB 不必回表，`Extra` 常显示 `Using index`。此时 ICP 以“减少回表”为目标就没有必要。

```text
Using index            = 覆盖索引，不需要读取完整表行
Using index condition  = 使用 ICP，通常仍需为通过条件的记录回表
Using where            = 还有条件需要过滤，不等于一定性能差
```

三个词不要望文生义地混为“用了索引”。

## 八、可执行的对照实验

### 8.1 建表

```sql
DROP TABLE IF EXISTS people;

CREATE TABLE people (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    zipcode VARCHAR(10) NOT NULL,
    lastname VARCHAR(64) NOT NULL,
    firstname VARCHAR(64) NOT NULL,
    address VARCHAR(255) NOT NULL,
    age INT NOT NULL,
    phone VARCHAR(20) NOT NULL,
    create_time DATETIME NOT NULL,
    INDEX idx_zip_last_first (zipcode, lastname, firstname),
    INDEX idx_phone (phone),
    INDEX idx_create_time (create_time)
) ENGINE = InnoDB;
```

测试表太小时，优化器很可能直接全表扫描。准备至少数万条、不同邮编和姓氏分布的数据，再执行：

```sql
ANALYZE TABLE people;
```

### 8.2 观察固定前缀与前导通配符

```sql
EXPLAIN ANALYZE
SELECT * FROM people WHERE lastname LIKE 'Xu%';

EXPLAIN ANALYZE
SELECT * FROM people WHERE lastname LIKE '%xu%';
```

注意：`lastname` 不是复合索引首列，单独查询时还会受到最左前缀影响。再加上首列对照：

```sql
EXPLAIN
SELECT *
FROM people
WHERE zipcode = '45000'
  AND lastname LIKE '%xu%';
```

### 8.3 对比 ICP 开关

```sql
SET optimizer_switch = 'index_condition_pushdown=off';

EXPLAIN ANALYZE
SELECT *
FROM people
WHERE zipcode = '45000'
  AND lastname LIKE '%xu%'
  AND address LIKE '%文华路%';

SET optimizer_switch = 'index_condition_pushdown=on';

EXPLAIN ANALYZE
SELECT *
FROM people
WHERE zipcode = '45000'
  AND lastname LIKE '%xu%'
  AND address LIKE '%文华路%';
```

比较实际读取行数和执行时间。首次执行、缓存预热和数据分布会影响结果，应多次测试，不能只截一张计划图下结论。

### 8.4 对比函数与范围改写

```sql
EXPLAIN ANALYZE
SELECT * FROM people WHERE YEAR(create_time) = 2025;

EXPLAIN ANALYZE
SELECT *
FROM people
WHERE create_time >= '2025-01-01'
  AND create_time <  '2026-01-01';
```

### 8.5 对比隐式转换

```sql
EXPLAIN ANALYZE
SELECT * FROM people WHERE phone = 13800000000;

EXPLAIN ANALYZE
SELECT * FROM people WHERE phone = '13800000000';
```

## 九、EXPLAIN 应该看什么

```sql
EXPLAIN FORMAT=TREE
SELECT ...;

EXPLAIN ANALYZE
SELECT ...;
```

| 字段/信息 | 重点 |
| --- | --- |
| `type` | 表访问方式，不是越靠某个固定顺序就一定越快 |
| `possible_keys` | 理论候选，不代表实际选择 |
| `key` | 实际选择的索引 |
| `key_len` | 用于访问的索引键长度线索，不等于 WHERE 中所有索引列都参与定位 |
| `rows` | 优化器估算扫描行数 |
| `filtered` | 估算通过条件比例 |
| `Extra` | ICP、覆盖、排序、临时表等提示 |
| `actual time/rows/loops` | `EXPLAIN ANALYZE` 的真实执行反馈 |

优化时尤其关注“估算 rows 与实际 rows 差多少”。偏差很大时，可能需要更新统计信息、检查数据倾斜或调整索引，而不是直接加 Hint。

> `EXPLAIN ANALYZE` 会真正执行语句。对大查询以及 `UPDATE/DELETE` 等修改语句要格外谨慎，先在测试环境和只读查询上使用。

## 十、推荐排查流程

1. 写清查询需要返回多少行、可接受延迟和调用频率；
2. 用慢日志或调用链确认真正的慢 SQL；
3. 检查列类型、参数类型、函数、前导 `%` 和 OR；
4. 查看 `EXPLAIN` 的访问路径、索引与估算行数；
5. 在安全环境用 `EXPLAIN ANALYZE` 对比实际行数；
6. 判断问题是扫描范围大、回表多、排序/临时表，还是锁与 IO；
7. 再选择改 SQL、改索引、更新统计信息或调整数据模型；
8. 用真实数据量回归写入成本和其他查询，避免只优化一条 SQL。

## 十一、面试速记

**问：范围条件后面的索引列一定完全失效吗？**

答：不一定。它通常不能继续缩小连续索引范围，但如果列在当前索引中，可能通过 ICP 提前过滤。

**问：OR 一定导致全表扫描吗？**

答：不一定，可能使用单索引、Index Merge、UNION 改写或全表扫描，由成本模型与数据分布决定。

**问：ICP 能减少扫描的索引项吗？**

答：它主要减少不满足条件记录的回表次数；用于定位范围的条件才决定主要扫描区间。

**问：`Using index` 和 `Using index condition` 有什么区别？**

答：前者通常表示覆盖索引，后者表示 ICP，后者往往仍需要对通过条件的记录回表。
