# 6. JSONB 操作（重点特性）

PostgreSQL 的 `JSONB` 是它相比 MySQL 的核心优势之一。

## 基本操作

```sql
-- 插入 JSONB 数据
INSERT INTO users (profile) VALUES ('{"name": "Tom", "age": 25, "skills": ["Java", "SQL"]}');

-- 查询 JSONB 字段
SELECT profile->>'name' AS name FROM users;         -- 取文本值（->>）
SELECT profile->'age' AS age FROM users;             -- 取 JSON 值（->）
SELECT profile->'skills'->>0 AS first_skill FROM users;  -- 数组元素
```

## 操作符详解

假设 `data` 列的值为：

```json
{"name": "Tom", "age": 25, "address": {"city": "Beijing", "zip": "100000"}, "skills": ["Java", "SQL"]}
```

### 第一组：取值操作符（`->` vs `->>`）

> 核心区别：`->` 返回的还是 JSON 类型（带引号），`->>` 返回的是纯文本（TEXT）。

```sql
-- -> 返回 JSON 类型（结果带引号，不能直接和字符串比较）
SELECT data->'name';          -- 结果: "Tom"  （JSON 类型）

-- ->> 返回 TEXT 类型（结果不带引号，可以直接用 = 比较）
SELECT data->>'name';         -- 结果: Tom    （TEXT 类型）

-- 实际开发中，WHERE 条件里几乎都用 ->>，因为要和普通值比较
SELECT * FROM users WHERE data->>'name' = 'Tom';   -- ✅ 正确
SELECT * FROM users WHERE data->'name' = 'Tom';     -- ❌ 类型不匹配
```

### 第二组：按路径取值（`#>` vs `#>>`）

> 当要访问嵌套很深的字段时，用 `#>` / `#>>` 比连续写 `->` 更清晰。路径用花括号 `{}` 包裹，逗号分隔。

```sql
-- 嵌套取值：获取 address.city
-- 方式一：连续用 ->
SELECT data->'address'->>'city';             -- 结果: Beijing

-- 方式二：用 #>> 按路径取值（更简洁）
SELECT data#>>'{address,city}';              -- 结果: Beijing

-- #> 返回 JSON，#>> 返回 TEXT（和 -> / ->> 的区别一样）
SELECT data#>'{address,city}';               -- 结果: "Beijing"  （JSON 类型）
SELECT data#>>'{address,city}';              -- 结果: Beijing    （TEXT 类型）

-- 访问数组元素（下标从 0 开始）
SELECT data#>>'{skills,0}';                  -- 结果: Java
```

### 第三组：包含判断（`@>` 和 `<@`）

> 用来判断一个 JSONB 是否"包含"另一个 JSONB。**这是最常用的查询操作符，因为它能走 GIN 索引。**

```sql
-- @>：左边的 JSONB 是否包含右边的 JSONB
-- 含义：data 里面有没有 name=Tom 且 age=25？
SELECT * FROM users
WHERE data @> '{"name": "Tom", "age": 25}'::jsonb;   -- ✅ 匹配

-- 只要部分字段匹配也行
SELECT * FROM users
WHERE data @> '{"name": "Tom"}'::jsonb;              -- ✅ 匹配

-- 甚至能匹配嵌套结构
SELECT * FROM users
WHERE data @> '{"address": {"city": "Beijing"}}'::jsonb;  -- ✅ 匹配

-- <@：方向反过来，右边是否包含左边（很少用）
SELECT '{"name":"Tom"}'::jsonb <@ data FROM users;   -- 等价于 data @> '{"name":"Tom"}'
```

> **性能提示**：`@>` 配合 GIN 索引速度极快，是 JSONB 查询的首选方式。`->>` 取值虽然直观，但无法利用 GIN 索引（需要单独建表达式索引）。

### 第四组：键存在性判断（`?`、`?|`、`?&`）

> 只检查 key 是否存在，不关心 value 是什么。

```sql
-- ?：是否存在某个 key
SELECT * FROM users WHERE data ? 'name';           -- ✅ 有 name 字段就匹配

-- ?|：是否存在其中任意一个 key（传入数组）
SELECT * FROM users WHERE data ?| array['name', 'phone'];  -- 有 name 或 phone 就匹配

-- ?&：是否同时存在所有 key（传入数组）
SELECT * FROM users WHERE data ?& array['name', 'age'];    -- 必须同时有 name 和 age
```

> **注意**：这些操作符只检查顶层 key，不会深入嵌套对象。例如 `data ? 'city'` 不会匹配到 `address` 里面的 `city`。

### 操作符速查表

| 操作符 | 一句话说明 | 返回类型 | 能走 GIN 索引 |
|--------|-----------|----------|:------------:|
| `->` | 取字段，返回 JSON | JSON | ❌ |
| `->>` | 取字段，返回文本 | TEXT | ❌ |
| `#>` | 按路径取嵌套值，返回 JSON | JSON | ❌ |
| `#>>` | 按路径取嵌套值，返回文本 | TEXT | ❌ |
| `@>` | 左边是否包含右边 | BOOL | ✅ |
| `<@` | 右边是否包含左边 | BOOL | ✅ |
| `?` | 顶层是否有这个 key | BOOL | ✅ |
| `?\|` | 顶层是否有任一 key | BOOL | ✅ |
| `?&` | 顶层是否同时有所有 key | BOOL | ✅ |

## JSONB 更新

```sql
-- 更新字段
UPDATE users SET profile = jsonb_set(profile, '{age}', '26') WHERE id = 1;

-- 合并（追加/覆盖）
UPDATE users SET profile = profile || '{"city": "Beijing"}'::jsonb WHERE id = 1;

-- 删除字段
UPDATE users SET profile = profile - 'city' WHERE id = 1;

-- 删除嵌套字段
UPDATE users SET profile = profile #- '{address,zip}' WHERE id = 1;
```

## JSONB 索引

```sql
-- GIN 索引（加速 @>、?、?|、?& 查询）
CREATE INDEX idx_users_profile ON users USING GIN (profile);

-- 针对特定字段的 B-tree 索引
CREATE INDEX idx_users_name ON users ((profile->>'name'));
```
