# 3. 选择建议

| 场景                 | 推荐方案                 |
| ------------------ | -------------------- |
| 单一 Java 应用         | ShardingSphere-JDBC  |
| Java 微服务，各服务独立管理数据 | ShardingSphere-JDBC  |
| 多语言系统              | ShardingSphere-Proxy |
| 需要统一数据库入口          | ShardingSphere-Proxy |
| 对链路延迟非常敏感          | 优先评估 JDBC            |
| DBA 统一运维和治理        | 优先评估 Proxy           |

ShardingSphere 官方也支持 JDBC、Proxy 独立部署或组合使用。

# 十九、生产环境必须关注的连接数问题

使用 ShardingSphere-JDBC 时，每个应用实例通常都会维护到底层各数据源的连接池。

假设：

```text
应用实例：20 个
底层数据源：8 个
每个连接池最大连接数：20
```

理论最大连接数可能达到：

```text
20 × 8 × 20 = 3200
```

这并不代表所有连接都会同时建立，但必须进行容量评估。

建议：

* 不要直接复制单库时期的连接池大小；
* 分别监控每个真实数据源的活跃连接；
* 根据单实例并发量设置连接池；
* 设置合理的连接超时；
* 避免应用实例数和数据源数量同时无限增长；
* 评估数据库最大连接数和故障切换容量。

ShardingSphere-JDBC 与应用共享进程和资源，官方也提示应关注应用内存配置及 SQL 解析缓存带来的堆内存消耗。

# 二十、跨分片关联查询怎么处理

以下查询可能涉及多个分片：

```sql
SELECT o.order_id,
       o.total_amount,
       u.username
FROM t_order o
JOIN t_user u ON o.user_id = u.user_id
WHERE o.order_id = #{orderId};
```

如果用户表和订单表位于不同数据库中，传统数据库无法直接完成本地关联。

处理方式按推荐程度排序：

## 方案一：应用层分别查询

```text
查询订单
    ↓
获取 user_id
    ↓
调用用户服务或查询用户库
    ↓
应用层组装结果
```

## 方案二：数据冗余

在订单表中冗余下单时的用户名称、手机号快照等字段。

订单本身通常需要保存业务快照，即使用户以后修改信息，也不应改变历史订单展示。

## 方案三：缓存或搜索系统

将用于检索和展示的数据同步到：

* Redis；
* Elasticsearch；
* ClickHouse；
* 数据仓库。

## 方案四：SQL Federation

ShardingSphere 可以通过 Federation 执行引擎处理部分跨数据库关联和复杂子查询，但官方文档仍将部分相关场景列为实验性支持，并指出仍需要优化。

因此，核心交易链路不要过度依赖跨库 Federation 查询。
