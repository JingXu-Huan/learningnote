# 一、分库分表到底解决什么问题

分库分表主要解决两个维度的问题。

## 1. 数据存储容量问题

假设订单表每年新增 5 亿条数据，即使单条数据不大，表数据和索引也会迅速膨胀。

将一张订单表拆分成 16 张物理表后，每张表只保存其中一部分数据，可以降低：

* 单表数据量；
* 单表索引大小；
* 索引维护成本；
* 单次查询需要扫描的数据范围。

## 2. 数据库吞吐量问题

只分表、不分库时，所有物理表仍然位于同一个数据库实例中。

虽然单表查询可能变快，但数据库实例的以下资源并没有增加：

* CPU；
* 内存；
* 磁盘 I/O；
* 网络带宽；
* 最大连接数；
* 写入能力。

因此：

* **分表主要降低单表压力；**
* **分库才能真正分散数据库实例的计算和存储压力。**

## 3. 分库分表不能解决的问题

分库分表无法自动修复以下问题：

* SQL 没有合适的索引；
* 一次查询返回几十万条数据；
* 大量长事务；
* 热点账户或热点商品；
* 不合理的表结构；
* 业务代码频繁进行跨表、跨库查询；
* 数据库连接池配置错误；
* 缓存设计不合理。

因此，实施分库分表之前，应先完成：

1. 慢 SQL 分析；
2. 索引优化；
3. SQL 和表结构优化；
4. 缓存与异步化改造；
5. 读写分离评估；
6. 数据归档和冷热分离评估。

**分库分表应该是容量和吞吐量达到单实例边界之后的架构选择，而不是所有项目的默认配置。**
