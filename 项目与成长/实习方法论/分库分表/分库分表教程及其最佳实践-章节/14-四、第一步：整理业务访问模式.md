# 四、第一步：整理业务访问模式

设计之前，应先列出核心 SQL。

以订单业务为例：

| 场景        | 查询条件                   | 频率 |
| --------- | ---------------------- | -: |
| 用户查询订单列表  | `user_id`、时间范围         | 很高 |
| 查询订单详情    | `user_id`、`order_id`   | 很高 |
| 商户查询订单    | `merchant_id`、时间范围     |  高 |
| 根据订单号查询   | `order_id`             |  高 |
| 按状态扫描超时订单 | `status`、`create_time` |  中 |
| 财务按日期统计   | `create_time`          |  中 |
| 客服模糊搜索订单  | 手机号、订单号                |  低 |

不可能用一个分片键同时优化所有查询。

因此，需要确定：

1. 哪些查询是核心在线链路；
2. 哪些查询允许多分片执行；
3. 哪些查询应该进入 Elasticsearch、ClickHouse 或数仓；
4. 哪些查询应该建立独立的映射表；
5. 哪些查询可以通过缓存解决。

例如，客服根据手机号搜索订单，可以先查询用户服务获得 `user_id`，再使用 `user_id` 查询订单，而不是直接扫描所有订单分片。
