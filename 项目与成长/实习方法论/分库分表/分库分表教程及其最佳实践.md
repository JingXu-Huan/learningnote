# 从设计到落地：如何做好分库分表——结合 Apache ShardingSphere 实战

在业务早期，单库单表通常是最简单、最可靠的数据库架构。但随着订单、流水、消息、日志等数据持续增长，单个数据库实例可能逐渐面临以下问题：

* 单表数据量过大，索引层级增加，查询性能下降；
* 数据库磁盘容量逐渐接近上限；
* 写入请求集中在单实例，CPU、I/O 和锁竞争加剧；
* 数据库连接数成为瓶颈；
* 单实例扩容成本越来越高。

这时，系统往往需要通过**分库分表**将数据和请求分散到多个数据库节点。

不过，分库分表并不是简单地“多建几个库、多建几张表”。真正困难的是：

1. 数据应该按照什么字段拆分？
2. 如何保证数据分布均匀？
3. 查询没有携带分片键时怎么办？
4. 跨库关联、分页、事务如何处理？
5. 以后需要扩容时，数据如何迁移？
6. 应用程序如何透明地访问多个数据库？

本文将从基础概念开始，讲清楚分库分表的设计方法，并使用 **Apache ShardingSphere-JDBC 5.5.3** 完成一个“2 库 × 4 表”的订单分片案例。ShardingSphere-JDBC 是运行在 Java JDBC 层的轻量级框架；ShardingSphere 还提供可独立部署、兼容数据库协议的 ShardingSphere-Proxy。

---

## 一、分库分表到底解决什么问题

分库分表主要解决两个维度的问题。

### 1. 数据存储容量问题

假设订单表每年新增 5 亿条数据，即使单条数据不大，表数据和索引也会迅速膨胀。

将一张订单表拆分成 16 张物理表后，每张表只保存其中一部分数据，可以降低：

* 单表数据量；
* 单表索引大小；
* 索引维护成本；
* 单次查询需要扫描的数据范围。

### 2. 数据库吞吐量问题

只分表、不分库时，所有物理表仍然位于同一个数据库实例中。

虽然单表查询可能变快，但数据库实例的以下资源并没有增加：

* CPU；
* 内存；
* 磁盘 I/O；
* 网络带宽；
* 最大连接数；
* 写入能力。

因此：

* **分表主要降低单表压力；**
* **分库才能真正分散数据库实例的计算和存储压力。**

### 3. 分库分表不能解决的问题

分库分表无法自动修复以下问题：

* SQL 没有合适的索引；
* 一次查询返回几十万条数据；
* 大量长事务；
* 热点账户或热点商品；
* 不合理的表结构；
* 业务代码频繁进行跨表、跨库查询；
* 数据库连接池配置错误；
* 缓存设计不合理。

因此，实施分库分表之前，应先完成：

1. 慢 SQL 分析；
2. 索引优化；
3. SQL 和表结构优化；
4. 缓存与异步化改造；
5. 读写分离评估；
6. 数据归档和冷热分离评估。

**分库分表应该是容量和吞吐量达到单实例边界之后的架构选择，而不是所有项目的默认配置。**

## 二、分库分表的基础概念

## 1. 垂直分库

垂直分库是按照业务领域拆分数据库。

例如将一个大型业务库拆分为：

```text
用户库
├── t_user
├── t_user_address
└── t_user_profile

订单库
├── t_order
├── t_order_item
└── t_order_log

商品库
├── t_product
├── t_category
└── t_inventory
```

垂直分库的核心目标是：

* 降低不同业务之间的耦合；
* 隔离不同业务的数据库压力；
* 明确数据归属；
* 降低单库表数量。

垂直分库之后，原来的本地事务和关联查询可能变成跨库操作，因此需要重新设计业务边界。

---

## 2. 垂直分表

垂直分表是将一张字段很多的表，按照字段使用频率拆成多张表。

例如：

```text
t_user
├── user_id
├── username
├── phone
└── status

t_user_detail
├── user_id
├── avatar
├── introduction
├── preference_json
└── extension_json
```

高频使用的核心字段放在主表，低频或大字段放在扩展表。

垂直分表通常用于：

* 减少单行数据长度；
* 提高缓存页利用率；
* 避免查询核心字段时读取大字段；
* 分离冷热字段。

---

## 3. 水平分表

水平分表是把一张逻辑表中的不同行，拆分到多张结构相同的物理表。

例如：

```text
逻辑表：t_order

物理表：
t_order_0
t_order_1
t_order_2
t_order_3
```

根据订单编号进行取模：

```text
order_id % 4
```

那么：

```text
order_id = 10001 → t_order_1
order_id = 10002 → t_order_2
order_id = 10003 → t_order_3
order_id = 10004 → t_order_0
```

应用程序操作的是逻辑表 `t_order`，分片中间件负责将 SQL 路由到真实表。

---

## 4. 水平分库

水平分库是将同一业务的数据拆分到多个数据库实例。

例如：

```text
ds_0
└── 部分用户的订单

ds_1
└── 另一部分用户的订单
```

按照用户编号分库：

```text
user_id % 2
```

那么：

```text
user_id = 1001 → ds_1
user_id = 1002 → ds_0
```

水平分库可以分散：

* 写入压力；
* 查询压力；
* 数据库存储；
* 数据库连接；
* CPU 和磁盘 I/O。

---

## 5. 逻辑表和真实表

在分片系统中，业务代码使用的表称为**逻辑表**。

例如：

```sql
SELECT *
FROM t_order
WHERE user_id = 1001
  AND order_id = 90001;
```

这里的 `t_order` 是逻辑表。

数据库中真正存在的可能是：

```text
ds_0.t_order_0
ds_0.t_order_1
ds_0.t_order_2
ds_0.t_order_3

ds_1.t_order_0
ds_1.t_order_1
ds_1.t_order_2
ds_1.t_order_3
```

这些表称为真实表或物理表。

---

## 6. 数据节点

一个数据节点表示一个具体的数据源和物理表组合。

例如：

```text
ds_1.t_order_2
```

如果系统采用 2 个数据库、每个数据库 4 张订单表，那么一共有 8 个数据节点。

在 ShardingSphere 中，可以使用行表达式描述这些节点：

```yaml
actualDataNodes: ds_${0..1}.t_order_${0..3}
```

ShardingSphere 的 YAML 分片规则支持逻辑表、真实数据节点、分库策略、分表策略、绑定表、主键生成器和分片算法等配置。

---

## 7. 分片键

分片键是决定数据存储位置的字段。

常见的分片键包括：

* `user_id`；
* `order_id`；
* `tenant_id`；
* `merchant_id`；
* `device_id`；
* `create_time`。

例如：

```text
按照 user_id 分库
按照 order_id 分表
```

在这种设计中，`user_id` 是分库键，`order_id` 是分表键。

分片键是整个分库分表设计中最重要的决策。一旦选错，后期可能出现大量全路由查询、跨库事务和数据迁移问题。

---

## 8. 分片算法

分片算法根据分片键计算目标数据库或目标表。

常见算法包括：

### 取模分片

```text
user_id % 4
```

优点：

* 实现简单；
* 数据通常比较均匀；
* 点查询路由效率高。

缺点：

* 增加分片数量时，通常需要重新分布大量数据；
* 不适合范围查询。

### 范围分片

```text
1 ～ 100 万       → shard_0
100 万 ～ 200 万  → shard_1
200 万 ～ 300 万  → shard_2
```

优点：

* 范围查询友好；
* 扩容时可以追加新的范围。

缺点：

* 新数据可能集中写入最后一个分片；
* 容易出现热点。

### 时间分片

```text
t_order_202601
t_order_202602
t_order_202603
```

适合日志、流水、历史记录等按照时间查询和归档的数据。

缺点是当前月份或当前日期的表容易成为写入热点。

### 哈希分片

先对分片键进行哈希，再根据哈希值确定分片。

适合字符串类型的分片键，例如：

```text
tenant_code
device_no
username
```

ShardingSphere 内置了 `MOD`、`HASH_MOD`、`INLINE`、`INTERVAL`、`AUTO_INTERVAL`、范围分片及复合分片等算法，也允许通过 SPI 或 `CLASS_BASED` 方式实现自定义算法。

---

## 9. 绑定表

订单表和订单明细表通常具有相同的分片规则：

```text
t_order
t_order_item
```

两张表都按照 `user_id` 分库、按照 `order_id` 分表。

此时可以将它们配置为绑定表：

```yaml
bindingTables:
  - t_order,t_order_item
```

绑定表的意义是告诉 ShardingSphere：

> 这两张表的数据具有相同的分布关系，关联查询时应访问对应的物理表。

例如：

```text
t_order_0      对应 t_order_item_0
t_order_1      对应 t_order_item_1
```

这样可以减少关联查询产生笛卡尔路由的风险。官方分片规则同样提供了 `bindingTables` 配置。

---

## 10. 广播表

字典表、地区表、状态配置表等数据量较小，但可能被所有分片表关联查询。

这类表可以在每个数据库中保存一份，称为广播表。

例如：

```text
ds_0.t_region
ds_1.t_region
```

配置如下：

```yaml
- !BROADCAST
  tables:
    - t_region
```

对广播表执行查询时，可以从本地数据库读取；执行修改时，中间件需要将操作发送到所有数据源。ShardingSphere 在 YAML 规则中使用 `!BROADCAST` 声明广播表。

---

## 三、设计分库分表的正确顺序

很多分库分表项目失败，是因为先确定了“分几张表”，然后才开始考虑业务查询。

正确顺序应该是：

```text
业务访问模式
    ↓
选择分片键
    ↓
确定分片算法
    ↓
计算分片数量
    ↓
设计主键和事务
    ↓
验证 SQL 路由
    ↓
设计迁移、扩容和回滚方案
```

---

## 四、第一步：整理业务访问模式

设计之前，应先列出核心 SQL。

以订单业务为例：

| 场景        | 查询条件                   | 频率 |
| --------- | ---------------------- | -: |
| 用户查询订单列表  | `user_id`、时间范围         | 很高 |
| 查询订单详情    | `user_id`、`order_id`   | 很高 |
| 商户查询订单    | `merchant_id`、时间范围     |  高 |
| 根据订单号查询   | `order_id`             |  高 |
| 按状态扫描超时订单 | `status`、`create_time` |  中 |
| 财务按日期统计   | `create_time`          |  中 |
| 客服模糊搜索订单  | 手机号、订单号                |  低 |

不可能用一个分片键同时优化所有查询。

因此，需要确定：

1. 哪些查询是核心在线链路；
2. 哪些查询允许多分片执行；
3. 哪些查询应该进入 Elasticsearch、ClickHouse 或数仓；
4. 哪些查询应该建立独立的映射表；
5. 哪些查询可以通过缓存解决。

例如，客服根据手机号搜索订单，可以先查询用户服务获得 `user_id`，再使用 `user_id` 查询订单，而不是直接扫描所有订单分片。

---

## 五、第二步：选择合适的分片键

一个较好的分片键通常具备以下特征。

### 1. 查询覆盖率高

核心 SQL 应尽可能携带分片键。

如果 90% 的订单查询都携带 `user_id`，那么 `user_id` 通常比 `create_time` 更适合作为分库键。

### 2. 数据分布均匀

以下字段容易造成数据倾斜：

* 国家；
* 城市；
* 订单状态；
* 用户等级；
* 商品类别；
* 布尔状态。

例如按照订单状态分片：

```text
待支付订单：5%
已支付订单：80%
已取消订单：15%
```

不同分片的数据量会严重不均匀。

### 3. 字段尽量不可变

修改普通字段只需要执行一次 `UPDATE`。

修改分片键可能意味着：

1. 从原分片删除数据；
2. 将数据写入新分片；
3. 同步关联表；
4. 处理并发修改；
5. 保证事务一致性。

因此，应将分片键视为业务数据的定位属性，原则上不允许修改。

### 4. 能够降低跨库操作

属于同一个业务聚合的数据，应尽量位于同一个数据库分片。

例如：

```text
订单
订单明细
订单支付记录
订单操作记录
```

可以统一按照 `user_id` 或订单所属用户进行分库，使订单创建、明细写入和状态修改尽可能在单库事务中完成。

---

## 六、一个容易忽略的取模陷阱

假设系统有 2 个库，每个库 4 张表，设计如下：

```text
数据库：user_id % 2
数据表：user_id % 4
```

看起来一共有 8 个数据节点，但实际上：

```text
user_id % 4 = 0 → user_id % 2 一定等于 0
user_id % 4 = 1 → user_id % 2 一定等于 1
user_id % 4 = 2 → user_id % 2 一定等于 0
user_id % 4 = 3 → user_id % 2 一定等于 1
```

因此只有以下节点会被使用：

```text
ds_0.t_order_0
ds_0.t_order_2
ds_1.t_order_1
ds_1.t_order_3
```

另外 4 个节点永远没有数据。

这就是分库算法和分表算法之间的**相关性问题**。

可选解决方式包括：

* 分库、分表使用不同的字段；
* 先计算统一的逻辑分片编号，再映射到库和表；
* 使用自定义分片算法；
* 引入虚拟分片槽，物理节点只负责承载若干槽位。

本文示例采用：

```text
user_id  分库
order_id 分表
```

这样可以避免简单取模产生的数据节点空置问题。

---

## 七、第三步：确定分片数量

不要根据“网上说单表不能超过 500 万”来决定表数量。

不同表的数据宽度、索引数量、查询模式和硬件差异很大，不能使用统一阈值。

可以从三个维度估算。

### 1. 数据容量

假设：

```text
预计三年订单量：24 亿条
期望每张物理表：不超过 1 亿条
```

那么至少需要：

```text
24 亿 ÷ 1 亿 = 24 张表
```

考虑增长余量，可以设计为 32 张表。

### 2. 写入吞吐量

假设高峰写入量为 4 万 TPS，一个数据库实例在目标延迟和稳定性要求下可以承担 1 万 TPS，那么至少需要：

```text
4 万 ÷ 1 万 = 4 个数据库实例
```

还应考虑：

* 主从复制开销；
* SQL 复杂度；
* 索引数量；
* 数据库故障后的降级容量；
* 未来业务增长。

### 3. 运维成本

分片越多，并不代表性能一定越好。

分片数量增加会同时增加：

* 数据库连接数；
* DDL 发布成本；
* 数据迁移成本；
* 全路由查询成本；
* 监控复杂度；
* 故障排查难度；
* 数据校验成本。

应在容量、吞吐量和运维复杂度之间取得平衡。

---

## 八、第四步：设计全局唯一主键

分库之后，不能继续依赖单个 MySQL 实例的自增主键生成全局唯一 ID。

常见方案包括：

* UUID；
* 数据库号段；
* Redis 自增；
* Snowflake；
* Leaf 等号段服务；
* 自研 ID 服务。

ShardingSphere 内置了主键生成算法，官方示例支持通过 `keyGenerateStrategies` 配置逻辑表、主键列和生成器，并可使用 `SNOWFLAKE` 生成器。

使用 Snowflake 时需要注意：

* 机器标识不能冲突；
* 系统时间不能随意回拨；
* ID 虽然整体趋势递增，但不等于严格连续；
* 不要让业务依赖 ID 连续性；
* ID 字段通常使用 `BIGINT`。

---

## 九、第五步：尽量避免跨库事务

分库之前：

```text
订单、订单明细、库存扣减
```

可能位于同一个数据库事务中。

分库之后，它们可能分布在不同数据库中，本地事务将变成分布式事务。

ShardingSphere 提供基于 XA 和 BASE 模式的分布式事务能力。

但是，能够使用分布式事务，不代表所有业务都应该使用分布式事务。

推荐优先级通常是：

```text
单库本地事务
    ↓
本地事务 + 事务消息 / Outbox
    ↓
Saga 或业务补偿
    ↓
TCC
    ↓
XA 强一致事务
```

在订单场景中，可以采用：

1. 本地事务创建订单；
2. 同一事务写入事件表；
3. 后台任务或 CDC 发布订单事件；
4. 库存服务消费事件并扣减库存；
5. 失败后进行重试或补偿。

这样可以将一个大型跨库事务拆成多个可恢复的本地事务。

# 十、使用 ShardingSphere-JDBC 实现 2 库 × 4 表

下面实现一个订单分片案例。

## 1. 分片结构

数据库：

```text
demo_order_0
demo_order_1
```

每个数据库包含：

```text
t_order_0
t_order_1
t_order_2
t_order_3

t_order_item_0
t_order_item_1
t_order_item_2
t_order_item_3

t_region
```

分片规则：

```text
按照 user_id % 2 分库
按照 order_id % 4 分表
```

查询特点：

| 查询条件                 | 路由范围           |
| -------------------- | -------------- |
| `user_id + order_id` | 1 个数据库、1 张表    |
| 只有 `user_id`         | 1 个数据库、4 张表    |
| 只有 `order_id`        | 2 个数据库、每库 1 张表 |
| 两个分片键都没有             | 2 个数据库、共 8 张表  |

因此，订单详情接口最好同时传入：

```text
user_id
order_id
```

不要只根据 `order_id` 查询。

---

## 2. 创建物理表

在两个数据库中分别创建 4 张订单表。

```sql
CREATE TABLE t_order_0 (
    order_id     BIGINT       NOT NULL,
    user_id      BIGINT       NOT NULL,
    merchant_id  BIGINT       NOT NULL,
    order_status VARCHAR(32)   NOT NULL,
    total_amount DECIMAL(18,2) NOT NULL,
    create_time  DATETIME      NOT NULL,
    update_time  DATETIME      NOT NULL,
    PRIMARY KEY (order_id),
    KEY idx_user_time (user_id, create_time),
    KEY idx_merchant_time (merchant_id, create_time)
) ENGINE = InnoDB;

CREATE TABLE t_order_item_0 (
    item_id      BIGINT        NOT NULL,
    order_id     BIGINT        NOT NULL,
    user_id      BIGINT        NOT NULL,
    product_id   BIGINT        NOT NULL,
    product_name VARCHAR(128)   NOT NULL,
    quantity     INT           NOT NULL,
    sale_price   DECIMAL(18,2) NOT NULL,
    create_time  DATETIME      NOT NULL,
    PRIMARY KEY (item_id),
    KEY idx_order_id (order_id),
    KEY idx_user_order (user_id, order_id)
) ENGINE = InnoDB;
```

将表名后缀分别修改为 `_1`、`_2`、`_3`，创建其他物理表。

生产环境中应通过数据库变更平台统一执行 DDL，避免某个分片漏建字段或索引。

## 5. 编写 sharding.yaml

在 `src/main/resources` 下创建 `sharding.yaml`：

```yaml
databaseName: order_db

dataSources:
  ds_0:
    dataSourceClassName: com.zaxxer.hikari.HikariDataSource
    driverClassName: com.mysql.cj.jdbc.Driver
    jdbcUrl: jdbc:mysql://127.0.0.1:3306/demo_order_0?useSSL=false&serverTimezone=Asia/Shanghai&characterEncoding=UTF-8
    username: root
    password: root

  ds_1:
    dataSourceClassName: com.zaxxer.hikari.HikariDataSource
    driverClassName: com.mysql.cj.jdbc.Driver
    jdbcUrl: jdbc:mysql://127.0.0.1:3306/demo_order_1?useSSL=false&serverTimezone=Asia/Shanghai&characterEncoding=UTF-8
    username: root
    password: root

rules:
  - !SHARDING
    tables:
      t_order:
        actualDataNodes: ds_${0..1}.t_order_${0..3}
        databaseStrategy:
          standard:
            shardingColumn: user_id
            shardingAlgorithmName: order_database_inline
        tableStrategy:
          standard:
            shardingColumn: order_id
            shardingAlgorithmName: order_table_inline

      t_order_item:
        actualDataNodes: ds_${0..1}.t_order_item_${0..3}
        databaseStrategy:
          standard:
            shardingColumn: user_id
            shardingAlgorithmName: order_database_inline
        tableStrategy:
          standard:
            shardingColumn: order_id
            shardingAlgorithmName: order_item_table_inline

    bindingTables:
      - t_order,t_order_item

    keyGenerateStrategies:
      order_id_strategy:
        keyGenerateType: column
        keyGeneratorName: snowflake
        logicTable: t_order
        keyGenerateColumn: order_id

      order_item_id_strategy:
        keyGenerateType: column
        keyGeneratorName: snowflake
        logicTable: t_order_item
        keyGenerateColumn: item_id

    shardingAlgorithms:
      order_database_inline:
        type: INLINE
        props:
          algorithm-expression: ds_${user_id % 2}

      order_table_inline:
        type: INLINE
        props:
          algorithm-expression: t_order_${order_id % 4}

      order_item_table_inline:
        type: INLINE
        props:
          algorithm-expression: t_order_item_${order_id % 4}

    keyGenerators:
      snowflake:
        type: SNOWFLAKE

  - !BROADCAST
    tables:
      - t_region

props:
  sql-show: true
```

官方 YAML 规则中，`actualDataNodes` 用于定义真实节点，`databaseStrategy` 和 `tableStrategy` 分别定义分库与分表策略，`shardingAlgorithms` 声明算法，`keyGenerateStrategies` 和 `keyGenerators` 负责主键生成。

`sql-show: true` 会输出真实路由 SQL，适合开发和测试环境。生产环境中通常应关闭，避免：

* 输出大量日志；
* 暴露 SQL 参数；
* 增加日志存储压力；
* 影响问题排查效率。

## 十一、分析一次完整的 SQL 路由

假设执行：

```sql
SELECT *
FROM t_order
WHERE user_id = 101
  AND order_id = 10008;
```

### 1. 分库计算

```text
101 % 2 = 1
```

目标数据库：

```text
ds_1
```

### 2. 分表计算

```text
10008 % 4 = 0
```

目标表：

```text
t_order_0
```

### 3. 真实 SQL

逻辑 SQL：

```sql
SELECT *
FROM t_order
WHERE user_id = 101
  AND order_id = 10008;
```

经过解析、路由和改写后，发送到数据库的真实 SQL类似于：

```sql
SELECT *
FROM t_order_0
WHERE user_id = 101
  AND order_id = 10008;
```

执行节点：

```text
ds_1.t_order_0
```

ShardingSphere 的分片执行过程主要包括 SQL 解析、路由、改写、执行和结果归并。

---

## 十二、没有分片键会发生什么

执行以下 SQL：

```sql
SELECT *
FROM t_order
WHERE order_status = 'PAID';
```

SQL 中既没有 `user_id`，也没有 `order_id`。

ShardingSphere 无法计算目标数据库和目标表，只能访问所有可能的数据节点：

```text
ds_0.t_order_0
ds_0.t_order_1
ds_0.t_order_2
ds_0.t_order_3
ds_1.t_order_0
ds_1.t_order_1
ds_1.t_order_2
ds_1.t_order_3
```

然后将结果归并。

这种操作称为：

* 全路由；
* 广播路由；
* 全分片扫描。

全路由不一定完全禁止，但必须控制：

* 执行频率；
* 返回数据量；
* 分片数量；
* 排序和聚合复杂度；
* 是否位于核心在线链路。

对于“扫描所有待支付订单并关闭超时订单”一类任务，可以考虑：

* 按照分片并行执行；
* 维护独立的延迟任务；
* 写入消息队列或延迟队列；
* 建立任务索引表；
* 使用调度系统逐个处理分片。

---

## 十三、不要对分片键进行函数计算

假设 `create_time` 是分片键，以下写法可能导致无法提取分片值：

```sql
SELECT *
FROM t_order
WHERE DATE(create_time) = '2026-07-17';
```

更好的写法是：

```sql
SELECT *
FROM t_order
WHERE create_time >= '2026-07-17 00:00:00'
  AND create_time <  '2026-07-18 00:00:00';
```

官方限制说明指出，当分片键被放入函数或运算表达式时，路由引擎可能无法提取其值，从而产生全路由。

---

## 十四、INLINE 算法的范围查询问题

ShardingSphere 的 `INLINE` 算法适合简单的单分片键 `=` 和 `IN` 路由。

例如：

```sql
SELECT *
FROM t_order
WHERE order_id = 10008;
```

或者：

```sql
SELECT *
FROM t_order
WHERE order_id IN (10008, 10009);
```

但是以下范围查询无法通过简单取模直接确定有限表范围：

```sql
SELECT *
FROM t_order
WHERE order_id BETWEEN 10000 AND 20000;
```

官方文档说明，INLINE 算法默认不允许范围查询；即使开启范围查询支持，也会忽略 INLINE 分片策略并进行全路由。

因此，如果核心业务大量依赖时间或 ID 范围查询，应考虑：

* 时间分片；
* 范围分片；
* 自定义分片算法；
* 将范围查询转移到搜索或分析系统。

## 十五、正确编写业务 SQL

### 1. 查询订单详情

推荐：

```sql
SELECT *
FROM t_order
WHERE user_id = #{userId}
  AND order_id = #{orderId};
```

不推荐：

```sql
SELECT *
FROM t_order
WHERE order_id = #{orderId};
```

前者可以路由到一个数据库和一张表；后者需要访问两个数据库。

---

### 2. 更新订单

推荐：

```sql
UPDATE t_order
SET order_status = #{status},
    update_time = NOW()
WHERE user_id = #{userId}
  AND order_id = #{orderId};
```

更新和删除 SQL 必须尽可能携带完整分片键。

尤其不要执行：

```sql
UPDATE t_order
SET order_status = 'CLOSED'
WHERE order_status = 'UNPAID';
```

这种 SQL 可能被发送到所有订单分片。

---

### 3. 查询用户订单列表

```sql
SELECT order_id,
       user_id,
       order_status,
       total_amount,
       create_time
FROM t_order
WHERE user_id = #{userId}
  AND create_time < #{lastCreateTime}
ORDER BY create_time DESC, order_id DESC
LIMIT 20;
```

由于携带了 `user_id`，查询只访问一个数据库。

因为没有携带 `order_id`，该数据库中的 4 张订单表都可能被访问，并进行排序归并。

---

## 十六、慎用深分页

下面的查询在分片环境中成本很高：

```sql
SELECT *
FROM t_order
WHERE user_id = #{userId}
ORDER BY create_time DESC
LIMIT 100000, 20;
```

每个相关分片可能需要读取大量数据，ShardingSphere 再进行归并和截取。

推荐使用游标式分页：

```sql
SELECT *
FROM t_order
WHERE user_id = #{userId}
  AND (
      create_time < #{lastCreateTime}
      OR (
          create_time = #{lastCreateTime}
          AND order_id < #{lastOrderId}
      )
  )
ORDER BY create_time DESC, order_id DESC
LIMIT 20;
```

这种方式也称为：

* Seek Pagination；
* Keyset Pagination；
* 游标分页。

它通常比大偏移量分页更适合高并发订单列表。

---

## 十七、批量写入应该按分片分组

假设一次批量写入 1000 个订单：

```java
orderMapper.batchInsert(orders);
```

如果这些订单分布在不同数据库和表中，中间件必须拆分 SQL，并发送到多个数据节点。

更可控的方式是先按照目标分片进行分组：

```java
Map<ShardKey, List<Order>> groupedOrders =
        orders.stream()
                .collect(Collectors.groupingBy(order -> {
                    int databaseIndex = Math.floorMod(order.getUserId(), 2);
                    int tableIndex = Math.floorMod(order.getOrderId(), 4);
                    return new ShardKey(databaseIndex, tableIndex);
                }));
```

然后按照分组分别批量写入。

这样可以：

* 降低单次 SQL 路由复杂度；
* 控制每批大小；
* 减少跨节点事务；
* 更容易进行失败重试；
* 提高批量执行效率。

但业务代码中的分片算法必须与中间件配置保持一致。更加稳妥的做法是将批处理分组逻辑封装在统一的数据访问组件中，避免算法散落在业务代码里。

# 十八、ShardingSphere-JDBC 和 Proxy 怎么选

## 1. ShardingSphere-JDBC

特点：

* 以 JAR 依赖方式集成；
* 应用直接连接底层数据库；
* 不需要独立部署代理服务；
* 适合 Java、MyBatis、JPA、Hibernate 等技术栈；
* 数据库连接池位于应用进程中。

适合：

* 纯 Java 技术栈；
* 追求较低访问链路开销；
* 应用团队能够维护分片配置；
* 不希望增加独立代理层。

## 2. ShardingSphere-Proxy

特点：

* 作为独立数据库代理部署；
* 对应用提供 MySQL、PostgreSQL、openGauss 等数据库协议入口；
* 适合多语言接入；
* 对 DBA 和统一运维更友好；
* 应用不直接感知底层数据库节点。

官方将 ShardingSphere-Proxy 定位为透明数据库代理，适用于异构语言和独立运维场景。

适合：

* Java、Go、Python、Node.js 等多语言共同访问；
* 希望统一数据库入口；
* 希望独立管理分片配置；
* DBA 需要统一治理底层数据库；
* 应用不适合引入 ShardingSphere-JDBC。

## 3. 选择建议

| 场景                 | 推荐方案                 |
| ------------------ | -------------------- |
| 单一 Java 应用         | ShardingSphere-JDBC  |
| Java 微服务，各服务独立管理数据 | ShardingSphere-JDBC  |
| 多语言系统              | ShardingSphere-Proxy |
| 需要统一数据库入口          | ShardingSphere-Proxy |
| 对链路延迟非常敏感          | 优先评估 JDBC            |
| DBA 统一运维和治理        | 优先评估 Proxy           |

ShardingSphere 官方也支持 JDBC、Proxy 独立部署或组合使用。

---

# 十九、生产环境必须关注的连接数问题

使用 ShardingSphere-JDBC 时，每个应用实例通常都会维护到底层各数据源的连接池。

假设：

```text
应用实例：20 个
底层数据源：8 个
每个连接池最大连接数：20
```

理论最大连接数可能达到：

```text
20 × 8 × 20 = 3200
```

这并不代表所有连接都会同时建立，但必须进行容量评估。

建议：

* 不要直接复制单库时期的连接池大小；
* 分别监控每个真实数据源的活跃连接；
* 根据单实例并发量设置连接池；
* 设置合理的连接超时；
* 避免应用实例数和数据源数量同时无限增长；
* 评估数据库最大连接数和故障切换容量。

ShardingSphere-JDBC 与应用共享进程和资源，官方也提示应关注应用内存配置及 SQL 解析缓存带来的堆内存消耗。

# 二十、跨分片关联查询怎么处理

以下查询可能涉及多个分片：

```sql
SELECT o.order_id,
       o.total_amount,
       u.username
FROM t_order o
JOIN t_user u ON o.user_id = u.user_id
WHERE o.order_id = #{orderId};
```

如果用户表和订单表位于不同数据库中，传统数据库无法直接完成本地关联。

处理方式按推荐程度排序：

### 方案一：应用层分别查询

```text
查询订单
    ↓
获取 user_id
    ↓
调用用户服务或查询用户库
    ↓
应用层组装结果
```

### 方案二：数据冗余

在订单表中冗余下单时的用户名称、手机号快照等字段。

订单本身通常需要保存业务快照，即使用户以后修改信息，也不应改变历史订单展示。

### 方案三：缓存或搜索系统

将用于检索和展示的数据同步到：

* Redis；
* Elasticsearch；
* ClickHouse；
* 数据仓库。

### 方案四：SQL Federation

ShardingSphere 可以通过 Federation 执行引擎处理部分跨数据库关联和复杂子查询，但官方文档仍将部分相关场景列为实验性支持，并指出仍需要优化。

因此，核心交易链路不要过度依赖跨库 Federation 查询。

# 二十一、上线分库分表的迁移步骤

已有系统不能直接停机后一次性切换。一个相对稳妥的迁移过程如下。

## 第一阶段：建立新分片结构

* 创建目标数据库；
* 创建所有物理表；
* 创建索引；
* 部署 ShardingSphere 配置；
* 验证分片路由；
* 完成容量和压力测试。

## 第二阶段：迁移历史数据

按照分片规则读取旧表数据：

```text
旧库数据
    ↓
计算目标分片
    ↓
写入新库新表
```

迁移程序必须支持：

* 分页读取；
* 限速；
* 断点续传；
* 重试；
* 幂等；
* 数据校验；
* 错误记录。

## 第三阶段：同步增量数据

可以采用：

* 双写；
* Binlog CDC；
* Canal；
* Debezium；
* ShardingSphere 数据迁移能力；
* 消息队列同步。

双写代码容易产生不一致，生产环境通常更适合使用可靠的变更日志或 CDC。

## 第四阶段：数据校验

至少校验：

* 总行数；
* 主键数量；
* 金额汇总；
* 状态分布；
* 时间范围；
* 抽样记录；
* 分片分布；
* 重复数据；
* 空字段比例。

重要业务不能只比较总行数。

## 第五阶段：灰度切读

逐步将查询流量切换到新分片：

```text
1%
    ↓
10%
    ↓
30%
    ↓
50%
    ↓
100%
```

同时比较：

* 查询结果；
* 错误率；
* P95、P99 延迟；
* 数据库连接数；
* 慢 SQL；
* CPU 和磁盘 I/O；
* 全路由 SQL 数量。

## 第六阶段：切换写入

写入切换前必须准备：

* 回滚开关；
* 旧库同步机制；
* 数据补偿程序；
* 异常订单核对流程；
* 新旧库差异检查工具。

# 二十二、扩容为什么比第一次分片更难

假设原来使用：

```text
order_id % 4
```

后来扩容为：

```text
order_id % 8
```

大量数据的目标表会发生变化。

例如：

```text
10005 % 4 = 1
10005 % 8 = 5
```

原来位于 `t_order_1`，扩容后应位于 `t_order_5`。

这意味着不能只增加 4 张新表，还必须重新迁移旧数据。

因此，第一次设计时就要考虑未来扩容。

常见方案包括：

### 1. 预留足够的逻辑分片

初期创建较多逻辑表，但将多个逻辑表放在同一物理实例中。

未来扩容时，将部分逻辑表迁移到新实例，而不改变表级路由算法。

### 2. 虚拟槽位

先计算固定数量的虚拟槽：

```text
slot = hash(sharding_key) % 1024
```

再维护：

```text
slot → 数据库节点
```

扩容时只迁移部分槽位。

### 3. 一致性哈希

适用于动态节点，但实现、数据均衡和故障恢复更加复杂。

### 4. 通过迁移工具重新分片

在新旧规则之间完成：

* 全量迁移；
* 增量同步；
* 数据校验；
* 流量切换。

无论采用哪种方案，都要在第一次分片时保留扩容路径。

# 二十三、常见错误总结

## 错误一：业务量不大就提前分片

结果是：

* 开发复杂度增加；
* SQL 调试困难；
* 测试成本增加；
* 运维成本增加；
* 数据迁移和统计更加困难。

## 错误二：只考虑数据量，不考虑查询方式

表虽然拆开了，但大部分查询没有分片键，导致每条 SQL 都扫描全部分片。

## 错误三：分库、分表使用相关的取模算法

例如同时使用：

```text
user_id % 2
user_id % 4
```

可能导致部分数据节点永远没有数据。

## 错误四：允许修改分片键

修改分片键本质上是跨分片迁移，不应该被当成普通 `UPDATE`。

## 错误五：在核心业务中大量跨库 JOIN

中间件可以提供一定支持，但跨库 JOIN 通常意味着：

* 更多网络传输；
* 更多内存归并；
* 更复杂的执行计划；
* 更难预测的性能。

## 错误六：滥用分布式事务

如果每次创建订单都跨多个数据库执行 XA 事务，系统吞吐量和可用性可能明显下降。

## 错误七：认为加分片就能解决热点

某个头部商户占据 50% 流量时，即使按照 `merchant_id` 分成 100 个库，该商户仍然只会落在一个分片中。

热点问题需要额外采用：

* 二级分片；
* 热点拆分；
* 缓存；
* 异步削峰；
* 写入聚合；
* 热点账户专属分片。

## 错误八：开发环境只测试逻辑结果

必须同时检查真实路由 SQL。

同样返回正确结果的两条 SQL，可能分别访问：

```text
1 个数据节点
```

和：

```text
全部 128 个数据节点
```

功能结果一样，性能完全不同。

# 总结

做好分库分表，关键不在于配置多少数据库和多少张表，而在于以下几点：

1. **先分析访问模式，再选择分片键。**
2. **让核心 SQL 尽可能携带完整分片键。**
3. **保证分片均匀，同时处理热点数据。**
4. **相关业务表尽量落在同一数据库分片。**
5. **谨慎使用跨库 JOIN 和分布式事务。**
6. **提前设计全局 ID、数据迁移和扩容方案。**
7. **不仅测试查询结果，还要检查真实路由范围。**
8. **建立分片级监控、对账和故障恢复能力。**

ShardingSphere 可以帮助应用完成 SQL 解析、路由、改写、执行和结果归并，也可以提供绑定表、广播表、分布式事务和多种内置分片算法。

但是，中间件只能执行已经确定的分片规则。

**真正决定分库分表项目成败的，仍然是业务访问模式、分片键设计、数据模型和长期扩容方案。**
