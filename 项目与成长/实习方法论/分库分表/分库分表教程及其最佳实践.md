# 从设计到落地：如何做好分库分表——结合 Apache ShardingSphere 实战

在业务早期，单库单表通常是最简单、最可靠的数据库架构。但随着订单、流水、消息、日志等数据持续增长，单个数据库实例可能逐渐面临以下问题：

* 单表数据量过大，索引层级增加，查询性能下降；
* 数据库磁盘容量逐渐接近上限；
* 写入请求集中在单实例，CPU、I/O 和锁竞争加剧；
* 数据库连接数成为瓶颈；
* 单实例扩容成本越来越高。

这时，系统往往需要通过**分库分表**将数据和请求分散到多个数据库节点。

不过，分库分表并不是简单地“多建几个库、多建几张表”。真正困难的是：

1. 数据应该按照什么字段拆分？
2. 如何保证数据分布均匀？
3. 查询没有携带分片键时怎么办？
4. 跨库关联、分页、事务如何处理？
5. 以后需要扩容时，数据如何迁移？
6. 应用程序如何透明地访问多个数据库？

本文将从基础概念开始，讲清楚分库分表的设计方法，并使用 **Apache ShardingSphere-JDBC 5.5.3** 完成一个“2 库 × 4 表”的订单分片案例。ShardingSphere-JDBC 是运行在 Java JDBC 层的轻量级框架；ShardingSphere 还提供可独立部署、兼容数据库协议的 ShardingSphere-Proxy。
