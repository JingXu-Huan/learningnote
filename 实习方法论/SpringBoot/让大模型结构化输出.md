截至 `2026-07-07`，如果你是结合 **LangChain v1** 做结构化输出，最重要的结论先放前面：

1. 不要再把“请返回 JSON”当成主方案。
2. 能用 **provider 原生结构化输出**，就别退回纯提示词。
3. 在 LangChain 里，优先用：
   - 单模型调用：`with_structured_output(...)`
   - Agent 最终结果：`create_agent(..., response_format=...)`
4. 提示词现在更多是补充字段语义，不是主要约束手段。
5. 结构化输出之后，后端仍然要做校验、归一化、业务匹配。

---

**一、LangChain 最近的变化，真正重要的是这几条**

如果你以前看过老教程，最容易被误导的地方是：

- 老文章喜欢讲 `OutputParser`
- 喜欢教你“写一个 JSON 提示词模板”
- 喜欢把“能 parse 成 JSON”当成成功

但 LangChain v1 的官方方向已经明显变了。

核心变化：

1. `create_agent` 的结构化输出已经并入主循环，不再靠额外补一轮 LLM 调用。
2. 现在主推两种策略：
   - `ProviderStrategy`：走模型厂商原生结构化输出
   - `ToolStrategy`：走工具调用式结构化输出
3. LangChain v1 迁移文档明确说了：
   - **prompted output 已不再作为 `response_format` 的主路线**
   - 原因很直接：**不够可靠**

这意味着：

**现在聊“让大模型结构化输出”，重点已经不是怎么雕提示词，而是怎么选对约束层。**

---

**二、你在 LangChain 里到底该怎么选**

别一上来就堆各种 parser。先按场景选：

1. 如果你只是“输入一段文本/一张图，抽字段出来”

优先用：

```python
llm.with_structured_output(Schema)
```

这是最适合“抽取”“分类”“识别结果结构化”的写法。

2. 如果你是 Agent，要先查工具、再做推理、最后给前端一个结构化结果

优先用：

```python
create_agent(..., response_format=Schema)
```

LangChain 会根据模型能力自动选策略：

- 支持原生结构化输出的模型，优先走 `ProviderStrategy`
- 不支持时，回退到 `ToolStrategy`

3. 只有在这两条都不适用时，才考虑老式 `OutputParser`

它不是不能用，而是：

- 稳定性弱
- 容易因为模型多说一句话就炸
- 对线上识别、抽取类业务不够稳

一句实战建议：

**2026 年再新写 LangChain 结构化抽取，默认起手不该是 OutputParser，而该是 schema + structured output。**

---

**三、LangChain 里最实用的两个写法**

**1. 单模型抽取：`with_structured_output`**

适合：

- 简历抽取
- OCR 识别结果结构化
- 合同字段抽取
- 小票/火车票信息抽取

```python
from pydantic import BaseModel, Field
from langchain_openai import ChatOpenAI


class TicketSchema(BaseModel):
    train_no: str | None = Field(description="车次，例如 G3360")
    departure_date: str | None = Field(description="开车日期，格式 yyyy-MM-dd")
    departure_time: str | None = Field(description="开车时间，格式 HH:mm")
    departure_station: str | None = Field(description="出发站")
    arrival_station: str | None = Field(description="到达站")
    passenger_name: str | None = Field(description="乘客姓名")
    masked_id_no: str | None = Field(description="脱敏证件号")
    seat_type: str | None = Field(description="席别")
    carriage_no: str | None = Field(description="车厢号")
    seat_no: str | None = Field(description="座位号")
    fare_amount: float | None = Field(description="票面金额，数值类型")
    e_ticket_no: str | None = Field(description="电子票号")
    recognition_status: str = Field(description="SUCCESS 或 FAILED")
    message: str | None = Field(description="失败或不确定时的说明")


llm = ChatOpenAI(model="gpt-5.5")

structured_llm = llm.with_structured_output(
    TicketSchema,
    method="json_schema",
)

result = structured_llm.invoke("请从这张火车票图片中提取字段")
```

这里最关键的不是提示词，而是：

- `TicketSchema`
- 字段类型
- 字段描述
- `method="json_schema"`

这几样才是“结构化输出稳定”的主骨架。

**2. Agent 最终返回结构化结果：`create_agent(..., response_format=...)`**

适合：

- 先搜资料，再生成结构化摘要
- 先调工具，再给出结构化审批结果
- 先查订单，再输出结构化匹配结论

```python
from pydantic import BaseModel, Field
from langchain.agents import create_agent


class MatchResult(BaseModel):
    matched: bool = Field(description="是否匹配到订单")
    partner_order_id: str | None = Field(description="命中的订单号")
    confidence: float = Field(description="匹配置信度，0 到 1")
    reason: str = Field(description="判断依据")


def query_order(order_no_prefix: str) -> str:
    """按前缀查询候选订单"""
    return "..."


agent = create_agent(
    model="openai:gpt-5.5",
    tools=[query_order],
    response_format=MatchResult,
)

result = agent.invoke({
    "messages": [
        {"role": "user", "content": "根据识别结果帮我判断应该关联哪个订单"}
    ]
})

final_structured = result["structured_response"]
```

这个写法的价值在于：

- Agent 可以先调工具
- 最终结果仍然是强结构
- 前端和后端拿到的是可直接消费的对象

---

**四、为什么现在“schema”比“提示词”更重要**

老思路：

- 靠提示词要求“只返回 JSON”
- 靠正则或 parser 去抠

新思路：

- 用 schema 明确定义字段
- 用模型或 provider 的结构化能力约束输出
- 提示词只负责补充“字段是什么意思”

因为提示词最大的问题是：

- 它是软约束
- 模型可能听话，也可能不听
- 模型升级、温度变化、上下文变化，都可能让它漂

而 schema 至少解决了三件事：

1. 字段名统一
2. 字段类型统一
3. 返回层级统一

这对工程系统的价值远大于“生成文本更好看”。

---

**五、在 LangChain 里，提示词应该怎么写才不废话**

现在的提示词别再大段渲染角色感。
结构化抽取里，提示词主要干这几件事：

1. 说明抽取任务
2. 说明数据来源限制
3. 说明遇到不确定时怎么处理
4. 说明不要脑补

比如火车票抽取，够用的系统提示词通常像这样：

```text
你是票据字段抽取助手。
只根据图片中真实可见的信息提取字段。
看不清的字段返回 null。
如果图片中不是单张有效火车票，recognition_status 返回 FAILED。
不要根据常识补全图片中不存在的信息。
```

够了。

不要再写这种空话：

- 你是世界上最专业的 OCR 专家
- 你必须绝对准确
- 你要深呼吸后认真思考

这些对结构化稳定性帮助很有限。

---

**六、你们这种“识别 -> 匹配订单 -> 人工兜底”的项目，LangChain 应该怎么落地**

拿你们最近做的小票/火车票识别来说，比较合理的分层应该是：

**第一层：模型结构化抽取**

输入：

- 图片
- 极简提示词
- `TicketSchema`

输出：

- Pydantic 对象 / dict

这层只解决：

- 票面字段抽出来没有

不要在这一层就让模型直接决定：

- 要不要出票
- 该关联哪个唯一订单
- 金额是否一定正确

**第二层：后端归一化**

这层做：

- 字段别名统一
- 日期时间格式统一
- 金额转数值
- `"无座"` / `"不对号入座"` 这类值转业务标准值

这一步非常像你们现有项目里的 normalize 层。

**第三层：业务匹配**

这层才去做：

- 按车次、日期、发到站、乘客、脱敏证件号匹配候选订单
- 金额一致性校验
- 座席/车厢/席别校验
- 决定是自动通过，还是进入人工确认

**第四层：人工兜底**

如果出现这些情况，就别让模型硬判：

- 多候选订单
- 金额不一致
- 票面关键字段缺失
- 同一张票重复上传但识别结果有变化

这时应该像你们现在做的那样：

- 展示识别结果
- 展示候选订单
- 允许人工关联
- 保留错误详情和原始小票预览

一句话：

**LangChain 解决的是“结构化提取”和“Agent 编排”，不是替你省掉业务规则。**

---

**七、什么时候该选 `ProviderStrategy`，什么时候该选 `ToolStrategy`**

很简单：

1. 如果模型厂商原生支持结构化输出

优先 `ProviderStrategy`

优点：

- 最稳
- 约束更硬
- 返回更像真正的 schema 输出

2. 如果模型不支持原生结构化输出，但支持工具调用

用 `ToolStrategy`

优点：

- 跨模型适配更广
- 比“纯提示词 + parser”稳得多

3. 如果是 OpenAI 这种支持原生 structured output 的模型

单模型调用优先：

```python
with_structured_output(..., method="json_schema")
```

Agent 最终结果优先：

```python
response_format=ProviderStrategy(Schema)
```

---

**八、别忽略错误处理，这恰恰是 LangChain 比手搓 JSON 更值钱的地方**

结构化输出线上最常见的错误不是“完全没结果”，而是：

- 字段类型不对
- 返回了两个结构化对象
- 工具和结构化输出一起用时走偏了
- 某个字段漏填

LangChain v1 在 `ToolStrategy` 上已经把这类错误处理当成正式能力了，不是旁门左道。

所以你设计时应该显式考虑：

1. schema 校验失败时，是否允许自动重试
2. 返回多个结构化对象时，是否直接判失败
3. 某些字段缺失时，是回退 null，还是进入人工处理

你如果完全跳过这层，最后还是会退回：

- 一堆 `try/except`
- 一堆手搓正则
- 一堆“模型怎么又没按格式来”的日志

---

**九、别把“能解析”误认为“能上线”**

一套能上线的结构化输出链路，至少要有这几层：

1. `Schema`
2. `Structured output`
3. `Validation`
4. `Normalize`
5. `Business rules`
6. `Human fallback`
7. `Raw response logging`
8. `Prompt / schema versioning`

少任何一层，demo 也许还能跑，线上就未必稳。

---

**十、我给你的最终建议**

如果你现在要写一篇“别太空”的教程，最值得保留的不是“提示词技巧大全”，而是下面这套判断顺序：

1. 先定 schema，不要先写文案。
2. 能用 LangChain 的 structured output，就别先上 OutputParser。
3. 能走 provider 原生约束，就别只靠提示词。
4. 提示词只负责补充抽取规则，不负责充当唯一约束。
5. 结构化输出之后一定要做 normalize 和业务校验。
6. 对多候选、金额冲突、关键字段缺失，直接进入人工兜底。

如果把它压成一句话，就是：

**结合 LangChain v1 之后，“让大模型结构化输出”这件事，重心已经从“怎么骗它吐 JSON”，转成了“怎么用 schema、provider 能力和业务后处理，把输出链路做成工程系统”。**
