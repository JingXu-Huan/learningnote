    操作记录

      这个模型表达什么

      蓝色表示进度已提交，绿色表示已处理但未提交，棕色表示崩溃后的待重放记录。每条记录显示的次数，记录它被处理了几次。

      完成 100 后提交 101，含义是下次从 101 开始。若完成业务后、提交前崩溃，100 可能被再次处理。

      现实里还多一层

      这里每次只交付并处理一条；真实 poll() 可以一次交付很多条，使 position 提前移动。多线程处理必须追踪每个分区的连续完成范围。

      演示中的次数没有模拟数据库幂等。业务唯一键、事务和外部接口幂等仍需单独实现。

      模型假设

      入口固定 20,000 条/秒，每个业务消费者最多处理 4,000 条/秒。使用简化的均匀分配，不代表某个官方 Assignor 的精确算法。

      热 key 模式将 70% 流量放在 P0，其余均分到其他分区；普通模式均分全部流量。消费者行尾显示被分配的入口速率。

      观察边界

      普通组中，一个分区同时只分给一个成员。消费者超过分区数，多余成员没有工作；热分区仍可能超过单成员能力。

      这里展示“完成均衡之后”的放置结果。原生 Kafka 添加 Broker 后，现有副本与 Leader 的迁移仍需另行规划，不会按本图瞬间自动搬完。

      把流量、副本和保留期，算成资源预算

      平均流量用于保留容量，峰值流量用于吞吐。下面是载荷估算器，所有默认值都是教学假设。

      MB / TB 用十进制；KiB / TiB 用二进制。压缩率是输入假设，不是固定性能指标。

      预算项目 计算依据 估算结果
      B = R × S × c
      D = B_avg × 保留秒数 × RF
      磁盘预算 = D / 使用上限
      出站 ≈ B_peak × (RF − 1 + 全量消费组数)

      载荷容量另加索引、段边界、内部 Topic、事务、增长和恢复余量。出站是所有 Broker 的汇总，不等于公网流量或云账单；不包含协议开销、重试与历史回放。还需检查单节点热点与故障后的剩余容量。
