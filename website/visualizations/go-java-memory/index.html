编译器无法将对象安全地安排在栈上时，可以将它分配到堆。堆对象按可达性决定是否继续存活，生命周期不绑定某次函数调用。堆是共享的存储资源；一个对象是否被多个 goroutine 访问，仍取决于引用如何传递。

为什么 Go 的 &u 可以安全返回？

编译器在分配前分析引用流向。需要跨调用存活的值可以直接安排在堆上；“逃逸”不表示运行中先创建栈对象，再在 return 时把它搬到堆上。返回指针的调用若被内联，仍可能避免真实堆分配。

Java 的逃逸分析等于栈上分配吗？

不等于。HotSpot 可能把对象字段拆成独立值，直接消除对象分配；这叫标量替换。它不等于必须保留一个完整对象再放到栈上。JVMS 的抽象对象语义与机器执行后的存储形式需要分开看。

Go 的 new / make 或取地址能决定进堆吗？

不能仅凭语法决定。对象大小、引用流向、内联和编译器版本都会影响结果。使用 go build -gcflags="-m=2" . 查看当前工具链的分析；使用 benchmark 的 -benchmem 观察实际分配。

依据：Go FAQ · HotSpot 性能增强 / Escape Analysis

Go 完全没有 STW 吗？

有。启动标记和终止标记等阶段需要停顿协调。并发标记期间，扫描某个 goroutine 的栈也需要暂停该 goroutine；分配方还可能承担标记辅助工作。不能把“并发 GC”理解为“业务没有任何 GC 成本”。

Go 的写屏障与 Java volatile 是同一种屏障吗？

不是。GC 写屏障服务于对象图在并发标记时的正确追踪；并发内存模型中的同步操作服务于程序读写的顺序与可见性。GC 写屏障不会让业务数据竞争变安全。

G1 必须依次经历 Young → Mixed → Full GC 吗？

不必须。Mixed 依赖一次标记后的候选与回收策略；Full GC 是某些失败或显式触发等情况下的后备路径，不是每次周期的固定末尾。这里回放选取了进入标记并发生 Mixed 的代表性序列。

对象已经在堆上，读线程就一定看得到更新吗？

不能据此保证。切换发布方式，观察两个执行者之间有没有建立 happens-before。
