## 🎉先说索引失效：

### 一、**模糊查询导致失效**

```sql
SELECT * FROM user WHERE name LIKE '%旭';
```

这种以 `%` 开头的模糊匹配，会让索引失效，因为 `MySQL` 无法从索引中定位起始位置，只能全表扫描。
 ✅ 改成 `name LIKE '景%'` 就能用上索引。

------

### 二、**对索引列使用了函数或计算**

```sql
SELECT * FROM user WHERE YEAR(create_time) = 2025;
SELECT * FROM user WHERE age + 1 = 20;
```

函数或计算会破坏索引的有序性，`MySQL` 就无法利用 B+ 树特性进行快速定位。
 ✅ 改成范围匹配：

```sql
SELECT * FROM user 
WHERE create_time >= '2025-01-01' AND create_time < '2026-01-01';
```

------

### 三、**隐式类型转换**

```sql
SELECT * FROM user WHERE phone = 13800000000;
```

如果 `phone` 是 `VARCHAR` 类型，而你写的是数字常量，`MySQL` 会先做类型转换成字符串。类型转换发生在列上，就会导致索引失效。
 ✅ 写成 `'13800000000'`。

------

### 四、**OR 条件中混入非索引列**

```sql
SELECT * FROM user WHERE id = 1 OR name = '景旭';
```

如果 `id` 有索引但 `name` 没有，整个 `OR` 查询的索引都会失效。
 ✅ 改成用 `UNION` 拆两条：

```sql
SELECT * FROM user WHERE id = 1
UNION
SELECT * FROM user WHERE name = '景旭';
```

------

### 五、**复合索引使用不当（违反最左前缀原则）**

假设有复合索引 `(a, b, c)`：
 **只有从左到右连续使用才会用上索引。**

```sql
WHERE a = 1              ✅ 用
WHERE a = 1 AND b = 2    ✅ 用
WHERE b = 2              ❌ 失效
WHERE a = 1 AND c = 3    ✅ 只用到 a
```

------

### 六、**范围查询截断了索引**

```sql
SELECT * FROM user WHERE a = 1 AND b > 5 AND c = 10;
```

因为 `b > 5` 是范围条件，索引只能用到 `(a, b)`，`c` 会被截断不用索引。
 ✅ 改写思路或调整索引顺序。

------

### 七、**`MySQL` 优化器“认为”全表扫描更快**

当表很小，或者条件筛选率很低时（返回行数多），`MySQL` 优化器可能判断**扫描索引再回表反而慢**，于是放弃索引。
 这种不是失效，而是优化器的选择。

------

如果你想精准知道某条 SQL 是否用了索引，可以用：

```sql
EXPLAIN SELECT ...
```

它会告诉你走了哪个索引、是否全表扫描等信息。

## 🎉再说索引下推：

### 一、主键索引查询时，`ICP` 直接没用

原因很简单：
 **主键索引是聚簇索引**，整行数据就在索引里，不存在“回表”问题。

`ICP` 的设计目标是“减少回表”，所以在主键索引查询中，它连出场机会都没有。

示例：

```sql
SELECT * FROM user WHERE id = 10;
```

这种直接用主键查的语句，`ICP` 不参与。

------

### 二、**覆盖索引**查询也不会触发 `ICP`

所谓“覆盖索引”（covering index），就是查询的字段全都能从索引中拿到，无需回表。

这时 MySQL 直接在索引里完成过滤和返回结果，根本不需要“下推”。

示例：

```sql
SELECT name, age FROM user WHERE name LIKE 'A%' AND age = 20;
```

如果 `idx_name_age(name, age)` 是覆盖索引，那么这条查询完全不需要 `ICP`。
 ——你连“下推”的机会都不给它，因为已经在索引里读完了。

------

### 三、使用 **非索引字段** 进行过滤时失效

`ICP` 只能在索引树扫描阶段提前过滤，
 如果你的过滤条件依赖的字段不在索引里，那就没法下推。

示例：

```sql
SELECT * FROM user
WHERE name LIKE 'J%' AND city = 'Beijing';
```

假设索引只有 `(name, age)`，
 那 `city` 不在索引中，只能在回表后判断，`ICP` 也救不了。

------

### 四、**函数或隐式类型转换** 会让索引条件下推失效

如果你的条件用函数或运算处理了索引列，
 优化器就认为索引无法直接利用，于是 ICP 不会触发。

比如：

```sql
WHERE LOWER(name) = 'jack'
WHERE age + 1 = 20
WHERE DATE(create_time) = '2025-10-15'
```

这些都会让 MySQL 放弃使用索引下推，因为索引中存的是原始值，无法对计算结果进行高效匹配。

------

### 五、**OR 条件** 通常会禁用索引下推

当 `WHERE` 子句里有多个 OR 连接的条件时，
 MySQL 会优先使用“全表扫描 + 过滤”策略，`ICP` 多半派不上用场。

例如：

```sql
SELECT * FROM user
WHERE name LIKE 'A%' OR age = 18;
```

优化器发现你要查的可能跨多个索引范围，
 于是干脆全拉回来过滤，这时索引下推失效。

------

### 六、**全表扫描（ALL）或全索引扫描（index）**

`ICP` 只在使用**索引范围扫描（range）、`ref`、`eq_ref`** 等访问方式时才有效。
 如果优化器判断这条 SQL 直接走全表扫描，那索引下推就没意义。

可以通过 `EXPLAIN` 看访问类型（type 列）：

- `type = range/ref/eq_ref` → 可能使用 ICP；
- type = index/all → 不会使用 ICP。

------

### 七、存储引擎或版本不支持

- ICP 仅支持 **InnoDB** 和 **MyISAM**；
- MySQL 版本需 ≥ 5.6；
- 对分区表（partitioned table），某些复杂查询场景下 ICP 也可能被禁用；
- 如果 `optimizer_switch` 参数中手动关闭了 `index_condition_pushdown=off`，自然也没戏。

------

### 八、组合索引中断时，`ICP` 会部分失效

假设有复合索引 `(a, b, c)`：

- 条件用到了前缀部分：`a = 1 AND b > 2 AND c = 3`，
   那 `ICP` 可以在扫描过程中对 `c = 3` 下推过滤；
- 但如果中间断了，比如 `a = 1 AND c = 3`，
   b 这一列跳过了，`ICP` 就无法正常发挥，只能回表再判断 `c`。

------

### 九、JOIN 查询中，如果表的访问方式不是 index/range/ref，也会失效

比如 MySQL 决定对被驱动表执行全表扫描或临时表操作，
 `ICP` 无法介入，只能在 Server 层做过滤。

------

### 🔎 小结一句话：

> 索引下推只在“用到二级索引 + 有额外过滤条件 + 可从索引读取字段”时有效。
>  一旦函数化、OR化、非索引化、覆盖化、主键化，`ICP` 就失效。
